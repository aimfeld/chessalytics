<assumption_delta_decision>
**Noun now primary:** *Stockfish engine instance on the Train solve screen* — previously
exactly one (`useTrainGradingEngine`), now two.

**Decision: `add-alongside`.** Mount a second, independent `useStockfishEngine`
scoped `enabled: isExploring`, alongside the untouched session-scoped grading engine.
Rationale, grounded in 200-RESEARCH.md's finding: grading is idle throughout the entire
reveal/exploration window (it only re-fires on the NEXT puzzle, by which point exploration
has already torn down), so there is no contention for a priority queue to arbitrate; the
two are separate `Worker` objects with no shared dispatch queue and no shared
`generationRef`, so an exploration search structurally cannot disturb the next puzzle's
grading; and `useStockfishEngine` already carries the debounce, the stale-search discard,
and teardown-on-`enabled`-toggle that EXPLORE-05 asks for, in code that has shipped on the
Analysis page since Phase 154-161.

**Accepted debt.** Engine ownership on this screen is now plural without a shared
supervisor. What would force a later `promote` to one arbitrated engine: (a) a feature that
needs grading and exploration searching *concurrently* (e.g. pre-grading the next puzzle
while the user explores the current one), or (b) a measured mobile memory regression
attributable to the second Stockfish worker specifically. Neither is in evidence today —
the Analysis page already sustains 4 concurrent WASM/ONNX workers on the same device class,
and Train's worst case here is 2 lite single-thread Stockfish workers with zero ONNX
involvement.

**Reversibility gates:** no decision in this plan rates `one-way`. Nothing is persisted, no
schema changes, no public API changes, no migration. Consequently no `checkpoint:decision`
task is inserted. Per-task ratings are recorded inline below.
</assumption_delta_decision>

*Following the live side to move.* There is no `isDraggablePiece` / `canDrag` / turn-restriction prop on
