<objective>
Give the browser the two handlers that turn a delivered push into a visible
notification and a click into a focused `/train` window, wired into the
Workbox-generated service worker through `workbox.importScripts` — the one
mechanism that does not require touching the hand-tuned `generateSW` config —
and close the cache-header gap that would otherwise let a stale `push-sw.js`
survive a deploy.

Purpose: completes the browser leg of the tracer proven in plan 201-01. Without
it, a push lands on the device and renders nothing.

Output: `frontend/public/push-sw.js`, a one-key addition to
`frontend/vite.config.ts`, a `/push-sw.js` entry in `deploy/Caddyfile`'s
`@nocache` matcher, and a Vitest suite that executes the service-worker script
in a stubbed scope.
</objective>

**`frontend/public/push-sw.js`** — a plain, un-bundled script that runs in the
service-worker global scope. Start from `201-RESEARCH.md` Code Example 6 and
harden it:

`push` handler: read the payload defensively — `event.data` can be `null` when
a push arrives with no body, and `event.data.json()` throws on a malformed
payload. Wrap the parse in `try`/`catch` and fall back to an empty object, then
build options with `body` from `data.body`, `tag` fixed to the string
`train-reminder` (D-14 — this must match the backend's
`REMINDER_NOTIFICATION_TAG` exactly, or a backlog would stack notifications
instead of collapsing), `renotify: false`, `icon: '/icons/icon-192.png'`,
`badge: '/icons/icon-192.png'`, and `data: { url: data.url || '/train' }`. Title
falls back to `'Time to train'`. The whole `showNotification` promise goes
inside `event.waitUntil(...)` — an unhandled rejection there terminates the
event and silently drops the notification, so attach a `.catch()` that swallows
a rejected `showNotification` (which is what a permission revoked mid-flight
looks like) rather than letting it escape.

`notificationclick` handler (D-13): `event.notification.close()` first, read the
target from `event.notification.data?.url` with `/train` as the fallback, then
inside `event.waitUntil`, `clients.matchAll({ type: 'window', includeUncontrolled: true })`;
if any client is returned, call `client.focus()` and, when `navigate` is
available on it, `client.navigate(targetUrl)`, and return — do NOT also open a
window (that is exactly the duplicate-tab pile-up D-13 exists to prevent).
Only when the list is empty call `clients.openWindow(targetUrl)`.

Add a header comment stating: this file is loaded by
`importScripts(['/push-sw.js'])` from the Workbox-generated `sw.js`; it is NOT
part of the precache manifest, so it is not content-hashed and is not
automatically cache-busted by a deploy — `deploy/Caddyfile` gives it
`Cache-Control: no-cache` for that reason. Also note that its notification
`tag` is the same literal as the backend's `REMINDER_NOTIFICATION_TAG`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| push service -> service worker | An encrypted payload authored by our backend arrives in the browser's SW global scope and is rendered to the OS |
| CDN/static origin -> browser SW | `/push-sw.js` is fetched as an `importScripts()` sub-resource under ordinary HTTP caching rules |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-201-08 | Tampering | Stale `/push-sw.js` surviving a deploy via browser heuristic caching | medium | mitigate | `/push-sw.js` joins the `@nocache` matcher in `deploy/Caddyfile`, forcing revalidation on every fetch regardless of whether the outer `sw.js` changed. |
| T-201-09 | Tampering | Switching VitePWA to the inject-manifest strategy to obtain push handlers | medium | mitigate | `workbox.importScripts` achieves the same result with a one-key change; the acceptance criteria pin `git diff --numstat frontend/vite.config.ts` to exactly one insertion and zero deletions, and re-assert `navigateFallback: null` and the `.onnx` `globIgnores` entry are still present. |
| T-201-10 | Denial of Service | An unhandled rejection inside `event.waitUntil` terminating the SW event and silently dropping the notification | medium | mitigate | The payload parse is wrapped in `try`/`catch` with an empty-object fallback, `showNotification` carries a `.catch()`, and both the null-payload and throwing-payload cases are pinned by tests. |
| T-201-11 | Information Disclosure | Notification content rendered on a locked screen | low | accept | The body is `"Day N is waiting."` — server-computed, no game data, no PII, no HTML/script surface in an OS notification's plain-text fields. |
| T-201-12 | Spoofing | A forged push rendering an arbitrary notification | low | accept | The push service only delivers payloads that decrypt against the subscription's own `p256dh`/`auth` pair and carry a valid VAPID signature; forging one requires the subscription's private key material, which never leaves the browser. |
</threat_model>
