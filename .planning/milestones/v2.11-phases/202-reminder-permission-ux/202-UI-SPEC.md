# Phase 202 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase adds **zero new visual language**. It wires three native browser
APIs into two existing, already-styled surfaces (`TrainScoreScreen`,
`TrainScheduleSettings`) using exclusively components, tokens, and spacing
already present in the codebase. Every value below is a *reuse* citation, not
a new choice, except where explicitly marked "New — Claude's Discretion
resolution" (the six items CONTEXT.md left open).

## Resolved — Claude's Discretion Items

CONTEXT.md left six items open. Resolutions (grounded above; restated here for a single reference point):

1. **Hour picker hidden vs. disabled when the master toggle is off:** **Hidden.** The picker only renders once `reminder_enabled` is (or is about to become, via D-09's async exception) `true`. Rationale: D-09 already lets the hour be corrected anytime after enabling via the normal debounced save, so hiding it while off carries no "stuck with a wrong hour" risk — it just avoids showing an editable control with no live effect. Simpler to implement and reason about than a disabled-but-visible state.
2. **"Remind me" button icon/copy + D-03 confirmation copy:** `Bell` icon + "Remind me" (D-01/D-02); confirmation is "Reminders on — HH:00 on your training days", `Check` icon, `text-muted-foreground` — see Copywriting Contract.
3. **Where `ensureDeviceSubscribed()` lives:** a plain async module, `frontend/src/lib/push.ts` (not a hook — both call sites invoke it imperatively from inside a click handler / `onCheckedChange`, and D-13's error-state integration needs a plain promise, not a rendered hook value). Obtains the registration via `navigator.serviceWorker.ready` (not `getRegistration()` — the purpose-built "wait for active SW" promise; see 202-RESEARCH.md Open Question 1).
4. **Score-screen surface: own component or inline:** extract `TrainReminderButton` (or equivalent) rather than inlining — it carries D-01 (visibility derivation), D-02 (click handler), D-03 (success swap), and the loading/error states above, which is roughly `TrainScheduleSettings`'s own `ScheduleCardShell`-sized extraction, and keeps `TrainScoreScreen.tsx` under CLAUDE.md's nesting/LOC limits.
5. **Test strategy for `PushManager`/`Notification.permission` under jsdom:** `vi.stubGlobal('Notification', {...})` + `Object.defineProperty(navigator, 'serviceWorker', {...})`, following the existing `vi.stubGlobal('Worker', ...)` / `vi.unstubAllGlobals()` precedent in `useTrainGradingEngine.test.ts:71-76`. `urlBase64ToUint8Array` gets its own dedicated unit test (pure function, cheap to isolate, explicitly named as worth it in CONTEXT.md).
6. **Placement of the toggle+picker block within the "Train schedule" card:** as the **third** sibling block, after `Puzzles per session`, inside the existing `flex flex-col gap-4` wrapper (`TrainScheduleSettings.tsx:215`). Reading order becomes: define your schedule (days) → size your sessions (puzzle count) → get reminded about it (toggle + hour) — reminders are a consequence of the schedule above them, so they read last, not interleaved.
