<objective>
Wave 1 of Phase 205 (Proposal B, locked as first by D-01): the free-play board's ROOT ply
stops being graded by a fresh MultiPV-2 search of the post-move position and is instead
graded from the settled MultiPV-4 mount search that produced the reveal's "Also fine" row.

Purpose: this is the bug users actually hit (SEED-137 case 2, prod drill session 107 —
a puzzle whose reveal reads "Several moves are fine here… Also fine: Qh4", where playing
Qh4 on the reveal board badges it a mistake). No threshold value can fix it: it is
browser-vs-browser, two independent Stockfish searches of the same position measuring the
same cutoffs at different budgets. The fix is to stop asking the second oracle a question
the first one already answered.

This plan is also the phase's tracer: it wires ONE path — mount search → `GradeResult` →
`freePlaySeedEval` → `seedEval` → `currentQuality`'s root branch — end to end through every
layer Phase 205 touches on the frontend, and proves it with a real end-to-end component
test before any horizontal expansion.

Output: `rankLineForMove` relocated to `uciParser.ts` beside a new from+to variant, a new
optional `lines` field on `GradeResult`, one threading seam through `TrainSolveScreen`, one
new branch in `useTrainFreePlay`'s `currentQuality`, and four automated tests (one of them
mutation-proved in each direction).

**Deliberately NOT in this plan** (D-04, D-08, D-09, all locked): unranked root moves keep
today's cross-oracle path; the "Also fine" row stays at three alternatives; the mount search
keeps `TRAIN_GRADING_MULTIPV_WIDTH = 4` at 1500 ms; free play stays on its own Worker.
</objective>
