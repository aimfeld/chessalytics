<objective>
Wave 2 of Phase 205 (Proposal A, gated on wave 1 landing per D-01): stop serving Train drill
items whose margins are too thin for a browser search to adjudicate. A selection-level dead
band excludes any own-blunder whose node-0 best-vs-second expected-score drop sits in
`[INACCURACY_DROP, BLUNDER_DROP)` = `[0.05, 0.15)`, together with both of
`classify_puzzle_type`'s degenerate node-0 shapes (D-03).

Purpose: this closes SEED-137 case 1 — a puzzle the server labels "one move is clearly better"
where the browser prices that same runner-up as an inaccuracy and awards the point. No
threshold change can fix it (raising `SHARP_GAP_ES` was explicitly rejected in the seed: it is
an identity, not a knob, and it converts case 1 into case 2). Filtering the pool is the fix.

The band is enforced **live at all three SR selection sites** and **never snapshotted onto
`drill_items`** — which is exactly what makes criterion 4 true by construction rather than by
a backfill: an item that a later reclassification moves into the band simply stops being
selected, and one that moves out of it resurfaces on its own.

Output: one SQL ply-parity helper, one shared predicate, three one-line `.where()` additions,
two retuned test fixtures, roughly a dozen tests, and a CHANGELOG entry that ships the
measured cost as a number.

**The measured cost is 34.80% of the pool, not the 12% the phase was scoped on.** D-02 locks
this as measure-and-record, not a gate ("the band ships regardless of the fresh number"), so
it does not re-open D-01 or D-11 and is not a decision point at execution time. Task 3 exists
so the number ships as documentation rather than as a later discovery.

Requirement IDs, the phase-wide artifact list and the edge-probe accounting are defined in
`205-01-PLAN.md`. Eleven of the fifteen probe rows are authored into this plan's

## Two findings from planning that change what you would otherwise write

**1. Two existing default test fixtures sit inside the band and will break the suite.**
`tests/repositories/test_train_repository.py` and `tests/routers/test_train.py` each define a
module-level default `missed_pv_lines` blob with `b = 40` and `s = -30`. Its expected-score
drop is **0.0643**, squarely inside `[0.05, 0.15)`. Dozens of composition, waiting-count and
router tests seed material with it. The moment the band lands at `pool_entry_stmt`, every one
of them composes an empty session. Retuning both to a drop comfortably below
`INACCURACY_DROP` (holding `b = 40` and moving `s` to `30`, giving a drop of ~0.0092) keeps
their classification exactly as it is today (both were, and remain, "soft" — the old drop was
already below `SHARP_GAP_ES` = 0.10), so no assertion elsewhere shifts. This is Task 1's work,
not an optional cleanup, and running the FULL backend suite is the gate that proves no third
fixture has the same problem.

**2. Cast the centipawn keys to a float type, not an integer type.** `_ladder_field`'s
precedent casts to an integer type, but it operates on a differently-shaped blob. Here the
boundary tests construct `b` by the exact inverse of the sigmoid, which is a non-integer, and
an integer cast of a non-integer text value **raises** in Postgres. A selection predicate that
can raise violates the total-operator discipline `answer_key_present`'s docstring establishes.
Cast `b`/`s` to a float type and `bm`/`sm` to an integer type (mate distances are whole
numbers and are only null-checked and sign-compared).
