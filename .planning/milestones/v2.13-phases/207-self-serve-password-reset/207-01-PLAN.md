## The noun that shifted: `hashed_password == ""`

**Before this phase**, an empty `hashed_password` had two meanings fused into one value:
(a) "this account has no password credential", and (b) "this account authenticates by
Google SSO or is a guest" — i.e. an *account type*. `app/services/guest_service.py` writes
`hashed_password=""` at `:40` (guest creation) and `:156` (Google promotion, comment:
"Google users have no password").

**After the D-04 reversal (operator, 2026-08-08)** the two meanings must be actively pulled
apart, because this phase introduces **the first production read of `hashed_password` as a
predicate** and the prod numbers show the two readings give different answers for the
majority of the target population:

| Group | Password | Google linked | Count | Eligible? |
|---|---|---|---|---|
| Pure email/password | `$argon2id$…` | no | 47 | yes |
| **Both** | `$argon2id$…` | **yes** | **125** | **yes** |
| Google-only | `''` | yes | 44 | no |
| Guests | `''` | no | 304 | no |

Reading the gate as *account type* ("is this a Google account?") answers **no** for 125
accounts that must get **yes**. Reading it as *credential state* ("is there a password to
reset?") is correct for all four rows. Guests share the empty hash, so no separate `is_guest`
check is needed.

**Decision: `no-change` on the data model; the semantics are pinned explicitly instead.**

Rationale for no new field: a `has_password` column would be derived state duplicating
`hashed_password != ''`, it would need a migration (an explicit ROADMAP non-goal), and it
would create a second source of truth that can drift on every password write. `is_guest`
remains the real account-type discriminator and this phase adds no reader of it.

What replaces the field is an **invariant, not a schema change** (Task 3): the empty-hash
comparison is permitted at exactly one site, it is documented there as credential state, and
`tests/test_users_account_type_invariant.py` fails if a future phase either (a) re-fuses the
account-type reading onto it, or (b) derives reset eligibility from `oauth_account`. The
125-account dual case is the executable form of that invariant — it is the regression a
plausible "skip Google accounts" implementation causes, and it is the majority of the
population, so it is a first-class test rather than an edge case.
</assumption_delta_decision>

**Email service** — create `app/services/email_service.py` mirroring `push_send.py`'s shape:
`_EMAIL_TIMEOUT_SECONDS = 10.0`; `is_email_configured() -> bool` returning truthiness of

say so in a comment); and `async def send_password_reset_email(client: httpx.AsyncClient, *, to: str, reset_url: str, user_id: int) -> bool`.
The send returns `False` immediately when unconfigured, builds the payload with `from` composed
from `settings.MAIL_FROM`, a single `to`, a fixed subject, and both `html` and `text` parts,
sets the bearer `Authorization` header, and issues exactly one POST with no retry loop.
Error handling has exactly two branches mirroring `push_send.py`: an `httpx.HTTPError` except
block, and a `resp.status_code >= 300` branch. Both set the Sentry tag `source` to
`email_service`, put variable values only into `set_context`, and pass a constant message.
Add a comment at the non-2xx branch recording that a Resend 429 (10 req/s per team) is
expected to land here and must NOT be "fixed" later by adding retry, per COVERAGE.md § 7.

**Manager hook** — add `on_after_forgot_password(self, user: User, token: str, request: Request | None = None) -> None`
to `UserManager` in `app/users.py`, placed after `on_after_login` and before `get_user_manager`
so the three `on_after_*` hooks stay grouped. Body, in four steps and in this order:

  1. **Eligibility gate (RESET-05).** If the user has no stored password, `return` silently.
     The predicate is the emptiness of `user.hashed_password` and nothing else. Do NOT consult
     `user.oauth_accounts`, the `oauth_account` table, or `user.is_guest`, and do NOT inspect
     the hash's algorithm prefix. Write a comment at this line stating the semantics in the
     terms that make it correct: it means "this account has no password to reset", NOT "this
     is a Google account" — 125 of the 172 eligible prod accounts hold BOTH a password and a
     linked Google account, so an account-type reading strands 73% of the target population.
     Guests share the empty hash, so no separate `is_guest` check is needed.
  2. Consult `reset_password_limiter.is_allowed(user.email.lower())` and `return` silently
     when it rejects.
  3. Build the reset URL as `settings.FRONTEND_URL` + `/auth/reset-password?token=` + the token.
  4. Dispatch the send.

Order matters only for clarity, not for observability: both guards are in-memory and neither
is on a network path, so neither can introduce a timing tell. Eligibility comes first because
the limiter exists to protect the Resend cap and prevent mail-bombing, and an ineligible
account can cause neither — spending its limiter slots would be meaningless bookkeeping.

Import the email service as a module (`from app.services import email_service`) and call it as
a module attribute, NOT via `from ... import send_password_reset_email` — the tests monkeypatch
that attribute and a direct name import would bypass the patch.

Four constraints on this hook that are the whole reason it exists as an override rather than
a router dependency, and which the executor must not "improve":
  1. It must never raise — for either guard. The library router only catches `UserInactive`
     from `forgot_password()` (verified, `router/reset.py:56-59`); anything else becomes a 500,
     and a 429 or a 403 here would be an enumeration oracle. Both rejections are silent no-ops,
     deviating from both existing limiter call sites which do raise (RESEARCH Pitfall 1,
     PATTERNS "Deviation to flag explicitly").
  1b. Neither guard may log, emit a Sentry event, or increment anything observable that
     distinguishes which branch was taken. "Skipped: no password" is exactly the kind of
     helpful debug line that turns an anti-enumeration contract into an oracle for anyone
     who can read logs.
  2. The reset URL host comes only from `settings.FRONTEND_URL`. Do not read the `Request`
     object's `Host`, `X-Forwarded-Host`, or `base_url` to build it (T-207-09).
  3. Neither the token nor the assembled reset URL may be passed to `logger`, to
     `sentry_sdk.set_context`/`set_tag`, or into any exception message anywhere in this
     phase — including any convenience "print the link in dev" affordance, which is
     explicitly forbidden (T-207-08).

## Trust Boundaries

| Boundary | Description |
|---|---|
| anonymous internet → `POST /api/auth/forgot-password` | Unauthenticated, attacker-chosen email string crosses here. Triggers outbound mail. |
| anonymous internet → `POST /api/auth/reset-password` | Unauthenticated token + new password crosses here. Changes a credential. |

| Reset link → browser URL bar / history / `Referer` | The token sits in a URL, so it is exposed to history, and to any third-party asset the reset page loads. |
