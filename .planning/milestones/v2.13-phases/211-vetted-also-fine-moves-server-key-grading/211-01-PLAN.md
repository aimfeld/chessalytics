## Background

Four facts were established by reading the tree during planning; the executor should not
re-derive them.

1. **`reveal_for_puzzle` needs no change** (RESEARCH Open Question 2, R13). It already
   OUTER JOINs `HerringPool` on `DrillSolve.herring_pool_id` and already reads the
   `GameFlaw` blob with `undefer(GameFlaw.missed_pv_lines)` in its SR branch. `record_solve`
   is the one that has neither — it calls `_classify_solve_puzzle_type`, which reads the
   blob but returns only the type, and never touches `herring_pool` at all.
2. **Delivery surface: `SolveResponse`, not `PuzzleRevealResponse`** — a deliberate
   deviation from RESEARCH's primary recommendation (R1), recorded here as required.
   Reasons: (a) `record_solve` must load the key ANYWAY for the D-07 override, so putting
   the list on the reveal GET would compute the same key in two places, which is precisely
   the two-sources-of-truth disease this phase exists to cure; (b) it lands synchronously
   with the verdict, closing the async window Phase 206's `source` field was moved onto
   this same response to close; (c) `trainRevealCache` already round-trips the whole
   `SolveResponse`, so the back-button restore gets the vetted list for free with no cache
   migration; (d) the reveal endpoint's 409 shape stays byte-identical, which makes
   VETFINE-02 a pure regression assertion. Consequence: RESEARCH Assumption A4 (the
   reveal-GET 409 race) is moot for this phase — no key material moves through that
   endpoint — and is discharged by a regression assertion that the reveal body's key set is
   unchanged.
3. **`test_pre_attempt_payload_shape` already exists** (`tests/routers/test_train.py:958`)
   and asserts `set(puzzle.keys()) == {six fields}` by EQUALITY. It is the P-01 guard;
   it must stay green untouched.
4. **The severity ladder must be shared.** `app/services/flaws_service._classify_severity`
   has exactly one production call site (line 388) plus a test import — a public rename is
   cheap and makes the "one severity ladder, server-side" contract explicit now that
   `train_pool` needs it too.

### Planner assumption — reconciling SC-3's "with no engine search"

ROADMAP Success Criterion 3 says a vetted move yields a verdict "with no engine search".
Under D-07 (LOCKED, and the resolution this phase adopts) the client still asserts
`move_quality` in every `SolveRequest` and the request schema does not change — so the
client MUST have completed its own after-move search before it can POST. The client
therefore still waits its ~1.5 s "Checking your move…" for a vetted non-best move; its
result is simply DISCARDED by the server for key moves.

The reading this plan adopts: "no engine search" qualifies the VERDICT, not the client's
wall clock. The verdict is computed from stored evals only. The latency claim in SEED-150
("needs no search at all, instant") is NOT deliverable without either handing the client
answer-key material pre-attempt (reopens POOL-10 / P-01 — a 1-to-5-move hash set over ~35
legal moves is trivially brute-forced, so even an obfuscated form is forbidden) or changing
`SolveRequest` (forbidden by D-07). This is recorded as an accepted residual, alongside the
related cost SEED-150 already acknowledged: a vetted non-best move now incurs the
after-move search it used to skip via the rank-match fast path.
