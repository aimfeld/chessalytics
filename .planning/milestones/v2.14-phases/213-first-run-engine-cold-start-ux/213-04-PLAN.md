<objective>
Close the failure half of the cold start: two genuinely different terminal
states, one silent retry before asking the user for consent to spend another
45.7 MB, and the telemetry that tells us what real devices actually experience.

The two terminal states are two populations, not one (project memory "Maia
iOS: two failure populations"): a device without WASM SIMD can never run Maia,
so offering Retry there is a lie; OOM and worker death usually do work on
retry.

Purpose: nobody is trapped behind a non-dismissible modal, and we finally have
data on real-device wait times — of which there is none today beyond the single
originating report.
Output: the D-14 terminal states, the D-15 retry ladder, and the D-16/D-17
Umami and Sentry wiring.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| App → Umami (3rd party) | Event names and string props leave the browser. |
| App → Sentry (3rd party) | Exception messages, tags and device context leave the browser. |
| Worker error messages → host | `{ type: 'error', message }` strings originate in worker code and third-party ORT. |

## STRIDE Threat Register (ASVS L1, block on `high`)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-213-02 | Denial of Service | `EngineReadyGate` non-dismissible `Dialog` | high | mitigate | Without a terminal state a failed or incapable engine leaves a modal with no exit over a live board. Every non-ready path now resolves to `'unsupported'` (dead end with an explanation) or `'failed'` (Retry). Task 2's zero-buttons and Retry-works tests are the proof; this is the threat that justifies the plan. |
| T-213-04 | Information Disclosure | Umami event props | low | mitigate | Wait durations ship as bucketed labels from a fixed tuple, never raw timings or identifiers; no user id, game id or FEN is attached. Asserted by the payload tests. |
| T-213-09 | Information Disclosure | Sentry device context | low | accept | `userAgent`/`hardwareConcurrency`/`deviceMemory` are standard Sentry device context already collected by the initialised SDK; adding them explicitly to the two terminal captures exposes nothing new and is what makes the two failure populations separable. |
| T-213-10 | Spoofing / grouping integrity | Sentry message strings | medium | mitigate | Interpolating a worker-supplied error string into the message would fragment Sentry grouping into one issue per device (the project's explicit anti-pattern). Messages are fixed literals; variable data goes in `tags`/`contexts`. Enforced by the no-interpolation acceptance criterion. |
| T-213-11 | Denial of Service | D-15 retry ladder | medium | mitigate | An unbounded retry loop would re-download 45.7 MB repeatedly on a flaky link. `MODEL_FETCH_ATTEMPTS = 2` bounds the silent path and every further attempt requires an explicit user tap. |
| T-213-SC | Tampering | package installs | low | accept | No new packages. `@sentry/react` and `@/lib/analytics` are already integrated. No install task, so no legitimacy checkpoint. |

ASVS V2/V3/V4/V6 do not apply. V5 applies only to the already-covered
`Content-Length` path (T-213-01, Plan 01).
