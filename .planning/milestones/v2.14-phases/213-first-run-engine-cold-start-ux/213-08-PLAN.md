<objective>
Fetch the Stockfish `.wasm` once per page load and share it with every Worker that
needs it.

This is the headline repair for `G-213-35` and it is a real performance fix, not a
progress-bar cosmetic. The analysis board constructs between five and eight
independent Stockfish Workers — `workerPool.ensureSpawned()` builds
`computePoolSize()` of them (up to `DESKTOP_POOL_MAX` = 4) in one synchronous loop,
`useStockfishEngine` adds a standalone one, and `useStockfishGradingEngine` is
mounted twice by `Analysis.tsx` plus once more behind `useGemSweep`. Each one
instantiates its own copy of the same 7,295,411-byte binary, and because every
request is issued in the same tick the HTTP cache cannot dedupe any of them. That is
between 29 MB and 51 MB of duplicate transfer on every desktop cold start, and the
progress store counts one copy of it.

The mechanism is the vendored glue's own already-shipped wasm-path override: the
worker script reads its `.wasm` URL out of `self.location.hash`
(`stockfish-18-lite-single.js`, worker entry — `u = decodeURIComponent(hash[0] || …)`),
and `instantiateWasm` streams from exactly that URL. Fetch the binary ONCE on the
main thread with the same streaming reader the Maia worker uses, publish it as an
`application/wasm` Blob object URL, and hand that URL to every Worker through the
hash. Zero network for workers two through eight. The vendored file is not edited.

Deliberately NOT serialising spawns behind the HTTP cache instead: DevTools
"Disable cache" is normally on while throttling, which removes second-visit dedupe
entirely — and the closing acceptance check for this gap is measured under exactly
those conditions.

Purpose: G-213-35 `missing` items 1 and 2 (stop fetching the same wasm N times; make
the bar's denominator equal the bytes actually transferred).
Output: one shared Stockfish worker source module, every construction site routed
through it, and the `stockfish-wasm` accounting reduced to a single honest transfer.

Explicitly out of scope, per the gap entry: the per-chunk `commit()` re-render storm
in `Analysis.tsx`. It is documented there as not needed to explain any observed
symptom, and this plan must not bill anything as its repair. If the closing human
check in `213-09` finds the bar accurate but janky, that is the follow-up seed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> same-origin static assets | unchanged origin, unchanged path, unchanged 30-day `Cache-Control` (`deploy/Caddyfile` `@vendored_runtime`). The same bytes are fetched from the same URL; only the number of times changes. |
| main thread -> Worker | new: a same-origin `blob:` object URL is handed to the Worker through its own location hash and fetched inside the Worker. No third-party origin is introduced and no remote code is loaded — the bytes come from the same `/engine/` path they always did. |
| vendored glue -> app | unchanged. The glue file is not edited; only its already-shipped hash-based wasm-path override is used. |

No new network surface, no server surface, no authentication path, no user input, and
no package-manager installs. The supply-chain threat row does not apply and no
package-legitimacy checkpoint is required.
