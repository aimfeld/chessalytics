<objective>
Move ownership of the onnxruntime-web runtime bytes to the main thread, so the gate
can count them and so only one build is ever fetched.

`G-213-35`'s second half. Today the ORT runtime binaries are fetched by
onnxruntime-web itself inside `InferenceSession.create()`, resolved off
`ort.env.wasm.wasmPaths = '/maia/'`. They never touch a streaming reader, post no
`progress` message and have no asset id, so 13.5 MB (wasm-only) or 24.3 MB
(WebGPU/asyncify) transfers with the bar showing nothing.

Worse, on a device whose WebGPU adapter lacks `shader-f16` — confirmed on the
reporter's Brave via `Program Cast requires f16 but the device does not support it` —
BOTH are fetched. The worker loads the WebGPU bundle, pulls 24.3 MB, fails the D-14
warmup `analyze()`, posts `webgpu-unavailable`, and the host respawns a replacement
pinned to wasm which pulls another 13.5 MB. That is 37.8 MB to end up exactly where a
straight wasm boot would have started.

**The design (revised — supersedes the in-worker approach):** the main thread owns the
bytes. `maiaWorkerHost` probes the adapter, picks ONE build, streams it once with a
reader that reports progress under a new `ort-runtime` asset id, and hands the buffer
to the worker at spawn. The worker sets `ort.env.wasm.wasmBinary` and creates the
session, issuing no runtime request of its own.

Why this shape rather than fetching inside the worker:

- **It cannot double-fetch.** The in-worker design avoids the second build by getting
  the `shader-f16` probe right. This one only ever fetches the build it hands over, so
  a wrong probe costs the wrong backend, never a wasted 24.3 MB.
- **The respawn path collapses.** The host already hands the model buffer from the
  dying WebGPU worker to its wasm replacement (G-213-8). The runtime buffer travels the
  same way, and the host — which already knows the replacement is wasm-only — fetches
  the right build directly instead of discovering it a second time.
- **One progress path.** No worker->host `progress({asset:'ort-runtime'})` plumbing at
  all; the thread that fetches is the thread that reports.
- **Both surfaces for free.** `acquireMaiaWorker()` is the single choke point every
  Maia consumer funnels through — `maiaQueue.ts` for the analysis board and its gem
  sweep, `useMaiaEngine.ts` for bot play. Placing the fetch there serves both with no
  per-surface wiring, and `requiredEngineAssets()` is already unconditional, so both
  `EngineReadyGate` mounts count the new asset the moment it is registered.

The glue bundles stay where they are: `ort.wasm.min.js` is 50 KB and
`ort.webgpu.min.js` is 67 KB, so leaving `importScripts` in the worker costs nothing
measurable. All the weight is in the `.wasm`, which is exactly what `wasmBinary` takes.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> same-origin static assets | unchanged origin and unchanged paths. The same vendored binaries are fetched from `/maia/`; what changes is who issues the request (the main thread, with a reader) and how many are issued (one instead of two). |
| main thread -> WebGPU adapter | new read, relocated from the worker: the adapter's advertised feature set is inspected before a build is chosen. Read-only capability inspection; no device is requested and no state is changed. |
| main thread -> worker | the init message gains a backend discriminator and a transferred `ArrayBuffer`. Both originate from our own same-origin fetch, never from user or game data. |
| worker -> onnxruntime-web | the runtime binary is handed to the library as bytes instead of being resolved by it from `wasmPaths`. The bytes come from the same path the library would have used, and the `.mjs` loader still resolves through `wasmPaths`. |

No new network surface, no server surface, no authentication path, no user input, and
no package-manager installs. The supply-chain threat row does not apply and no
package-legitimacy checkpoint is required.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-213-09-01 | Denial of Service | `ort-runtime` as a gate-required asset | critical | mitigate | An id in the required set that no path ever marks done would leave the non-dismissible gate up forever, locking the user out of BOTH Bots and the analysis board. Mitigated structurally: the id is registered in the same synchronous call as `maia-model` (so it cannot be half-registered) and marked done at the one place every path passes through, `InferenceSession.create()` success, including the degraded path where our fetch failed. Both halves carry a dedicated test, and the ready half is proven load-bearing by a recorded revert. |
| T-213-09-02 | Denial of Service | our runtime fetch failing on a flaky link | high | mitigate | A failed runtime fetch must not fail the session. `ensureOrtRuntime()` resolves a null buffer rather than rejecting, the worker is still spawned, `wasmBinary` is left unset and onnxruntime-web resolves the binary from `wasmPaths` exactly as today. Covered by the null-buffer degrade case in both describes. |
| T-213-09-03 | Denial of Service | spawn seam becoming async | high | mitigate | Making `spawn()` await a fetch opens the window plan 08 hit with `grade()`: `dispatchNext()` guards on `worker && isReady`, both false across the await, so a request arriving mid-fetch could be dropped or could start a second spawn. Mitigated by an explicit in-flight flag guarding re-entry and by draining the queue from the existing ready handler, with dedicated tests for concurrent `ensureSpawned()` and for an `analyze()` issued mid-fetch. |
| T-213-09-04 | Tampering | wrong bundle-to-binary pairing | high | mitigate | Handing the wrong build's bytes to a bundle produces a hard session failure. Mitigated by the Task 1 gate: an empirical grep of each vendored bundle for the filename it requests, before any code is written — the same technique that caught an incorrect pairing in earlier research, per the vendored README. |
| T-213-09-05 | Denial of Service | `wasmBinary` unsupported on the asyncify build | high | mitigate | The whole design assumes `wasmBinary` suppresses the runtime fetch. If the asyncify/WebGPU build ignores it, handing bytes would leave the fetch in place and the accounting would double-count. Mitigated by making that a blocking headless verification at the head of Task 1, with an explicit HALT-and-report instruction rather than a workaround invented mid-task. |
| T-213-09-06 | Denial of Service | peak memory at `InferenceSession.create()` | medium | accept | The runtime buffer and the model buffer are both live at create time, raising peak worker memory by 13.5 MB on the wasm path and 24.3 MB on the WebGPU path against an ORT heap already around 226 MB. Bounded by transferring rather than copying the buffer (the main thread retains nothing), by clearing `wasmBinary` immediately after create, and in the common case by Task 1 keeping the larger asyncify build off devices that cannot use it. The relevant history is the FLAWCHESS-92 mobile-Safari OOM cluster; mobile takes the smaller of the two. |
| T-213-09-07 | Spoofing | adapter feature-set inspection | low | mitigate | A malformed or hostile adapter object could throw or lie. A false "absent" costs GPU inference on that device; a false "present" would cost 24.3 MB, so the safe direction is the one taken — and unlike the in-worker design, a false "present" here still costs only the wrong backend, never a second download. |
| T-213-09-08 | Repudiation | closing acceptance evidence | medium | mitigate | "The bar looks smooth" is unfalsifiable and was explicitly ruled out as the acceptance criterion.
