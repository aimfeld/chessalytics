<objective>
Stop a 45.7 MB download from re-rendering the analysis board a few thousand times.

This is `G-213-35`'s third and final part. Plans 213-08 and 213-09 closed the other
two (one Stockfish fetch; one counted ORT runtime), and the UAT gap entry for
`G-213-35` listed this one alongside them from the start:

> `frontend/src/pages/Analysis.tsx` — "useEngineAssets() is called at line 1115 inside
> the 3,600-line Analysis() component, so every per-chunk store commit re-renders the
> whole analysis tree"
>
> `frontend/src/lib/engine/engineAssetProgress.ts` — "Also commits per chunk with no
> coalescing."

Plan 213-09 mischaracterised this as cosmetic jank and deferred it to a seed. That was
wrong: it is listed as required work in the diagnosis, and the user's cold-cache run in
Brave demonstrated why. With every byte already transferred (DevTools showed the full
66,537 kB in), the modal sat at `Maia model — 75% (50.2 / 66.5 MB)` and crawled for
minutes. The engine was ready; the UI could not catch up.

**The mechanism.** `fetchModelBuffer()` calls `onProgress(loaded, total)` once per
stream chunk with no threshold. Each call reaches `reportEngineAssetProgress()`, which
calls `commit()`, which notifies every listener. `Analysis.tsx:1115` is one of those
listeners — and it subscribes the ENTIRE 3,600-line page component, while using the
result at exactly one place, line 3893, for a single boolean:

```
const engineAssets = useEngineAssets(requiredEngineAssets());   // 1115
engineGateOpen && engineAssets.status !== 'unsupported' ? (     // 3893 — sole use
```

So a ~45.7 MB model at typical chunk sizes re-renders the board, the charts, the engine
lines and every panel on the order of a thousand-plus times. The main thread falls
minutes behind a message queue it cannot drain.

This also explains why bot play is unaffected: `Bots.tsx` never calls
`useEngineAssets` at all. It mounts `<EngineReadyGate>`, which subscribes internally,
so only a small modal re-renders. Analysis is pathological; Bots is merely wasteful.

**Two fixes, both wanted.** (1) narrows the Analysis subscription so a progress tick
cannot reach the page at all; (2) coalesces notifications at the store so every
consumer — the gate included, on any surface and any device — is capped at a sane
update rate. (1) alone would fix the reported symptom; (2) is what stops it reappearing
somewhere else.
</objective>

  <behavior>
    - Store STATE is always updated synchronously. `getEngineAssetsSnapshot()` called
      immediately after any mutator reflects that mutator's effect, with no flush, no
      timer and no await. Only the listener NOTIFICATION is gated.
    - A `reportEngineAssetProgress` call that does not change the reporting asset's
      ROUNDED per-asset percent updates the snapshot but notifies no listener.
    - A call that does change it notifies synchronously.
    - The final byte always notifies: reaching 100% of an asset's total changes the
      rounded percent, and `markEngineAssetReady` notifies unconditionally regardless.
    - Every non-progress mutator notifies unconditionally and synchronously:
      `markEngineAssetPending` (CR-02), `markEngineAssetReady`,
      `markEngineAssetFailed`, `markEngineAssetsUnsupported`,
      `markEngineAssetsRetrying`, `resetEngineAssetForRefetch`.
    - A status transition caused by a progress call (`idle -> downloading`) notifies
      even when the rounded percent did not change.
    - `resetEngineAssetForRefetch` resets the remembered percent for that id, so the
      first progress report of the new pass is not swallowed as "unchanged".
    - Monotonicity and the malformed-`total` coercion (T-213-01) are unchanged.
    - The notification count for a full 45.7 MB single-asset download is bounded by
      ~101 (0..100 inclusive), not by the chunk count.
  </behavior>
  <action>
Introduce a module-scope record of the last-notified rounded percent per asset id.
`reportEngineAssetProgress` computes the new rounded per-asset percent after its
existing clamp/monotonic logic, always assigns `currentAssets` and `cachedSnapshot`,
and then notifies only when either the rounded percent changed for that id or
`currentStatus` changed as part of this call.

Split the existing `commit()` into two pieces rather than adding a flag no caller can
read at a glance: one that refreshes `cachedSnapshot` from current state (always
called), and one that notifies listeners (called unconditionally by the terminal
mutators, conditionally by the progress path). Keep the names obvious — a future reader
must not have to infer which one notifies.

Add a comment at the change site recording what broke and why (CLAUDE.md
comment-bug-fixes rule): a per-chunk notify re-rendered the whole Analysis tree
thousands of times during the 45.7 MB model download, leaving the bar minutes behind a
transfer that had already finished.

**Rejected alternative, record it in the summary:** rAF batching. It defers the
notification to a frame callback, which drags `requestAnimationFrame` into a store with
a large synchronous test suite and makes every assertion timing-dependent. The
percent-change gate achieves the same bound (~101 notifications per asset) while
staying fully synchronous and deterministic. Do NOT introduce rAF or timers here.

Clear the remembered percent for an id inside `resetEngineAssetForRefetch`, and clear
the whole record in `resetEngineAssetsForTests`.

Extend `engineAssetProgress.test.ts`:
- a listener spy receives ONE notification across many sub-one-percent progress calls,
  and the snapshot still reports the exact latest byte count throughout;
- crossing a percent boundary notifies;
- `markEngineAssetPending` notifies even when nothing else changed (CR-02);
- ready/failed/unsupported/retrying/refetch each notify unconditionally;
- a refetch's first progress report notifies rather than being swallowed;
- the 0-to-100 sweep of one asset produces at most 101 notifications.

Prove the gate is load-bearing: revert the percent-change condition to notify
unconditionally, confirm the bounded-notification test fails, restore it, and record
the revert in the summary.

<threat_model>
## Trust Boundaries

No boundary changes. This plan alters only in-process notification frequency and which
React component subtree subscribes to an existing in-process store. No network surface,
no server surface, no authentication path, no user input, no new dependency, and no
change to which bytes are fetched or from where.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-213-10-01 | Denial of Service | coalesced notification swallowing the final update | critical | mitigate | If the last progress report or a readiness transition were ever suppressed, the non-dismissible gate would never reach 100% and would lock the user out of both surfaces — a worse version of the bug being fixed. Mitigated structurally: only `reportEngineAssetProgress` is ever gated, every terminal mutator notifies unconditionally, and reaching an asset's total necessarily changes its rounded percent. Carries dedicated tests for the final-byte notification and for each terminal mutator. |
| T-213-10-02 | Tampering | deferring store STATE rather than just the notification | high | mitigate | Batching the snapshot itself would break `useSyncExternalStore`'s tearing guarantee and could return stale bytes to a render triggered by an unrelated cause. Mitigated by contract: `cachedSnapshot` is refreshed on every mutation and only the listener loop is conditional, with a test asserting the snapshot is exact after a notification-suppressed call. |
| T-213-10-03 | Denial of Service | CR-02 regression via a gated `markEngineAssetPending` | high | mitigate | If pending registration were coalesced, an asset could be invisible to a concurrent readiness check and `allDone` could fire early, enabling Start before every byte landed. Mitigated by leaving `markEngineAssetPending` on the unconditional path, with the existing CR-02 test extended to assert it notifies. |
| T-213-10-04 | Tampering | losing the Analysis/Bots `unsupported` asymmetry | medium | mitigate | Analysis deliberately hides the gate when unsupported (the board works without Maia); Bots shows the dead-end. A careless narrowing could converge them and either strand analysis users behind a dead gate or hide the dead-end from bot users. Mitigated by a `read_first` instruction naming the asymmetry and an `Analysis.test.tsx` case pinning the hide behaviour. |
| T-213-10-05 | Repudiation | acceptance evidence for a timing fix | medium | mitigate | "It feels faster" is unfalsifiable, and the previous checkpoint was passed to the user with a symptom this severity already latent. The resume-signal therefore requires a specific number — how long after the transfer stopped the bar reached 100% — rather than an impression. |
