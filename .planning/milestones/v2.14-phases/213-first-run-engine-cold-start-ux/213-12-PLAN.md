<objective>
Close `G-213-37` — the last open blocker in this phase — by giving all three engine
assets one byte-ownership layer instead of three per-path patches.

**The gap.** Starting a bot game after the engine is already warm re-downloads the
45.7 MB Maia model. Triage is complete and is recorded in `213-UAT.md`; the short
version is that this is NOT a spawn-per-move defect. `useBotGame`'s bring-up effect has
`[]` deps, so the pool and queue live for the whole game and no worker is torn down
between moves. But a per-GAME respawn is guaranteed BY DESIGN: `BotsGame` mounts with
`key={boot.nonce}` and unmounts on every new game or rematch, the effect cleanup calls
`queue.terminate()`, the last lease releases, and `maiaWorkerHost` deliberately runs
`worker.terminate()` + `resetModuleState()` to give back the ~226 MB heap (the
FLAWCHESS-92 mobile-OOM policy). The next mount warms a fresh worker whose ONLY source
for the model is `fetch(MODEL_PATH)` inside `maia-worker.js`. With "Disable cache"
ticked that is a full 45.7 MB per game start. StrictMode doubles the reading in dev.

**Why the obvious fix is the wrong fix.** The phase promised "download once, zero
refetches across surfaces" while the lifecycle deliberately frees everything at zero
leases. The only thing reconciling those two facts was the HTTP cache, which is exactly
what UAT's "Disable cache" removes. Three in-memory patches have already been applied,
one per path — 213-08's shared Stockfish fetch, G-213-8's `modelBuffer` respawn handoff,
213-11's ORT retain-and-copy — and each covered one route while leaving the largest
asset, fetched only inside the worker, with no cache at all. A fourth patch (retain the
45.7 MB model on the main thread) would be the worst of them: it re-imports the
FLAWCHESS-92 memory problem the teardown exists to avoid.

**The locked fix — D-20.** CacheStorage becomes the single byte-ownership layer for all
three assets. It is disk-backed, so nothing is retained in main-thread RAM and the OOM
policy stands. It is available inside `DedicatedWorkerGlobalScope`, so the worker can
read the model directly — no main-thread buffer hop. And it is NOT bypassed by DevTools
"Disable cache", so the zero-refetch criterion this phase is verified against becomes
honestly measurable for the first time.

Two pleasant consequences fall out and are taken in this plan: the retained ORT master
that 213-11 added for `G-213-36`, and the `modelBuffer` respawn handoff from `G-213-8`,
both become removable. Every spawn reads from CacheStorage and gets a fresh,
never-shared ArrayBuffer, which is what makes a `DataCloneError` recurrence structurally
impossible rather than merely avoided. The invariants those two fixes established do NOT
relax — the second spawn must still work, must still cost zero network, and its init
message must still LAND — only the mechanism moves.

**What this plan must not do.** It must not make the gate predicate async or key it on
CacheStorage (D-04's localStorage seen-flags stay). It must not weaken the
terminate-at-zero-leases teardown to keep bytes alive — reconciling that teardown with
zero refetches is the entire point. It must not touch D-18's gate asymmetry or 213-10's
coalescing. And it must not claim the gap is closed on a device whose Cache API quota
cannot hold 66.5 MB; iOS is an honest, documented degrade, not a silent one.
</objective>

  <action>
Create `frontend/src/lib/engine/engineAssetCache.ts` as the single byte-ownership layer
for engine assets (D-20). It owns three things and nothing else: the cache name, the
cache-first read, and the write.

Name and version. Define a private `ENGINE_ASSET_CACHE_VERSION` and export
`ENGINE_ASSET_CACHE_NAME_PREFIX` (the literal `flawchess-engine-assets-`) and the derived
`ENGINE_ASSET_CACHE_NAME`. Both the version and the prefix are named constants, never
inlined at a call site (CLAUDE.md no-magic-numbers, which covers a magic string from a
fixed set). Assets under `public/` are not content-hashed, so this constant IS the
invalidation path: bumping it changes the cache name, and the next open deletes the old
one. Say that in the module doc comment and add a short section to
`frontend/public/maia/README.md`, next to its existing "Cache headers" / "PWA precache"
sections, recording that replacing any of the three engine asset files requires bumping
this constant in the same commit.

Cache open + sweep. A single internal `openEngineAssetCache()` memoised for the page
session: feature-detect `caches` (missing in Safari private mode and on insecure
contexts) and resolve `null` when absent; otherwise `caches.open(ENGINE_ASSET_CACHE_NAME)`
and, once, enumerate `caches.keys()` and delete every key that starts with the
engine-asset prefix and is not the current name. Filter on the prefix, never on anything
broader — the Workbox caches that serve the offline app shell live in the same
CacheStorage and deleting one would take the PWA's offline shell with it.

Public read. Export
`getEngineAsset(id: EngineAssetId, url: string, onProgress: (loaded: number, total: number) => void, fallbackBytes: number): Promise<ArrayBuffer>`.
Order of operations: try `cache.match(url)` first; on a hit whose body has non-zero
length, call `onProgress(byteLength, byteLength)` once and resolve those bytes. On a miss
(or a zero-length entry, which is treated as a miss), join or start a single-flight entry
keyed by asset id; the populating path runs the streaming fetch — the same shape
`fetchRuntimeBinary` already uses, including the
`Number(response.headers.get('content-length')) || fallbackBytes` coercion so a missing
or garbage header can never produce a NaN percent — then `await cache.put(url, new Response(bytes))`
inside a try/catch before resolving. Await the put rather than firing it off: a
deterministic "the cache is populated before the caller proceeds" is what makes the
second spawn measurably free, and it is a local disk write.

Two invariants on that single-flight entry, both load-bearing and both easy to get wrong:

1. **No two callers ever receive the same ArrayBuffer instance.** A caller may push what
   it receives into a `postMessage` transfer list, which detaches it — that is exactly
   how `G-213-36` happened. The populating caller may take the streamed bytes directly;
   every joiner must get an independent copy (a `slice(0)` of the result, or its own
   fresh cache read now that the put has landed — either is acceptable, the invariant is
   what matters).
2. **The entry is DELETED once it settles.** A promise memoised for the page session
   would retain the bytes in module scope, which is precisely the RAM cost D-20 removes
   and precisely the shared-instance hazard 213-11 had to paper over. After settling, the
   next call must go back through `cache.match`.

Failures. Do not swallow a fetch failure — throw, exactly as `fetchRuntimeBinary` does;
both callers already catch and degrade, and swallowing here would hide a terminal
download failure the gate needs in order to offer Retry. Never write a non-ok or partial
response to the cache. Catch `cache.put` failures, report once through Sentry with a
`tags: { source: ... }` shape and no variable data in the message (CLAUDE.md Sentry
rule), resolve the bytes anyway, and set a module-level flag that skips further writes
for the page session. That flag matters on iOS: the Cache API limit there is roughly
50 MB (the same limit already recorded in `vite.config.ts`'s `globIgnores` comment) and
the three assets total 66.5 MB, so an over-quota device would otherwise write, evict,
and rewrite on every start. With the flag it simply degrades to today's HTTP-cache
behavior after the first refusal.

Wire the worker — the gap path itself. `maia-worker.js` is a standalone, un-bundled
classic script and cannot import this module, so it gets its own small read/write logic
in `fetchModelBuffer`. It must NOT duplicate the cache-name literal: add an
`assetCacheName?: string` field to `InitMessage` in `maiaWorkerHost.ts`, set it from
`ENGINE_ASSET_CACHE_NAME` on every spawn (both `spawn()` branches reach the same
`constructWorker`, so one assignment covers both), and have the worker use
`msg.assetCacheName` when it is present and `caches` is defined. Absent either, the
worker plain-fetches exactly as it does today. Update the worker's message-protocol
header block to document the new field, and keep the existing D-15 retry loop, the
content-length coercion, and the `onProgress(0, total)` bar restart between attempts
intact — a cache hit short-circuits before the retry loop rather than replacing it.

On a hit the worker reports `onProgress(length, length)` once, mirroring the existing
`prefetchedBuffer` branch in `initWasmOnlySession` which already does this for a download
that is not going to occur. On a miss it writes the complete body after the successful
attempt, in a try/catch, and returns the bytes either way.

Add a comment at each of the two fix sites (`fetchModelBuffer` and `getEngineAsset`)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| network -> CacheStorage | Same-origin asset bytes cross from the network into persistent, origin-scoped storage. No new origin and no new request is introduced; what changes is that the bytes now persist under our own key rather than only in the HTTP cache. |
| CacheStorage -> Worker | The Maia worker reads model bytes out of CacheStorage and compiles them into an ONNX session. A corrupt or truncated entry would be compiled, so entry integrity matters at this boundary. |
| main thread -> Worker (init message) | Unchanged in kind: a same-app `postMessage` carrying a cache NAME plus a runtime buffer this app fetched. The model buffer that used to cross here is removed. |
