| GitHub Actions cache -> CI runner | Restored cache contents become build inputs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-216-04 | Tampering | `astral-sh/setup-uv` as a new build-time dependency | medium | mitigate | The action is published by the same Astral org this repo already trusts for `ghcr.io/astral-sh/uv:0.10.9`, which `Dockerfile` pins by digest. | T-216-04B | Tampering | restored uv / npm cache contents | medium | mitigate | Neither cache is authoritative: `uv sync --locked` resolves against `uv.lock` and `npm ci` against `package-lock.json`, both of which carry integrity hashes, so a poisoned cache entry cannot substitute a different artifact without failing the lockfile check. GitHub scopes caches per repository and restricts cross-branch restore to the default branch. |
| T-216-04C | Denial of service | stale npm cache from a missing `cache-dependency-path` | low | mitigate | The path input is mandated and asserted, because the lockfile is not at the repo root; without it the cache silently never hits and the stated speedup would not materialize. |
