<objective>
Build the guest-purge core: the eligibility query that finds inactive guests and the per-guest
purge that deletes their games (via cascade), deletes their import_jobs cursor row(s), and resets
the Phase-186 backfill cursors — reusing the exact repository functions the existing
`DELETE /api/games` endpoint already uses in production. This plan LEADS with a tracer that proves
the entire purge mechanic end-to-end for a single eligible guest before expanding to the full
eligibility matrix and orchestration loop.

Purpose: SEED-116 — implement the already-advertised-but-never-built 30-day guest cleanup. This is
the load-bearing mechanic; Plan 02 only wraps it in a periodic loop + lifespan wiring.
Output: `app/services/guest_cleanup_service.py` (constants, `get_eligible_guest_ids`, `_purge_guest`,
`cleanup_inactive_guests`) and `tests/test_guest_cleanup_service.py`.
</objective>

## Plan-time decisions

- **Pitfall 2 (RESEARCH Open Question 1) — RESOLVED: mirror the precedent.** `_purge_guest` also
  deletes `UserBenchmarkPercentile` and `UserRatingAnchor` rows for the guest, exactly like
  `DELETE /api/games` (`imports.py:455-479`). Rationale: consistency with the existing production

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internal job → users table | The cleanup job self-selects rows; there is NO user-supplied input (no request body, no path/query params). The only authorization boundary is the `is_guest=true` WHERE clause. |
| games row delete → cascading children | The DB engine performs multi-table deletion via ON DELETE CASCADE FKs; correctness depends on all 5 child FKs being CASCADE (DB-verified in RESEARCH). |

Reverting the predicate must fail the test (acceptance criterion). |
| T-187-02 | Tampering (silent data gap) | dual cursor reset | high | mitigate | _purge_guest resets BOTH import_jobs (delete) AND user_import_settings backfill cursors (reset_backfill_cursors) — Pitfall 1; end-to-end test asserts the 3 cursor columns are NULL post-purge. |
| T-187-03 | Tampering (orphaned rows) | game-scoped child FKs | high | mitigate | RESEARCH DB-verified all 5 game-referencing FKs (game_positions, game_flaws, game_best_move, eval_jobs, bot_game_settings) are ON DELETE CASCADE; the end-to-end test asserts zero rows in every child table for the purged guest (no-orphans assertion). |
