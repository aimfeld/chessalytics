<gap_reference>
## The gap, as verified

From `189-VERIFICATION.md` (`status: gaps_found`, 3/4 success criteria verified, POOL-01 blocked):

- `pool_entry_stmt` (`app/services/train_pool.py`, WHERE clause ~line 232) filters the answer key with `GameFlaw.missed_pv_lines.isnot(None)` only.
- `app/services/eval_apply.py` writes `[]` — a non-NULL empty JSONB array — for un-fillable flaw lines (`_assemble_one_line_blob` returns `[]` for a line in `sentinel_lines` or a line missing its node-0 result; `_batch_update_flaw_pv_lines` persists it). The verifier reproduced this against the live dev DB: a seeded blunder with `missed_pv_lines=[]` returns one row from `pool_entry_stmt`.
- `blob_pending_stmt` (~line 412) is the mirror image: `.is_(None)` only, so a `[]` sentinel is counted in neither "entered" nor "pending".

## Facts established during planning (do not re-derive)

1. **`[]` is terminal, not transient.** The tier-4 blob lottery claims games by `GameFlaw.allowed_pv_lines.is_(None)` (`app/routers/eval_remote.py:843,902`), and the sentinel write exists precisely to clear that predicate "so the game is never re-picked" (same file, ~lines 793 and 816). A flaw whose blob line came back `[]` therefore never self-heals through the opportunistic lane. A true NULL blob does.
2. **Postgres does NOT protect `jsonb_array_length` with a sibling `jsonb_typeof` guard.** Verified directly against the dev database: `SELECT c FROM (VALUES ('null'::jsonb), ('[]'::jsonb), ('[{"b":1}]'::jsonb), (NULL::jsonb)) v(c) WHERE jsonb_typeof(c) = 'array' AND jsonb_array_length(c) > 0;` returns `ERROR: cannot get array length of a scalar` — the planner has no control over AND-clause evaluation order. The same query with `c IS NOT NULL AND jsonb_typeof(c) = 'array' AND c <> '[]'::jsonb` returns exactly the one real array with no error, because `jsonb_typeof` and `<>` are total for every jsonb input. This is why the plan does NOT use the `jsonb_array_length(...) > 0` form the verification report suggested.
3. **The `null::jsonb` hazard is real in this codebase** (`project_asyncpg_jsonb_null_vs_sql_null`, and the comments in `tests/routers/test_train.py:161-165` / `tests/test_migration_suppress_ungated_tactic_tags.py:121-125`): a Python `None` bound into a JSONB column can land as `null::jsonb`, not SQL NULL. The dev DB currently holds none (`jsonb_typeof` over 43k `game_flaws` rows returns only NULL and `array`), but the predicate must not be able to 500 the composition endpoint if one ever appears.
4. **Test seeders already support the new case.** `tests/services/test_train_pool.py::_seed_blunder_game` passes `missed_pv_lines` unconditionally, and `tests/routers/test_train.py::_seed_game_with_blunder` / `tests/repositories/test_train_repository.py::_seed_flaw_game` pass it whenever it `is not None` — so `missed_pv_lines=[]` writes a genuine `'[]'::jsonb`. No seeder changes are needed or wanted.
</gap_reference>

<decision id="D-GAP-01">
## Decision: an empty-list sentinel counts toward NEITHER pool entry NOR `blob_pending_count`

The verification report explicitly required this call to be made and encoded. It is made here.

**Chosen semantics:**
- `pool_entry_stmt` requires a non-empty array → a `[]` flaw is NOT a puzzle. (This is the gap fix; not optional.)
- `blob_pending_stmt` keeps counting ONLY true SQL NULL → a `[]` flaw is NOT "pending" either.

**Rationale.** `blob_pending_count` exists (per `app/schemas/train.py`'s `TrainSessionResponse` docstring and Pitfall 4 in `189-RESEARCH.md`) to let the client tell "your session is short because analysis has not caught up yet" from "your session is short because you are genuinely caught up". That is a promise about material that is still coming. Fact 1 above establishes that a `[]` flaw is never coming — the sentinel was written specifically to stop the tier-4 lottery from re-picking it. Counting it as pending would pin the client's "still analyzing" signal at a permanently non-zero floor that never resolves, which is exactly the dishonest signal that field was introduced to prevent. A terminal-unfillable flaw is not drillable material, so it belongs in the same bucket as a flaw that fails the winnability floor: excluded, uncounted, silent.

**Accepted consequence.** A user whose entire flaw set carries `[]` blobs sees `puzzle_count = 0, blob_pending_count = 0` and the client will say "caught up" rather than "analyzing". That is the honest, actionable message: nothing more is arriving. Surfacing the unfillable population would require a third response field with no consumer (Phase 190/191 UI does not exist yet) and is deliberately NOT added here.

**Encoding.** The asymmetry gets a name rather than living in an implicit missing predicate: `answer_key_pending` is documented as deliberately NOT the boolean negation of `answer_key_present`, with this rationale, so the next reader cannot mistake it for an oversight of the same class this plan is fixing.

<reversibility rating="reversible">
Two-way door. Reversing to "count `[]` as pending" is changing one predicate in `answer_key_pending` plus one assertion in `test_empty_blob_not_counted_as_blob_pending`. No stored data, no migration, no client contract change (the field already exists and its type is unchanged). No decision checkpoint required.
</reversibility>
</decision>
