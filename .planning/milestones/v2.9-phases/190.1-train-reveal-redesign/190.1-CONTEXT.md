# Phase 190.1: Train Reveal Redesign — Context

**Source**: gsd-explore session 2026-07-26 (190 UAT feedback, discussed directly with Adrian).
**Inserted after**: Phase 190 (Train Page + Solve Loop), before Phase 191.

## What this phase is

Phase 190's post-solve reveal works but under-informs: bare ✓/✗ verdicts, a single
best line, and a full game card that pulls attention away from the position. This
phase rebuilds the reveal into a self-contained study surface where the board and
the panel together answer "what was good, what did I play, what happened in the
game, and why was it bad" — with every number and line coming from ONE engine
(the client-side grading engine) so nothing can contradict the verdict.

## Decisions

Machine-readable index of the locked decisions detailed in the next section
(the gate parser needs `- **D-NN:**` bullets; the prose below is authoritative):

- **D-01:** Client engine sources ALL lines and evals (MultiPV mount search, kept after-move PV, lazy game-move search); never mixed with stored server evals
- **D-02:** Board arrows on reveal follow puzzle type (sharp = 1 green, soft/herring = good moves capped at 3) plus played-move arrow and smaller white game-move arrow
- **D-03:** Reveal panel = verdict rows stating the given answers, three steppable eval-tagged line boxes, opponent+date footer replacing the game card, Analyze+Next on one line, deep link to the puzzle position (ply − 1)
- **D-04:** Session score at the top-right of the progress bar (localStorage-backed, survives resume)
- **D-05:** Server reveal provides the game move as UCI; answer-key fields (`best_move`/`best_move_san`/`pv`) are candidates for removal (resolved at plan time: promote/slim)

## Locked decisions (from the discussion — do not re-litigate)

### D-1: Client engine sources ALL lines and evals

All three reveal lines and their evals come from the client-side Stockfish WASM
grading engine, never from stored server evals. Rationale: stored evals and
client evals are not reproducible across machines (project_eval_nondeterminism),
so mixing sources can show "YOUR MOVE +0.2 / BEST MOVE +0.3, verdict: incorrect"
contradictions. Adrian explicitly chose re-evaluating everything client-side
over accepting that rough edge.

Search plan (the cheap version — one genuinely new search per puzzle):

1. **Mount search → MultiPV.** The existing once-per-puzzle mount search in
   `useTrainGradingEngine.ts` becomes a MultiPV search on the puzzle FEN. One
   search yields: the best move, the best line (PV) + its eval, AND the
   good-moves set for the green arrows. Grading semantics must not regress
   (esBefore still read from multipv 1).
2. **After-your-move search: keep the PV.** `gradeMove`'s existing search on the
   position after the played move already produces the YOUR MOVE eval
   (esAfter); it currently discards the PV arriving in the same UCI `info`
   stream — capture it instead. No extra search.
3. **Refutation search: new, lazy.** One new search on the position after the
   game move, dispatched only when the reveal opens (needs the game move as
   UCI from the server reveal). PLAYED IN GAME box may show a short spinner
   while the other two boxes render instantly.

### D-2: Board arrows on reveal follow puzzle type

- **Green arrows = actual good moves**: moves whose expected-score drop vs. best
  is better than an inaccuracy, per the project's EXISTING live-flaw thresholds
  (`liveFlaw.ts` / `INACCURACY_DROP` family) — no new magic cutoff. Sourced from
  the MultiPV mount search.
- Count follows puzzle type: **sharp = exactly 1** green arrow (by definition
  only one move is right); **soft/herring = all good moves, capped at 3**.
- **User's played move**: shown with its own arrow (distinct from green;
  visual treatment is a UI-spec decision).
- **Game move**: smaller white arrow, same style as the analysis board's
  played-move arrow (`BoardArrow` / `arrowColor.ts` precedent carries over).

### D-3: Reveal panel content

- **Verdict rows state the answers given**, not bare marks:
  - `Guess: One critical move ✗` (the guess the user committed)
  - `Move: Nc3 ✓` (the played move in SAN — client-side UCI→SAN via chess.js)
- **Three steppable line boxes**, each with an eval, each steppable on the
  shared board via the existing `TrainLineStepper` + `onFenChange` pattern
  (multi-stepper precedent: the tactic missed/allowed pair):
  1. **YOUR MOVE** — played move + engine continuation (after-search PV)
  2. **BEST MOVE** — best move + best line (MultiPV rank 1)
  3. **PLAYED IN GAME** — game move + engine **refutation line** (Adrian chose
     refutation over the actual game continuation)
- **Game card removed.** Replaced by a small footer: opponent + game date
  (data already available from the game fetch; no full `GameCard`).
- **Analyze + Next on one line.** The reference mockup (chat, 2026-07-26) was
  illustrative for the line boxes ONLY — its share/trash icons are out of
  scope, its exact styling is not binding.
- **Analyze deep link → the puzzle position**, i.e. one ply BEFORE the mistake
  was made (currently `GameCard analyzePly={puzzle.ply}` lands one ply late).

### D-4: Session score on the progress bar

Current session score at the top-right of the progress bar (e.g. `5 / 8 pts`,
max = solved-so-far × 2). `trainSession.sessionScore` is already
client-accumulated and localStorage-backed (190-04 D-03), so it survives a
resume — pure wiring, no new state.

### D-5: Server reveal slims down (or at minimum extends)

The server reveal must additionally provide the **game move as UCI** (it has
SAN only today) so the client can run the refutation search. With all
lines/evals client-sourced, `best_move`/`best_move_san`/`pv` in the reveal
response become candidates for removal — plan-time decision whether to slim
now or keep as fallback. The reveal keeps: game move, `puzzle_type`,
`has_tactic_lines`, game_id/ply/fen. POOL-10 (no answer key pre-attempt) is
untouched — the reveal endpoint's 409 gate stays as is.

## Explicitly dropped / deferred (do NOT scope in)

- **Back-nav from analysis board restoring the reveal**: dropped for now by

- **Share / trash icons** from the mockup: out of scope (trash would imply a

- **Whole game card in the reveal**: intentionally removed, don't keep it
  behind a toggle.

## Plan-time decisions (open, resolve during planning)

1. **Line-coincidence dedupe**: played move == best move (YOUR MOVE and BEST
   MOVE boxes would duplicate — collapse to one box? label "YOUR MOVE = BEST"?);
   game move == best move (the original game move was fine — herring-adjacent);
   herring positions where "refutation" framing is wrong (there may be nothing
   to refute — several moves fine).
2. **MultiPV width**: enough to find "up to 3 good moves" reliably (likely
   MultiPV 4-5); measure the movetime cost vs. the existing grading budget
   (190-01 measured the single-PV budget; MultiPV splits nodes across lines).
3. **Server reveal slimming** (see D-5): remove vs. keep-as-fallback.
4. **Eval display convention**: white-POV numbers as on the analysis board
   (the engine hook already sign-normalizes to white POV).
5. **Engine-failure fallback in the reveal**: if a reveal-time search fails or
   times out, the boxes need an honest error/absent state (CLAUDE.md isError
   rule) — never a hang, never silently swapping in stored server evals
   (would reintroduce the D-1 inconsistency).
