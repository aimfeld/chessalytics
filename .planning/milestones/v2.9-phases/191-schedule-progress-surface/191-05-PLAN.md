<objective>
Replace the Phase-190 boolean first-visit Train dot with the numeric waiting-puzzles badge that is this feature's entire attention mechanism (SCHD-02, D-06/D-07/D-08) — desktop header and mobile bottom bar, no dashboard card, no push, no email.

Purpose: the badge is the only thing that pulls a user back into the habit loop. It has to be honest (absent when unknown, absent when nothing is waiting) and it has to be cheap (one shared query, no polling, no request at all for accounts that cannot train).

Output: an `enabled`-gated `useTrainProgress`, the badge at both nav call sites, and the dot chain fully removed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nav chrome → `GET /train/progress` | The badge issues an authenticated request from every page of the app, for every logged-in account including guests. |
| query failure → Sentry | The global `QueryCache.onError` forwards every failed query to Sentry, so an expected failure becomes reported noise. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-191-19 | Information Disclosure | badge count in nav chrome | high | mitigate | The count comes from `GET /train/progress`, which scopes every query to `current_active_user.id` (T-191-01/T-191-06) — the client never supplies a user id and the badge renders only what that endpoint returned for the authenticated session. |
| T-191-20 | Denial of Service | per-page-view progress request | medium | mitigate | One shared `TRAIN_PROGRESS_QUERY_KEY` deduped across the badge and the stats row, the global `staleTime: 30_000`, and no `refetchInterval` — the badge refreshes on focus and navigation rather than polling. |
| T-191-21 | Denial of Service | Sentry noise from expected 403s | medium | mitigate | The query is `enabled`-gated on `navUnlocked && profile != null && !profile.is_guest`, so accounts that would provoke a guaranteed 403 never issue the request and never file a Sentry issue. Proven by the two `enabled: false` tests. |
| T-191-22 | Elevation of Privilege | guest reading Train state | high | mitigate | Defence in depth: the client gate above, plus the server's `_reject_guest(user)` 403 on the endpoint itself. The client gate is an optimisation; the server gate is the control. |
| T-191-23 | Repudiation | silently absent badge on error | low | accept | UI-SPEC E5 deliberately chooses a silent absence over an error affordance in nav chrome; the failure surfaces on the Train page's own stats row (E1 error), where the user can act on it. |
| T-191-SC | Tampering | npm installs | low | accept | Zero new dependencies. No install task exists, so no legitimacy audit is required. |
</threat_model>
