  <name>Task 1: Decide the migration strategy for the `drill_solves.game_id` one-way door</name>

  <decision>
How to land `drill_solves.game_id` `NOT NULL` + `ON DELETE CASCADE` -> nullable +

  </decision>

  <context>
This is the phase's one-way door. The ROADMAP flags it explicitly as a plan-time decision to
resolve rather than default, and CONTEXT.md D-05 rates it one-way: it is a nullability change on
a table holding recorded solve outcomes, and reversing it later means either re-imposing
`NOT NULL` on rows that may by then legitimately hold NULL, or dropping those rows.

**What is NOT being decided here.** D-05 itself is locked: the column becomes nullable with
`SET NULL`. The reason is settled and not up for revisit — with a global pool, a *foreign* user
deleting their games would otherwise vaporize a row out of a stranger's in-flight session, and
`drill_solves` rows ARE the session's frozen puzzle list (PK `(session_id, position)`), so the
deletion punches a hole in the position sequence and shifts the session-score denominator.
POOL-09 promises "no orphaned drill rows, no crashes"; only a global pool can produce this
failure mode.

**What IS being decided:** the migration strategy and the blast-radius acknowledgement.

Facts the decision rests on, all verified against the current tree:

1. **No data migration is needed.** Every existing `drill_solves` row has a non-NULL `game_id`
   today, and nothing retroactively introduces NULLs — only *new* pool-sourced herring rows, and
   only after a source game is deleted.
2. **Exactly three INNER JOIN sites** key on `DrillSolve.game_id`:
   `load_session_puzzles` (`app/repositories/train_repository.py:792`),
   `_mark_session_complete_if_done` (`:1419`), and `reveal_for_puzzle` (`:1675`).
   The fourth `join(Game, ...)` at `:1021` is on `DrillItem.game_id`, an unrelated table that
   keeps `NOT NULL` + `CASCADE`.
3. **RESEARCH.md's assumption A2 is wrong and must not be followed.** A2 predicted that the
   `Game` outer join needs no parallel `or_` guard. It does. Today a deleted game CASCADEs the
   `drill_solves` row away, which is what makes the WR-02 "stuck session" fix work. After
   `SET NULL`, an orphaned **SR** row survives forever with `solved_at IS NULL` and would count
   as remaining, reintroducing the exact stuck-session bug WR-02 fixed. SR and herring rows need
   opposite treatment: SR orphans are excluded, herring orphans still count.
4. `record_solve`'s two `_advance_drill_item` / `_read_drill_item_state` calls pass
   `solve_row.game_id` into `game_id: int` parameters. They are already `is_sr`-guarded, but the
   guard is on `source`, not on the value, so `ty` will flag them after the widening and they
   need explicit `is not None` narrowing.

**Recommended option: A.** It is the smallest change that matches the facts, and options B and C
each buy their safety by adding a second source of truth for the same fact.
  </context>

  <options>
    <option id="option-a">
      <name>A — In-place ALTER, both halves in one migration, after the code fixes land</name>
      <pros>One migration, no data backfill, no dual-write window. `ALTER COLUMN ... DROP NOT NULL` is instant; `DROP CONSTRAINT` + `ADD CONSTRAINT ... ON DELETE SET NULL` re-validates the FK, which on `drill_solves` (a small, session-scoped table) is cheap. Task 2 lands all three join fixes first, so at no point does the schema permit a NULL the code cannot handle. Matches D-05 exactly.</pros>
      <cons>Genuinely one-way: reverting means restoring `NOT NULL`, which fails if any NULL rows exist by then. `ADD CONSTRAINT` takes a brief `ACCESS EXCLUSIVE` lock on `drill_solves` (acceptable — the table is tiny and Train is not a hot path).</cons>
    </option>
    <option id="option-b">
      <name>B — Split into two migrations: drop `NOT NULL` now, change the FK policy in a later phase</name>
      <pros>Halves the irreversible surface per deploy; the nullability half alone is enough for the code paths to be exercised.</pros>
      <cons>Does not actually deliver the phase goal. With `CASCADE` still in place, a source-game deletion still DELETES the `drill_solves` row, so ROADMAP SC3 ("a foreign user's deletion never removes a row from another user's in-flight session") stays unmet. Ships a half-migration that looks done and is not.</cons>
    </option>
    <option id="option-c">
      <name>C — Leave `game_id` alone; add a separate nullable `source_game_id` column for herrings only</name>
      <pros>Zero change to an existing live column; fully reversible by dropping the new column.</pros>
      <cons>Two columns meaning "which game this puzzle came from" is exactly the add-alongside anti-pattern this phase's Assumption Delta rejects. Every read site would have to coalesce them, `uq_drill_solves_session_puzzle` would stop protecting herrings, and a herring's row would still CASCADE away on `game_id` — so SC3 remains unmet. Strictly worse than A while looking safer.</cons>
    </option>
  </options>
