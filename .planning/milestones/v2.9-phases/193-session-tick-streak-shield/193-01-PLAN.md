<objective>
Replace Phase 191's weekly settlement machine with the per-scheduled-day tick + depletable
shield, end to end: a new `shield_level` column and eligibility watermark, one shared
`_judge_one_day` primitive, a `tick_days` walk with the correct elapsed-day boundary, the
rewritten `GET /train/progress` payload, and the 7-segment pip meter that renders it.

This plan LEADS with the tracer: one real scheduled day is judged all the way from the column
through the pure tick machine, the repository settlement, the wire payload, and the rendered
meter — proving the architecture before Plan 02 expands it with the eager completion path and
the nav-badge signal.

Decisions locked here: **D-01** (7-segment pip meter), **D-02** ("N-session streak" label),
**D-04** (empty meter + 0 count + persistent state-derived notice), **D-05** (a no-material
scheduled day is neutral), **D-06** (one nullable eligibility watermark on `train_settings`).
**D-03**'s eager tick and **D-07**/**D-08**/**D-09**/**D-10** land in Plan 02 and Plan 03.

Purpose: kill the weekly-fulfillment check, `required_sessions_per_week` and its 1→6 cliff, and
the 3-rung flame ladder in one atomic rewrite — a partially-migrated state does not compile.
Output: a green backend + frontend suite on the new model, with existing completed sessions
retroactively replayed under the new rules.

Size note (reviewed, deliberately retained): this plan carries four tasks across ~14 files, above
the usual 2–3 task budget. Splitting the backend rewrite from the pip meter was considered and
rejected — the flame→shield swap is one atomic rename across the column, the wire schema and the
component, so every candidate split point produces a wave that neither compiles nor type-checks.
The tracer contract is precisely that one slice proves the architecture end to end. Do not
re-litigate this.
</objective>

1. **Carry-over of Phase 191's three streak columns — hard-reset + replay, WITH a real
   watermark backfill.** The migration sets `streak_count = 0, streak_settled_through = NULL`
   and, in the SAME revision, backfills `pool_eligible_since` from
   `MIN((drill_items.created_at AT TIME ZONE train_settings.timezone)::date)` per user. A NULL
   `streak_settled_through` is exactly the state that already triggers full-history replay, so
   existing completed `drill_sessions` retroactively rebuild the new count/shield under the new
   rules — honouring Phase 191 **D-05** (retroactivity as an explicit user requirement) without
   inventing a week-count→session-count translation that has no valid formula. The backfill is
   load-bearing, not cosmetic: a lazily-stamped "today" watermark would collapse the replay
   window to empty and silently discard that history (RESEARCH.md Pitfall 3). Gated by the
   Task 1 `checkpoint:decision`.
2. **The D-06 watermark trigger — the existing `has_drill_items OR has_pool_candidates` EXISTS
   pair.** Reuses the two queries `_pool_state` already runs on every progress read; refactored
   into `_material_flags` so they run exactly once per request. `blob_pending_count > 0` alone is
   deliberately excluded: a blunder still awaiting tier-4 analysis has no answer key, so it is
   not yet drillable material under D-06's own wording. (`game_flaws` has no `created_at`, so
   "first qualifying flaw timestamp" was never available.)
3. **`streak_settled_through` keeps its name and its `Date` type.** Its meaning shifts from
   "Monday of the last settled week" to "the last judged day", which is a docstring change, not a
   schema change. A rename would be free in Postgres but buys nothing: every call site is being
   rewritten anyway, and keeping the name keeps the migration to one column drop and two adds.
4. **The "This week: N of M sessions" line stays, with zero frontend change** (UI-SPEC.md
   `## "This Week" Line — Decision`, LOCKED). Backend-only: `current_week_required` becomes

   the identical oklch literals the flame constants used. Empty pips use
   `border-muted-foreground/50`, never a fourth named colour.
6. **Drain stays symmetric ±1 and `SHIELD_CAP` stays 7.** Not a tuning exercise; CONTEXT.md

    streak_reset_notice: bool, changed: bool)` — deliberately WITHOUT any display overlay field
    (RESEARCH.md Pitfall 5: the Phase 191 `display_flame` overlay is deleted, not ported, because

    `DayOutcome = Literal["fulfilled", "missed", "neutral", "credit_only"]`;
    `_judge_one_day(snapshot, *, day, outcome: DayOutcome) -> TickSnapshot` as the ONLY place
    shield/count arithmetic happens; and `tick_days(snapshot, completed_session_dates, *,
    weekday_mask, today, pool_eligible_since) -> TickView`.

    `_judge_one_day` takes a four-value discriminant rather than a `(fulfilled, eligible)` boolean
    pair for two reasons: the pair encodes one impossible combination
    (`fulfilled=True, eligible=False`), and Plan 02's eager path needs a fourth transition that
    the pair cannot express at all — credit the shield WITHOUT the count and WITHOUT moving the
    boundary. Structure the branches so the shield-credit expression is written ONCE and shared:
    compute the credited snapshot a single time, return it directly for `credit_only`, or return
    it with `streak_count + 1` and `settled_through=day` for `fulfilled`. That single expression
    must be the only place in the entire `app/` tree where the cap constant bounds an incremented
    shield, because Plan 02 calls this function instead of re-deriving it (a Plan 01 acceptance
    criterion greps for exactly one occurrence, and Plan 02 re-greps it).

    Semantics per outcome: `neutral` advances `settled_through` only; `fulfilled` advances count,
    shield and `settled_through`; `missed` drops shield by 1 floored at 0, zeroes the count when
    the shield reaches 0, and advances `settled_through`; `credit_only` advances the shield ONLY
    and deliberately leaves both `streak_count` and `settled_through` untouched, because the day
    it describes is either unscheduled (D-07) or already frozen (Pitfall 2) and the boundary must
    not move for either. `day` is accepted for all four outcomes and is ignored by `credit_only` —
    say so in the docstring, alongside the note that this function is the single arithmetic
    primitive both settlement paths share.

    `tick_days` starts at `next_scheduled_day(snapshot.settled_through + 1 day, weekday_mask)`
    when `settled_through` is set, else at `next_scheduled_day(pool_eligible_since or today,
    weekday_mask)`. Its loop condition is
    `is_session_expired(session_window(day, weekday_mask), today)` — NEVER `day < today`. Per day
    it computes `eligible = pool_eligible_since is not None and day >= pool_eligible_since` and
    resolves one outcome — `"neutral"` when not eligible, else `"fulfilled"` when
    `day in completed_set`, else `"missed"` — delegates to `_judge_one_day`, then advances via
