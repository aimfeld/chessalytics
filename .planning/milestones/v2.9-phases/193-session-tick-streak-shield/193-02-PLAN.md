<objective>
Expand the proven tick machine with the D-03 eager completion path and the SCHD-02 badge signal.

Two behaviours land here: (1) a completed session writes its tick immediately, correctly composed
with the lazy miss walk so neither path can double-count or skip a day; (2) `GET /train/progress`
gains a server-computed `badge_visible` boolean encoding D-09 (scheduled days only) and D-10 (an
open unfinished session keeps its badge on an off-day). The compose-side D-06 watermark stamp is
folded in because it is the second place a `drill_items` row can first appear.

Decisions locked here: **D-03** (eager completion tick), **D-07** (off-day session credits a pip
but not the count), **D-08** (started-and-abandoned is a miss), **D-09**/**D-10** (badge
visibility, backend half — Plan 03 consumes it).

Purpose: this is the phase's highest-risk correctness surface. `record_solve` has no expiry check
today, so a stale open session can still be completed after an intervening progress read already
judged its day a miss. Output: an eager path that is provably incapable of double-crediting, with
a dev-clock integration test proving it.

**Late-completion tie-break — recorded decision, not a gate.** RESEARCH.md assumption A3 asked for
a `checkpoint:decision` on what a late completion of an already-frozen day should do. It is
resolved here as "credit one shield pip, never the count, never re-open the day", which is
RESEARCH.md's own recommendation and the forgiving reading CONTEXT.md's values position implies.
It is rated `reversible` (one `DayOutcome` discriminant behind a unit test), so it is recorded as
a plan decision rather than a blocking gate — the phase spends its one blocking decision gate on the
carry-over migration in Plan 01, which is the choice with a migration and a user-visible outcome
behind it. Consequence, stated plainly so it is not discovered later: on the day a session's window
closes, the lazy miss (−1) and the late-completion pip (+1) net to zero shield change and no count
tick. That is the intended "you did the work late; you don't advance, but you don't lose ground"
outcome, and it is not farmable — `_mark_session_complete_if_done` flips a session open→completed
exactly once, and `solved_at IS NULL` claims each puzzle exactly once.
</objective>

    `app/repositories/train_repository.py`, and call it from `record_solve` immediately after
    `_mark_session_complete_if_done` returns True — inside the existing transaction, with no new

    `_apply_completion_tick` performs, in this exact order:
    1. `SELECT drill_sessions.session_date WHERE id = :session_id AND user_id = :user_id` (scoped
       by `user_id` — ASVS V4). If no row, return.
    2. `get_or_create_settings` for the user, then `today = local_today(settings_row.timezone,
       now_utc)`.
    3. `await settle_streak_snapshot(session, user_id=..., settings_row=..., today=today)` — the
       lazy walk runs FIRST so every scheduled day whose window has already closed is judged
       before the completion is applied. This is the fix for the skip case: without it, a
       completion on a later day would move `streak_settled_through` past unjudged misses. Note
       that today's own scheduled day can never be judged by this walk, because
       `session_window(today, mask)` is strictly after `today` and `is_session_expired` is
       therefore False for it — so there is no conflict between the two paths on the current day.
    4. Re-read the settings row (or use the `TickView` the settle call returned) so the tick is
       applied to the POST-settle snapshot, never a stale pre-settle one.
    5. Build a `TickSnapshot` from the post-settle row, choose exactly ONE `DayOutcome`, and call
       `_judge_one_day(snapshot, day=session_date, outcome=chosen)` exactly once. The outcome is
       `"fulfilled"` when `is_scheduled_day(session_date, settings_row.weekday_mask)` AND
       (`streak_settled_through` is None OR `session_date > streak_settled_through`); otherwise —
       an off-day session (D-07) or a late completion of an already-frozen day (Pitfall 2) — it is
       `"credit_only"`. Persist the returned snapshot's `streak_count`, `shield_level` and
       `settled_through`. Note what falls out of routing both branches through the primitive:
       `"credit_only"` returns `streak_count` and `settled_through` unchanged by construction, so
       the two branches differ ONLY in which discriminant is passed, and this function derives no
       shield or count value itself. Do not hand-write the cap arithmetic in either branch — it
       lives in `_judge_one_day`, and both plans gate on it being typed exactly once in `app/`.
    6. Both writes use an UPDATE scoped by `user_id`; the fulfilled branch keeps the same
       compare-and-set shape `settle_streak_snapshot` uses (`streak_settled_through IS NULL OR
       streak_settled_through < :session_date`) so a concurrent settler cannot be overwritten with
       an older boundary. The credit-only branch needs no boundary guard because it does not move
       the boundary. Both branches write the already-bounded integer `_judge_one_day` returned,
       never a SQL-side `shield_level + 1` expression — a SQL-side increment would bypass the cap
       entirely and could violate `ck_train_settings_shield_level`.

    Both branches go through `_judge_one_day`. That is the entire point of the shared primitive,
    and the reason Plan 01 gave it a four-value discriminant instead of a `(fulfilled, eligible)`
    boolean pair: `"credit_only"` is the transition the boolean pair could not express, so without
    it the eager path would have to re-derive the shield arithmetic and the two paths could drift
    apart under a later change. `_judge_one_day` is module-private by naming convention but is
    declared in Plan 01's artifact contract as the shared primitive with the repository as its one
    other caller — import it alongside `tick_days` from `app.services.train_scheduler`.
    Document in the docstring that D-08 needs no code: only `status='completed'` sessions ever
    reach this function, so a started-and-abandoned session is judged by the lazy walk as a plain
    missed scheduled day.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → `POST /train/sessions/{id}/solve` | The client supplies `session_id`, `position`, `guess`, `played_move` and `move_quality`. This is the only client-driven path in the phase that WRITES the streak snapshot. |
| authenticated client → `GET /train/progress` | Read path; the new `badge_visible` field is derived entirely from server-side state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-193-06 | Tampering | `record_solve` → `_apply_completion_tick` (streak inflation by replaying solves on a stale session) | high | mitigate | Three stacked guards, each independently sufficient to bound the exploit: the existing `solved_at IS NULL` conditional UPDATE claims each puzzle exactly once; `_mark_session_complete_if_done`'s `status = 'open'` guard flips a session open→completed exactly once, so `_apply_completion_tick` runs at most once per session; and the frozen-day guard (`session_date > streak_settled_through`) caps a late completion at one shield pip with no count increment. Maximum achievable gain from replaying a stale session is therefore +1 shield, never a count tick. Proven by the Pitfall-2 acceptance test. |
| T-193-07 | Elevation of Privilege | `_apply_completion_tick`, `_open_unfinished_exists` (IDOR on `session_id`) | high | mitigate | The `session_date` lookup resolves `drill_sessions` by `(id, user_id)` together, exactly as `record_solve`'s existing claim UPDATE does — a foreign or invented `session_id` resolves to nothing and the function returns without writing. `_open_unfinished_exists` scopes by `user_id` from `current_active_user.id`. No new client-supplied identifier reaches a `train_settings` write. |
| T-193-08 | Tampering | `weekday_mask` chosen to farm off-day shield pips (D-07) | medium | mitigate | An off-day completion credits at most one pip and is bounded by `SHIELD_CAP`, and the pip buys forgiveness only — never count/intensity, which is D-07's entire design intent. Composition already refuses a second session inside an open window (`completed_session_in_window` / the `uq_drill_sessions_user_open` partial index), so the achievable rate is at most one pip per session window regardless of mask changes. Bounded-and-intended rather than exploitable. |
