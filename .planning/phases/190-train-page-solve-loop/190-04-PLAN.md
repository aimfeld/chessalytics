<objective>
Turn the proven one-puzzle slice into a complete, honest session experience.

The tracer proved the loop works. This plan makes it survive contact with real sessions: the six landing states D-01..D-04 and D-14 demand, the progress indicator SOLV-04 requires, the last-move highlight SOLV-02 requires, and the two failure modes the research flagged as the ones that silently destroy user progress — a failed solve POST and a dead grading worker.

Purpose: every state here is a state a real user hits in week one. A short session, a resumed session, a completed session, and a network hiccup mid-solve are not edge cases in this feature; they are the normal week.

Build `TrainStartScreen.tsx` as the single owner of every pre-loop state, and have `Train.tsx` render it instead of the tracer's provisional Start button.

The component takes the session response (or its absence), the loading and error flags, and a start callback, and resolves to exactly one of six states:

1. **Fresh session available.** Status line `{N} puzzles waiting` where N is the puzzle count, and a `Button variant="default"` labelled `Start session` (`data-testid="btn-train-start"`).
2. **Short session.** When the pending-blob count is above zero AND the puzzle count is below the requested count: status line `{N} puzzles ready` plus the notice `More of your games are still being analyzed.` on its own line, and the same Start button. Both conditions must hold — a session that is short for any other reason shows the fresh copy, and a session that is full shows no notice even with pending blobs.
3. **Resume.** When an open session has at least one solved puzzle and at least one unsolved puzzle remaining: a `Button variant="default"` labelled `Resume session — {solved} of {total} done` (`data-testid="btn-train-resume"`).
4. **Completed session in window.** When the session is complete and its expiry date has not passed: no Start button; show `You scored {score}/{2N} today.` and `Next session: {date}`, formatting the date with `date-fns` in the app's existing short-date style.
5. **Truly empty.** When no session id and no puzzles: `EmptyState` with `layout="page"`, title `No puzzles available yet` and subtitle `Analyze more games to build your training pool.` No action button, no crash path. This is the plain Phase 190 placeholder — do not build the differentiated import-pointer or pool-exhausted variants, which are explicitly Phase 191's.
6. **Loading and error.** While the session request is in flight, render the muted text-only loading treatment matching the existing route-loading pattern (a `data-testid="train-session-loading"` node), not a new skeleton component. On error, render `LoadError` with `variant="centered"` and the resource name `your training session` — never fall through to the empty placeholder, which would tell a user with a full pool that they have nothing to train.

State selection must be a single explicit resolution (one function returning a discriminated state, or one ordered branch chain), not scattered inline ternaries — the six states are mutually exclusive and one must always match.

Give the container `data-testid="train-start-screen"`. Type sizes follow the UI-SPEC roles: the title at the heading size, status and notice lines at the label size. Never go below the project's minimum type size in any of these strings — including the notice and the recap, which read as supporting copy but are not exempt.

In `Train.tsx`, render `TrainStartScreen` whenever the loop is not active, pass the start callback through, and keep the page container test id. Pressing Resume must enter the loop at the next unsolved puzzle — the hook already seeds its index from the solved count, so this is a wiring assertion, not new index maths.

Write `TrainStartScreen.test.tsx` covering all six states, including the two negative short-session cases (pending blobs but a full session shows no notice; a short session with zero pending blobs shows the fresh copy).

  <action>
Make a lost solve impossible to miss.

The solve mutation is the only thing that persists the spaced-repetition outcome; a network failure after grading looks, to the user, like nothing happened while the backend's streak, due date, and fail count never moved. Per the settled recommendation, this is block-and-retry, not advance-with-a-counter.

In `useTrainSession.ts`, gate `advance()` so it is a no-op while the current puzzle's solve mutation has not succeeded, and expose the mutation's pending/error state and a retry callback that re-submits the identical payload (same position, guess, played move, and graded verdict — the verdict is not re-computed, so a retry cannot change the answer).

In `TrainSolveScreen.tsx`, when the solve mutation is in error: render the locked failure line `Couldn't save your result.` with a `Retry` button (`data-testid="btn-train-solve-retry"`), and render the Next control disabled. On a successful retry, the error clears and Next enables. Do not swallow the error, do not auto-advance on a timeout, and do not add a `Sentry.captureException` call here — the mutation cache's global handler already reports it, and a second capture would double-report.

Apply the same treatment on both the desktop and the mobile layout.

Extend `TrainSolveScreen.test.tsx` with a forced-failure case: make the mocked solve mutation reject, assert the failure copy and Retry render, assert the Next control is disabled and that pressing it does not advance the puzzle index, then resolve the retry and assert Next becomes enabled and advancing works. Also assert the retry submits a payload identical to the first attempt.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Train API | Session compose and solve POST; the solve body carries the client's own graded verdict |
| Page state → Stockfish Worker | Puzzle FENs handed to the WASM worker; the worker can die or hang |
| Session response → rendered copy | Server-supplied counts and dates interpolated into user-facing strings |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-190-12 | Repudiation | Lost solve POST | high | mitigate | Block-and-retry: `advance()` is a no-op until the solve mutation succeeds, the failure surfaces locked copy plus a Retry that re-submits the identical payload, and a forced-failure test asserts the index cannot move. A silently dropped solve would leave the user's schedule permanently wrong with no record. |
| T-190-13 | Denial of Service | Grading worker hang or init failure | medium | mitigate | A bounded named-constant readiness timeout plus a worker error handler replace the checking indicator with an inline retry affordance, so a dead engine degrades to a recoverable notice instead of an indefinite wait. Covered by a forced-engine-failure test. |
| T-190-14 | Information Disclosure | Landing/solve screens rendering session data | low | mitigate | The start screen reads only counts and dates from the session response; the solve screen renders only the puzzle FEN, orientation, and arriving move. No reveal, game-card, or tactic-lines request is issued anywhere in this plan — those are Plan 05's, strictly post-solve. |
| T-190-15 | Tampering | Retry re-submitting a different verdict | low | mitigate | The retry re-sends the stored payload rather than re-grading, so a retry cannot produce a different `correct_move` than the original attempt. Asserted by a deep-equality test on the two payloads. |
| T-190-SC | Tampering | npm/pip/cargo installs | low | accept | Zero new packages this phase (190-RESEARCH.md Package Legitimacy Audit); `date-fns` is already a direct dependency. No install task exists. |
</threat_model>
