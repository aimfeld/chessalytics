# Phase 190.1 Plan 02: MultiPV Mount Search, Kept PV, Good-Moves Set Summary

**Widened the Train grading engine's once-per-puzzle mount search to MultiPV width 4 (measured, not guessed) so a single `gradeMove` call now also returns the best line and the good-moves set, while the after-move grading search's already-running PV is captured instead of discarded — zero regression to the existing exact-match fast path or esBefore/esAfter grading contract.**

## Performance

- **Duration:** ~55 min
- **Completed:** 2026-07-26
- **Tasks:** 2
- **Files modified:** 5 (1 measurement script, 1 hook, 3 test files)

## Accomplishments

- `measure-train-movetime.mjs` gained a `--multipv=N` report mode (default 1, byte-identical single-line output when omitted) that reports, per FEN and movetime, the ranks actually returned vs requested, rank-1 bestmove/expected-score/depth, and a STABLE/UNSTABLE verdict against a fixed single-line 1500ms baseline.
- Ran the width x movetime sweep (1/3/4/5 x 1500/2500ms) over the same 10 real sharp-blunder FENs used for the original `TRAIN_GRADING_MOVETIME_MS` measurement — full tables below.
- `useTrainGradingEngine.ts`'s mount search now requests `TRAIN_GRADING_MULTIPV_WIDTH` (4) via `setoption name MultiPV value 4` sent first in `dispatchNow`, before `position`/`go`, so it rides the existing idle/thinking/stopping state machine for free.
- The single `multipv === 1` scalar capture was replaced with a `pvMapRef` `Map<number, PvLine>` accumulator (mirroring `useStockfishEngine.ts`'s own pattern), committed once at `bestmove` into a rank-sorted, white-POV-normalized `RawSearchResult.lines` array. `evalCp`/`evalMate`/`pv` remain as rank-1 convenience fields, so Plan 01's `startGameMoveSearch` needed zero changes.
- `width`/`movetimeMs` now travel WITH a dispatch through `QueuedDispatch` and `pendingReadyDispatchRef`, so a search deferred behind an in-flight `stop` or the initial `readyok` handshake still requests the caller's intended budget rather than a stale/default one.
- `GradeResult` gained `bestLine` (rank 1's line), `playedLine` (played move + the after-move search's own PV, or exactly `bestLine` on the exact-match fast path), and `goodMoveUcis` (every returned rank whose expected-score drop against rank 1 classifies `null` via the existing `classifyLiveSeverity` — no new cutoff).
- `esBefore` still comes from rank 1 alone and the D-06 exact-match fast path is unchanged — verified by the full pre-existing grading-contract suite passing unmodified, plus new tests pinning the exact behavior.

## Decisions Made

- See `key-decisions` in the frontmatter above for the width/movetime choice rationale and the illegal-move defensive-branch treatment.
- `pvMapRef` is committed to the resolved `lines` array only at `bestmove`, not on every `info` line the way `useStockfishEngine.ts`'s live-rendering `pvMapRef` is — this hook has no per-tick UI consumer (unlike the analysis board's live eval bar), so a single commit at settle time is simpler and avoids allocating a sorted array on every `info` line during a search.

**Verdict:** FEN 4 (game 238467 ply 22, a middlegame position around +2.2 to +2.9 pawns) is a genuinely noisy read for this engine build at every width/movetime combination tested — never the bestmove, always a cp wobble of roughly 40-70 that occasionally crosses the 0.025 ES tolerance. Every other FEN is STABLE at every width/movetime, and no FEN ever returned fewer ranks than requested (all 10 curated positions have >=5 legal moves). Chose width 4 (smallest satisfying "at least 4 ranks") and kept the existing 1500ms movetime (raising it did not remove FEN 4's noise, so there is no justification for the larger budget).
