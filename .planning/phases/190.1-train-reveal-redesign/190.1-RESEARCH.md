## User Constraints (from CONTEXT.md)

### Locked Decisions

#### D-1: Client engine sources ALL lines and evals

All three reveal lines and their evals come from the client-side Stockfish WASM
grading engine, never from stored server evals. Rationale: stored evals and
client evals are not reproducible across machines (project_eval_nondeterminism),
so mixing sources can show "YOUR MOVE +0.2 / BEST MOVE +0.3, verdict: incorrect"
contradictions. Adrian explicitly chose re-evaluating everything client-side
over accepting that rough edge.

Search plan (the cheap version — one genuinely new search per puzzle):

1. **Mount search → MultiPV.** The existing once-per-puzzle mount search in
   `useTrainGradingEngine.ts` becomes a MultiPV search on the puzzle FEN. One
   search yields: the best move, the best line (PV) + its eval, AND the
   good-moves set for the green arrows. Grading semantics must not regress
   (esBefore still read from multipv 1).
2. **After-your-move search: keep the PV.** `gradeMove`'s existing search on the
   position after the played move already produces the YOUR MOVE eval
   (esAfter); it currently discards the PV arriving in the same UCI `info`
   stream — capture it instead. No extra search.
3. **Refutation search: new, lazy.** One new search on the position after the
   game move, dispatched only when the reveal opens (needs the game move as
   UCI from the server reveal). PLAYED IN GAME box may show a short spinner
   while the other two boxes render instantly.

#### D-2: Board arrows on reveal follow puzzle type

- **Green arrows = actual good moves**: moves whose expected-score drop vs. best
  is better than an inaccuracy, per the project's EXISTING live-flaw thresholds
  (`liveFlaw.ts` / `INACCURACY_DROP` family) — no new magic cutoff. Sourced from
  the MultiPV mount search.
- Count follows puzzle type: **sharp = exactly 1** green arrow (by definition
  only one move is right); **soft/herring = all good moves, capped at 3**.
- **User's played move**: shown with its own arrow (distinct from green;
  visual treatment is a UI-spec decision).
- **Game move**: smaller white arrow, same style as the analysis board's
  played-move arrow (`BoardArrow` / `arrowColor.ts` precedent carries over).

#### D-3: Reveal panel content

- **Verdict rows state the answers given**, not bare marks:
  - `Guess: One critical move ✗` (the guess the user committed)
  - `Move: Nc3 ✓` (the played move in SAN — client-side UCI→SAN via chess.js)
- **Three steppable line boxes**, each with an eval, each steppable on the
  shared board via the existing `TrainLineStepper` + `onFenChange` pattern
  (multi-stepper precedent: the tactic missed/allowed pair):
  1. **YOUR MOVE** — played move + engine continuation (after-search PV)
  2. **BEST MOVE** — best move + best line (MultiPV rank 1)
  3. **PLAYED IN GAME** — game move + engine **refutation line** (Adrian chose
     refutation over the actual game continuation)
- **Game card removed.** Replaced by a small footer: opponent + game date
  (data already available from the game fetch; no full `GameCard`).
- **Analyze + Next on one line.** The reference mockup (chat, 2026-07-26) was
  illustrative for the line boxes ONLY — its share/trash icons are out of
  scope, its exact styling is not binding.
- **Analyze deep link → the puzzle position**, i.e. one ply BEFORE the mistake
  was made (currently `GameCard analyzePly={puzzle.ply}` lands one ply late).

#### D-4: Session score on the progress bar

Current session score at the top-right of the progress bar (e.g. `5 / 8 pts`,
max = solved-so-far × 2). `trainSession.sessionScore` is already
client-accumulated and localStorage-backed (190-04 D-03), so it survives a
resume — pure wiring, no new state.

#### D-5: Server reveal slims down (or at minimum extends)

The server reveal must additionally provide the **game move as UCI** (it has
SAN only today) so the client can run the refutation search. With all
lines/evals client-sourced, `best_move`/`best_move_san`/`pv` in the reveal
response become candidates for removal — plan-time decision whether to slim
now or keep as fallback. The reveal keeps: game move, `puzzle_type`,
`has_tactic_lines`, game_id/ply/fen. POOL-10 (no answer key pre-attempt) is
untouched — the reveal endpoint's 409 gate stays as is.

## Summary

This phase rebuilds the Train reveal panel to be fully self-consistent: one client-side
Stockfish search (mounted with MultiPV) supplies the best move, the best line, and the
good-moves arrow set; the existing after-move grading search is extended to keep its PV;
and a new lazy single-line "refutation" search runs once the reveal opens. All of this
builds directly on infrastructure that already exists and is already proven in this
codebase — `useStockfishEngine.ts` already runs `setoption name MultiPV value N` against
the exact same vendored engine binary (`stockfish-18-lite-single.js`), and a headless Node
probe run during this research (see `<verification>` in Code Examples) confirmed the
per-rank `info ... multipv K ... pv ...` line shape the parser must handle, including the
"fewer legal moves than requested width" edge case (2 legal moves, MultiPV 5 requested → the
engine reports exactly ranks 1 and 2, no fabricated ranks).

The reveal's backend change is smaller than the CONTEXT.md's open question implies: the
game move's UCI is NOT currently stored, but it does not need a migration. `game_positions`
already stores `move_san` (the move played *from* the puzzle's own ply) and the reveal
already reconstructs the puzzle's full FEN via `full_fen_at_ply`. `chess.Board(fen).parse_san(move_san).uci()`
— an idiom already used three times elsewhere in this codebase (`library_service.py`,
`flaws_service.py`) — derives the UCI with zero schema change.

The Analyze deep-link off-by-one is confirmed and precisely diagnosable: `Analysis.tsx`'s
`goToNode(mainLine[ply])` lands on the node reached AFTER `ply+1` half-moves (because
`mainLine[k]` is built from `sans[k]`, the (k+1)-th half-move). `GameCard analyzePly={puzzle.ply}`
therefore lands one ply late, exactly as CONTEXT.md states. The fix is `analyzePly={puzzle.ply - 1}`.

**Primary recommendation:** Extend `useTrainGradingEngine.ts`'s existing single-line UCI
plumbing to a `Map<multipv, PvLine>` accumulator (mirroring `useStockfishEngine.ts`'s
`pvMapRef` pattern almost verbatim), reuse `hooks/uciParser.ts`'s `PvLine`/`parseInfoLine`
completely unchanged (it already parses `pv` and `multipv` per line — nothing there needs
to change), derive "good move" purely from the existing `classifyLiveSeverity`/`INACCURACY_DROP`
predicate applied to each MultiPV rank's ES relative to rank 1, and add exactly one new
nullable backend field (`played_in_game_move: str | None`, UCI) computed via `parse_san`
with no migration.

### Pattern 1: MultiPV accumulation via a rank-keyed Map (proven precedent)

**What:** Accumulate one `PvLine` per `multipv` rank into a `Map<number, PvLine>`, cleared
at the start of each search, committed (sorted by rank) once needed.
**When to use:** The mount search (needs N ranks for best move + good-moves set + best line).
**Example:**
```typescript
// Source: frontend/src/hooks/useStockfishEngine.ts:94-95,211-274 (existing, proven pattern)
const pvMapRef = useRef<Map<number, PvLine>>(new Map());

// on each `info ...` line:
const parsed = parseInfoLine(line); // hooks/uciParser.ts — UNCHANGED, already returns { multipv, pv, scoreCp, scoreMate, depth }
if (parsed !== null) {
  pvMapRef.current.set(parsed.multipv, {
    multipv: parsed.multipv,
    depth: parsed.depth,
    moves: parsed.pv,          // full UCI move list for this rank
    evalCp: parsed.scoreCp,
    evalMate: parsed.scoreMate,
  });
}

// on `bestmove` (commit):
const ranked = [...pvMapRef.current.values()].sort((a, b) => a.multipv - b.multipv);
```
This requires ZERO changes to `hooks/uciParser.ts` — `parseInfoLine` already extracts
`pv`/`multipv` per line; only `useTrainGradingEngine.ts`'s own accumulation (currently a
single scalar `currentRawEvalRef`, only committing `multipv === 1`) needs widening.

### Pattern 2: `setoption name MultiPV value N` ordering (documented gotcha, already fixed once in this repo)

**What:** `setoption` must be observed by the engine before the `go` it is meant to affect.
**When to use:** Every time the grading engine dispatches a search whose desired MultiPV
width differs from the previous search's width (mount search wants N; after-move and
refutation searches want 1).
**Example:**
```typescript
// Source: frontend/src/hooks/useStockfishEngine.ts:278-281 + its own bug-fix comment at
// lines 346-351 documents the exact failure mode to avoid:
// "isReady survived the toggle, so on re-enable analyze() fired a `go` on the fresh worker
//  BEFORE it had received `setoption MultiPV value 2` — the re-search ran at MultiPV=1"
if (line === 'uciok') {
  worker.postMessage(`setoption name MultiPV value ${MULTIPV}`);
  worker.postMessage('isready');
  return;
}
```
For `useTrainGradingEngine.ts`, the safer per-search pattern (not just at init) is: send
`setoption name MultiPV value <width>` immediately before `position fen ...` + `go ...`
inside `dispatchNow`, gated on state === idle (which `dispatchNow` already guarantees — it
is only ever called from `search()`'s idle branch or the CR-01 ready-drain path). A headless
probe (this research session) confirmed the vendored engine's own JS shim queues `go`/`setoption`-
prefixed commands and dispatches them strictly in submission order once idle — no additional
`isready` round-trip is required for a mid-session MultiPV change, only at the very first
init (uciok → isready) does the ordering race exist. **Verify this holds during
implementation** by asserting the FIRST `info` line of the mount search after a
`setoption ... value N` reports `multipv <= N`, never a leftover-scoped single line.

**When to use:** Rendering the green good-move set, the user's played-move arrow, and the

Good-move arrows should reuse `DARK_GREEN` (`'#1E6B1E'`, `arrowColor.ts:30`) — the
established "good/green" categorical arrow color elsewhere in the app (Move Explorer) —

### Anti-Patterns to Avoid

- **Re-deriving PV→FEN replay logic:** `TrainLineStepper.tsx`'s `replayLine()` and
  `EngineLines.tsx`'s `replayPvLine()` already do this (SAN-based and UCI-based
  respectively). The new client-computed lines are UCI arrays from the grading engine — use
  `chess.js` to convert to SAN once (mirroring `replayPvLine`'s pattern exactly), then feed
  SAN into the EXISTING `TrainLineStepper` (which only accepts `moves: string[]` as SAN) —
  do not add a second UCI-aware stepper variant.
- **Reinventing eval formatting:** `formatScore(evalCp, evalMate)` already exists
  (`frontend/src/components/analysis/EngineLines.tsx:179-193`, exported) and produces
  exactly the `+0.3` / `#+5` convention this phase's line-box headings need. Import it
  rather than writing a new formatter.
- **Trusting stored server evals anywhere in the reveal (D-1, LOCKED):** every eval shown
  in the three line boxes and every arrow's "good move" classification must originate from
  THIS puzzle's client-side searches. `PuzzleRevealResponse.best_move`/`best_move_san`/`pv`
  (the OLD server-stored answer key) must not be displayed as an eval-bearing number anywhere
  — if kept at all (see D-5 plan-time decision), they exist only as a defensive fallback for
  a genuinely dead grading engine, never blended with client numbers.

## Common Pitfalls

### Pitfall 1: MultiPV width change without re-arming the readiness/generation machinery

**What goes wrong:** If `setoption name MultiPV value N` is sent but the subsequent `go`
races a stale in-flight `stop` (state `'stopping'`), the option can apply to the WRONG
search, silently producing fewer ranks than expected (or ranks from the previous width).
**Why it happens:** `useTrainGradingEngine.ts`'s `search()` already serializes dispatch
through `stateRef.current` (`idle`/`thinking`/`stopping`) — `dispatchNow` is the single
choke point where `position`+`go` are sent. As long as the `setoption` line is inserted
INSIDE `dispatchNow` (not in the calling code), it inherits the existing serialization for
free.
**How to avoid:** Put `worker.postMessage('setoption name MultiPV value ...')` as the FIRST
line of `dispatchNow`, before `position fen`. Do not send it from `startGrading`/`gradeMove`
directly (those can be deferred behind a `stop` via the `queuedDispatchRef`/`pendingReadyDispatchRef`
paths — the width value must travel WITH the deferred dispatch, not be sent eagerly at call time).
**Warning signs:** A grading run's first `info` line reports `multipv` > 1 when only a
single-line (after-move/refutation) search was requested, or `bestSearchRef` settles with
fewer ranks than the puzzle's `puzzle_type` requires for its arrow count.

### Pitfall 2: The refutation search competing with StrictMode double-mount / abort semantics

**What goes wrong:** `TrainSolveScreen`'s puzzle-mount effect already calls `abortGrading()`
on cleanup (bumping `generationRef.current`), and the 190-01 checkpoint bug fix depends on
`startGrading` being idempotently re-callable on StrictMode's double-invoke. The NEW
refutation search is dispatched from `TrainReveal` (a CHILD component, later in the render
tree, mounted only once `verdict !== null`) — it must reuse the SAME `generationRef` so an
in-flight refutation search is correctly discarded if the user somehow navigates away
mid-search (e.g. a fast double-click on Next, or unmounting via route change).
**Why it happens:** `abortGrading()` already bumps the generation and is called
unconditionally on `TrainSolveScreen`'s puzzle-mount effect cleanup — but that effect's
cleanup fires when `puzzle.fen` changes (i.e., when advancing to the NEXT puzzle), which is
exactly when a still-in-flight refutation search for the PREVIOUS puzzle must be discarded.
**How to avoid:** Expose the refutation search as `search(fen, generationRef.current, 1)`
under the hood (reusing the exact same generation-guarded promise machinery `startGrading`
already uses) rather than a parallel ad-hoc mechanism. Any `.then()`/`.catch()` on its
result must check `generation !== generationRef.current` before committing to state, exactly
like `startGrading`'s existing `if (generation !== generationRef.current) return;` guard.
**Warning signs:** A refutation eval from puzzle N appears in puzzle N+1's PLAYED IN GAME box.

### Pitfall 3: `gradeMove`'s D-06 fast path has no PV to "keep"

**What goes wrong:** D-1 point 2 says "gradeMove's existing search on the position after the
played move already produces the YOUR MOVE eval; capture its PV" — but when the played move
EXACTLY MATCHES the engine's best move (`playedMoveUci === best.bestMoveUci`), `gradeMoveInner`
takes the fast path and returns `esAfter: esBefore` with **no second search at all**
(`useTrainGradingEngine.ts:466-470`). There is no "after-move PV" to capture in that branch.
**Why it happens:** The fast path is intentional (D-06, avoids a redundant search when the
player found the engine's own top move) — but "YOUR MOVE" and "BEST MOVE" are now two
SEPARATE reveal boxes that both need a line to display.
**How to avoid:** When the fast path fires, YOUR MOVE's line and eval are simply BEST MOVE's
line and eval (rank 1 from the mount search) — this is exactly CONTEXT.md's plan-time
question 1 ("played move == best move ... collapse to one box?"). The mount search's rank-1
PV (already captured per Pattern 1) is available and correct here with zero extra search;
no code path needs to special-case "missing PV" — it should read from the SAME rank-1 result
regardless of which path graded the move.

### Pitfall 4: MultiPV search cost is not free — node budget splits across ranks

**What goes wrong:** `TRAIN_GRADING_MAX_NODES = 2_000_000` was measured (190-01) for a
SINGLE-line search. Requesting MultiPV=4-5 on the SAME node budget forces Stockfish to share
search effort across more root moves, reducing the effective depth/quality on EVERY rank
(including rank 1, whose eval and PV are the "BEST MOVE" box's displayed truth).
**Why it happens:** MultiPV is not free — Stockfish's search tree work scales with the
number of requested lines; a search that reached depth 16 at MultiPV=1 will reach a
shallower depth at MultiPV=4 under the identical node/time cap (confirmed in this research's
headless probe: MultiPV=4 example capped depth ~15-16 vs. `useStockfishEngine.ts`'s own
MultiPV=2 default at the same 1500ms/2M-node budget).
**How to avoid:** Either (a) accept the depth reduction for the mount search specifically
(the plan-time "MultiPV width" question already flags this as needing measurement — likely
resolved via a headless-Node timing sweep mirroring `scripts/measure-train-movetime.mjs`'s
methodology), or (b) bump the mount search's movetime/node budget above
`TRAIN_GRADING_MOVETIME_MS` specifically for the MultiPV=N case, while leaving the
single-line after-move/refutation searches at the existing measured 1500ms budget (they do
not need multiple ranks, so their per-rank depth is unaffected by this phase at all).
**Warning signs:** Rank-1's eval on the mount search visibly disagrees with what a bare
MultiPV=1 search at the same budget would report for the same FEN — a regression in grading
accuracy the 190-01 measurement explicitly guarded against.

### Pitfall 5: `PuzzleRevealResponse` field removal breaks a live consumer without a compile error

**What goes wrong:** D-5's "candidates for removal" (`best_move`, `best_move_san`, `pv`) are
read today by `TrainReveal.tsx` (`pv` for the "Best line" stepper) — removing them from the
Pydantic response model AND the TS mirror is a coordinated two-repo change; removing only
one side either 500s (backend still returns the field, frontend type says it doesn't exist —
harmless) or silently `undefined`s a field the frontend still reads (backend removes it,
frontend type still declares it — a TYPE LIE that `tsc` cannot catch since the type is
hand-mirrored, not derived).
**Why it happens:** `frontend/src/types/train.ts` is a hand-maintained mirror of
`app/schemas/train.py` (no codegen) — nothing enforces they stay in sync except discipline
and the router-level test suite (`tests/routers/test_train.py`).
**How to avoid:** If D-5 resolves to "slim now," change `app/schemas/train.py`,
`app/repositories/train_repository.py`'s `RevealedPuzzle` dataclass, `app/routers/train.py`'s
response construction, `frontend/src/types/train.ts`, AND every read site
(`TrainReveal.tsx`'s `revealQuery.data?.pv`/`.best_move_san`) in the SAME task/commit — never
split across plan waves. Grep `revealQuery.data\?\.` before removing any reveal field to find
every consumer.
**Warning signs:** `npm run build` (tsc -b) passing while a removed field is still referenced
— this happens if the type mirror update lags the actual removal, since esbuild-based
`vitest`/`vite build` dev paths do not always catch property-access-on-removed-field errors
the way a strict `tsc -b` run does (CLAUDE.md already flags this general class of gap: "npm
lint+test do NOT type-check").

## Open Questions

1. **MultiPV width vs. movetime budget (CONTEXT.md plan-time question 2)**
   - What we know: MultiPV is not free; the headless probe in this session observed shallower
     depth at MultiPV=4 (~15-16) vs. `useStockfishEngine.ts`'s own MultiPV=2 default at the
     identical 1500ms/2M-node budget.
   - What's unclear: The exact width (4 vs 5) and whether the existing 1500ms budget should be
     kept, raised specifically for the mount search, or left unchanged with the accuracy
     tradeoff accepted (only ranks 2-4 are used for a boolean "is this an inaccuracy-or-better
     move" classification, which tolerates more search noise than the rank-1 exact eval).
   - Recommendation: A short headless-Node timing sweep (same technique as this research's
     probe, extended to more FENs) before locking the constant, mirroring 190-01's own
     measurement discipline. This is inexpensive (no browser needed) and directly informs
     `TRAIN_GRADING_MULTIPV_WIDTH`/a possibly-separate `TRAIN_GRADING_MOUNT_MOVETIME_MS`.

2. **Line-coincidence dedupe UX (CONTEXT.md plan-time question 1)**
   - What we know: `BoardArrow.layerKey`/`onTop` already let coincident arrows survive
     rendering (Pattern 3); `TrainReveal`'s box-collapse behavior when played===best or
     game-move===best is a pure UI-copy decision, not a data-availability gap (Pitfall 3
     confirms the data is always available regardless of which path graded the move).
   - What's unclear: The exact copy/layout for a collapsed box (e.g. "YOUR MOVE = BEST MOVE"
     single box vs. two boxes both showing the same line).
   - Recommendation: Resolve as a UI-spec decision alongside the played-move arrow color
     (A2) — both are presentation-only, zero new data plumbing either way.

3. **`solvedPositions` exposure for the score-bar's "max" denominator**
   - What we know: `useTrainSession.ts`'s `sessionScore` updates in the solve mutation's
     `onSuccess` (immediately on solve success, BEFORE `advance()`/Next is pressed).
     `currentIndex` only advances when the user presses Next — so it LAGS `sessionScore` by
     one puzzle at reveal time. The internal `solvedPositions` Set (already tracked, used
     for the block-and-retry gate) updates on the SAME timing as `sessionScore`, but is not
     exposed in `UseTrainSessionResult` today.
   - What's unclear: Whether the plan should expose `solvedPositions.size` (or a derived
     `sessionSolvedCount`) as a new hook return field so the progress-bar's "max = solved-so-far
     × 2" stays in sync with `sessionScore`'s own update timing, rather than reusing
     `currentIndex` (which would show a stale "5 / 6 pts" instead of "5 / 8 pts" right after
     a correct 2-point solve, until Next is pressed).
   - Recommendation: Expose it — reusing `currentIndex` for this specific display will visibly
     desync from `sessionScore` at the exact moment (right after solving, on the reveal
     screen) where the score display bullet in the phase description calls it out.
