<objective>
Build the Train progress read-model end to end: a pure weekly streak/flame settlement machine backed by the D-18 settled-streak snapshot, a `GET /train/progress` endpoint that lazily settles elapsed weeks and computes the remaining numbers on the fly from `drill_sessions`/`drill_items` history, and the compact stats row that becomes the Train start screen's motivational headline (D-13).

Purpose: this is the phase's tracer. Every later plan (nav badge, empty states, settings) hangs off this one endpoint and this one query key. Proving the whole path — migration → pure service → repository → router → typed client → TanStack hook → rendered chip row — before any expansion means an architectural dead end costs one commit, not six.

Note on D-05: mastered/parked counts (and Plan 02's waiting count and `pool_state`) remain fully compute-on-the-fly per the original D-05. Only the streak/flame portion is amended by D-18's snapshot, because a settled week must be frozen against a later schedule change. The retroactivity requirement is preserved: the FIRST settlement replays all pre-existing Phase-190 history from an all-null snapshot, so prior sessions still count with no backfill migration.

- `class FlameState(StrEnum)` with `MINIMUM = "minimum"`, `MEDIUM = "medium"`, `MAXIMUM = "maximum"` (import `StrEnum` from `enum`). A string-valued enum makes the in-memory value, the TEXT column value and the wire literal byte-identical, so no mapping table is needed in either direction. Add `FLAME_LADDER: tuple[FlameState, ...] = (FlameState.MINIMUM, FlameState.MEDIUM, FlameState.MAXIMUM)` plus two tiny module-private helpers that step up and down that tuple by index — the notch arithmetic must read off an explicit ordered ladder, never off integer adjacency.
- `required_sessions_per_week(weekday_mask: int) -> int` returning `1` when `weekday_mask == 0` (D-07 "train anytime") else `bin(weekday_mask).count("1")` — the count of scheduled days, never which specific days (D-01).
- `@dataclass(frozen=True) class SettledStreak` with `streak_count: int`, `flame_state: FlameState | None`, `settled_through: datetime.date | None`. This is exactly what persists on `train_settings`.
- `@dataclass(frozen=True) class StreakView` with `settled: SettledStreak` (the snapshot to persist), `display_flame: FlameState | None` (the D-03 overlay, never persisted), `current_week_completed: int`, `streak_lost_last_week: bool`, and `changed: bool` (True when `settled` differs from the input snapshot, i.e. the caller must write).
- `settle_weeks(snapshot: SettledStreak, completed_session_dates: Sequence[datetime.date], *, weekday_mask: int, today: datetime.date) -> StreakView`.

`settle_weeks` contract to implement and document:
- Bucket every input date by `week_start(d)` into a count-per-week mapping. Count list ENTRIES, not distinct dates: `required` counts sessions, and two completed sessions sharing a date both count (the D-10 session window makes that near-impossible in practice, but the function must not silently deduplicate).
- `current_start = week_start(today)`. The current week is NEVER settled: its count becomes `current_week_completed` and it never touches `streak_count`, `flame_state` or `settled_through` (D-03/D-04, and D-18's "once settled, frozen forever" only makes sense if an in-progress week is never folded in).
- Determine the first week to settle. When `snapshot.settled_through is None` this is the FIRST settlement: start at `week_start(min(completed_session_dates))` so the entire pre-existing history replays (this is what preserves D-05's Phase-190 retroactivity with no backfill migration). With no sessions at all there is nothing to settle. Otherwise start at `snapshot.settled_through + 7 days`.
- Settle every week `w` with `first_week <= w < current_start`, in chronological order, INCLUDING zero-activity gap weeks — those are missed weeks. Do not iterate only over weeks present in the input.
- Per settled week with `required = required_sessions_per_week(weekday_mask)`: fulfilled (`count >= required`) -> `streak_count += 1` and the flame rises one ladder notch, where an unlit (`None`) flame lights at `MINIMUM` and `MAXIMUM` is the cap; missed -> if the flame is `None` nothing changes (no streak is running), if the flame is `MINIMUM` then `streak_count = 0` and the flame becomes `None`, otherwise the flame drops one notch and `streak_count` is left unchanged.
- `settled_through` advances to the Monday of the last week settled in this call, or stays at its input value when nothing settled. It must never move backwards.
- `changed` is True only when the returned `settled` differs from the input `snapshot`. A call that settles nothing reports `changed=False` so the caller performs no write — this is the idempotence guard that makes repeated reads free.
- `display_flame` applies the D-03 overlay: normally `settled.flame_state`, but `FlameState.MINIMUM` when `settled.flame_state is None` and `current_week_completed > 0` ("the minimum flame lights immediately after the very first completed session while the count stays 0"). Keeping this on a separate field rather than mutating `settled.flame_state` is load-bearing: persisting the overlay would write an unsettled week's state into the frozen snapshot and corrupt it.
- `streak_lost_last_week` is derived from the resulting state, not from "did this call settle the reset", so it survives a page reload within the same week: True when `settled.settled_through == current_start - 7 days`, `settled.streak_count == 0`, `settled.flame_state is None`, `current_week_completed == 0`, and at least one completed session predates `current_start` (the last clause distinguishes a lost streak from a brand-new user who never had one; the `current_week_completed == 0` clause clears the notice once the user trains again rather than showing "Streak reset" beside a freshly lit flame).
- Order-insensitive by construction (bucketing, not scanning) — no sort assumption on the input beyond `min()`.
- Add `"FLAME_LADDER"`, `"FlameState"`, `"SettledStreak"`, `"StreakView"`, `"required_sessions_per_week"`, `"settle_weeks"`, `"week_start"` to the module's `__all__`.

Document in the docstring that a settled week is frozen forever (D-18): a later `weekday_mask` or timezone change cannot re-judge it, because settlement only ever walks weeks strictly after `settled_through`. The current week alone is judged live against the current mask, so a mid-week schedule change prospectively re-judges only the in-progress week — accepted semantics per D-18.

The detector fired `pluralization` on the phase scope ("SCHD-03 is scoped to this phase **alongside** the schedule settings UI"). Two nouns were re-examined:

**0. What "the streak" is — decision: `promote` (added by the D-18 revision).**
Before D-18 the streak was a *derived view* over session history, recomputed from scratch on every read. D-18 promotes it to a **settled snapshot with an append-only frontier** (`streak_settled_through`): the primary noun is now "the frozen record of judged weeks", and raw session history is demoted to the input that advances that frontier. This is the promote, not an add-alongside — there is exactly one authority for a settled week's judgment (the snapshot), and the replay is no longer a parallel source of truth that could disagree with it. Mastered/parked/waiting counts stay pure derivations (original D-05); only the streak crossed the line, because only the streak has to be stable against a later input change.
*Invariant test encoding the generalized intent:* `test_settled_week_survives_mask_change` — a settled week's judgment is unchanged by a subsequent `weekday_mask` change.

**1. What a "week is fulfilled" names — decision: `promote`.**
Through Phase 189 the implicit noun was *the set of scheduled weekdays* ("did the user train on their scheduled days?"). D-01 generalises it to *a count of completed sessions* (`completed >= required`), with the weekday set demoted to a single input that determines `required = popcount(weekday_mask)`. The general representation is promoted to primary and the specific one becomes a detail of one variant — `weekday_mask == 0` ("train anytime") is now just `required = 1`, the same expression, not a special case bolted alongside. `required_sessions_per_week` is the single function that names this, and no code path asks "which days did they train on".
*Invariant test encoding the generalized intent (already in Task 2's behavior block):* for a mask with 3 bits set, three sessions on any three arbitrary days fulfil the week, and two do not — the identity of the days is never consulted.

**2. Whether an ad-hoc session is a second kind of session — decision: `no-change`.**
Phase 189 D-12 already made composition day-agnostic: neither the resume guard, the completed-in-window guard, nor fresh composition consults `weekday_mask` to decide whether composing is allowed.
