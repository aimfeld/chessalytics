<objective>
Complete the Train backend read-model. Two strands, both landing in `app/repositories/train_repository.py`:

1. The three fields the attention and empty-state surfaces need — a read-only waiting-puzzle count for the nav badge (SCHD-02/D-07), a `pool_state` discriminant that tells "never had training material" apart from "pool exhausted" (PROG-05/D-16), and `next_due_date` for the "All caught up!" copy.
2. The settle-before-mutate half of D-18 on `PUT /train/settings` (Task 3), which protects PROG-01's streak from being retroactively re-judged.

Purpose: the badge count and the two empty states are the two places where guessing on the client would silently produce the wrong message; both signals are computed server-side, from the same eligibility predicates composition uses, without ever writing a `drill_sessions` row. Task 3 closes the matching hazard on the write side: lazy-on-read settlement alone does not protect a user who never opens Train between elapsing a week and changing their schedule.

All three tasks operate on the same repository module and the same two backend test files, so they share nearly all of their `read_first` context — that shared context is why this backend plan carries three tasks comfortably where a cross-stack plan could not.

Output: `get_waiting_puzzle_count`, `_pool_state`, `_next_due_date` and settle-before-mutate in `upsert_settings`, all in `train_repository.py`; three new fields on `TrainProgressResponse` and its TypeScript mirror.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → FastAPI `/train/progress` | Authenticated but untrusted client; identity comes only from the session cookie. |
| FastAPI → PostgreSQL | The new COUNT queries traverse `drill_items`, `game_flaws`, `games` and `game_best_moves` via the pool statements — every one must stay `user_id`-scoped. |
| client-triggered mutation → D-18 settled snapshot | `PUT /train/settings` now advances `streak_count` / `flame_state` / `streak_settled_through` as a side effect, so a client-controlled request mutates a durable competence record. |
