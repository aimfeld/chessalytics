## Assumption Delta

**Signal:** `pluralization` — the red-herring puzzle's identity moves from *"a row owned by the
solving user"* to *"a globally shared row that any user may be served, whose source game belongs
to someone else and may vanish."*

**The noun that is now primary:** the **pool position** — a `herring_pool` row, position-scoped
and identity-blind, exactly as `GameBestMove` is position-scoped rather than user-scoped.

**Decision: `promote`.**

- `herring_pool.id` is promoted to the herring puzzle's authoritative identity. It is the key
  `drill_solves.herring_pool_id` records (D-04) and the key the no-repeat exclusion runs on.
- The source `(user_id, game_id, ply)` triple is **demoted to nullable provenance** — a
  uniqueness key at generation time only (SEED-120's "real triple"), never an access-control
  column, never a serve-time filter (D-10 forbids an own-game exclusion join).
- `drill_solves.game_id` is likewise demoted from "the puzzle's identity" to "a nullable link to
  where this position came from" (D-05).
- **Authoritative owner of the FEN + arriving move: the pool row itself** (D-03). The source PGN
  is never consulted for a herring, alive link or not.

**Why not add-alongside:** keeping `(game_id, ply)` as the herring's key alongside the new pool
row is exactly the shape that breaks when a foreign user deletes their game — the key evaporates
and the in-flight session loses a puzzle. Promotion is what makes D-01's `SET NULL` survivable.

**Consequence this plan must honor:** `herring_pool.id` must be a surrogate primary key. The
SEED-120 `(user_id, game_id, ply)` triple **cannot** be the PK, because a PK column cannot be
NULL and D-01 requires the composite FK to null out on source-game deletion. The triple becomes
a `UNIQUE` constraint instead.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Confirm the pool row's identity model before the table is created</name>

  <decision>
What is `herring_pool`'s primary key, given that D-01 requires the source-game link to null out on
deletion?
  </decision>

  <context>
SEED-120 states that the pool row's "identity is a real `(user_id, game_id, ply)` triple,
mirroring `game_positions`' own PK". That statement and CONTEXT.md D-01 cannot both be satisfied
literally: D-01 requires a **nullable** composite FK to `games(id, user_id)` with
`ondelete="SET NULL"`, and a PostgreSQL primary-key column cannot be NULL. The moment a source
game is deleted, a `(user_id, game_id, ply)` primary key would either block the delete or violate
the PK.

CONTEXT.md is explicit that where it and the seed differ, CONTEXT.md wins, and D-01 is one of the
two named divergences. So the triple must move somewhere that tolerates NULLs. This checkpoint
confirms *where*, because a primary key is a one-way door: changing it later means a table rewrite
plus a remap of every `drill_solves.herring_pool_id` value already recorded against live sessions.

This is also the concrete form of this plan's Assumption Delta: the herring's identity is being
promoted from "a row owned by the solving user" to "a globally shared pool row", and the PK is
where that promotion is either made real or quietly undermined.

What is NOT in question: D-01's `SET NULL` policy itself (locked, with the user's reasoning
recorded — a `CASCADE` would silently erode a pool that is supposed to be computed once), and
D-04's decision that `drill_solves.herring_pool_id` is the no-repeat key.

**Recommended option: A.**
  </context>

  <options>
    <option id="option-a">
      <name>A — Surrogate `id` primary key, with the SEED-120 triple as a UNIQUE constraint</name>
      <pros>Satisfies D-01 exactly: `user_id` and `game_id` are free to null out while the row keeps a stable identity. Gives `drill_solves.herring_pool_id` a single, narrow FK target (D-04). The triple still does its real job — generation-time dedup and top-up idempotency via `ON CONFLICT (user_id, game_id, ply) DO NOTHING`. Matches the Assumption Delta's `promote` decision: the pool row is primary, the source triple is demoted to provenance.</pros>
      <cons>Departs from the seed's literal wording and from `game_positions`' natural-key convention. Adds 8 bytes per row (negligible at 3,000-5,000 rows).</cons>
    </option>
    <option id="option-b">
      <name>B — Keep `(user_id, game_id, ply)` as the PK and make the FK `ON DELETE CASCADE`</name>
      <pros>Literally matches SEED-120's identity wording and the codebase's dominant FK convention.</pros>
      <cons>Directly contradicts locked decision D-01 and the seed's own Pitfall 2 ("store the FEN so the puzzle survives independently, treat the game link as a nullable garnish"). A source-game deletion would delete the whole pool row, silently eroding a pool that is computed once and topped up manually (D-14), and it fails ROADMAP SC3. Not viable.</cons>
    </option>
    <option id="option-c">
      <name>C — Keep the triple as PK but store a sentinel (e.g. user_id = 0) instead of NULL on deletion</name>
      <pros>Preserves the natural key literally while keeping the row alive.</pros>
      <cons>Requires an application-level trigger or delete hook to rewrite the key, since `ON DELETE SET NULL` cannot target a PK column — replacing a database-enforced guarantee with code that can be forgotten. Sentinel rows collide on the PK the moment two deleted games shared a ply. Strictly worse than A while looking more faithful to the seed.</cons>
    </option>
  </options>

  <resume-signal>Select: option-a, option-b, or option-c (option-a is recommended)</resume-signal>

**1. `app/models/herring_pool.py` — new `HerringPool` model, `__tablename__ = "herring_pool"`.**
Follow `GameBestMove`'s position-scoped docstring convention and `GamePosition`'s table-level
constraint style. Columns:
`id` BigInteger surrogate primary key (see this plan's Assumption Delta for why the SEED-120
triple cannot be the PK); `user_id: int | None`; `game_id: int | None`; `ply` SmallInteger NOT
NULL (a plain column, never part of a foreign key, per D-01); `mover_color` String(5) NOT NULL;
`fen` String(120) NOT NULL; `arriving_move_uci` String(5) nullable; `phase` SmallInteger NOT
NULL; `source_played_at` `DateTime(timezone=True)` nullable; `ladder` JSONB NOT NULL with
`deferred=True`; `created_at` `DateTime(timezone=True)` NOT NULL, `server_default=func.now()`.
Table args:
`ForeignKeyConstraint(["game_id", "user_id"], ["games.id", "games.user_id"], ondelete="SET NULL", name="herring_pool_game_user_fkey")` (D-01 — `SET NULL`, deliberately not the codebase's
dominant `CASCADE`);
`UniqueConstraint("user_id", "game_id", "ply", name="uq_herring_pool_source")` (the SEED-120
identity triple, demoted to a generation-time dedup key);
`CheckConstraint("phase IN (0, 1, 2)", name="ck_herring_pool_phase")`;
`CheckConstraint("mover_color IN ('white', 'black')", name="ck_herring_pool_mover_color")`;
`CheckConstraint("jsonb_typeof(ladder) = 'array' AND jsonb_array_length(ladder) = 5", name="ck_herring_pool_ladder_shape")`;
`Index("ix_herring_pool_recency", "source_played_at", "id")`.

The ladder-shape CHECK is load-bearing, not decoration: it makes "every stored row has a complete
5-element array" a *write-time* structural invariant, so the serve-time query can call
`jsonb_array_elements` with no shape guard. That is the only safe way to satisfy the
total-operator rule documented in `answer_key_present`'s docstring — a `jsonb_typeof` guard
AND-ed with an array-length function in a WHERE clause is a live crash in this codebase, not a
style preference.

Document on the model, in the docstring:
- `ladder` element shape is exactly `{"move_uci": str, "cp": int | null, "mate": int | null}`,
  five entries, ordered best-first as Stockfish returned them, with `cp`/`mate` in **white POV**
  via the house `_score_to_cp_mate` convention — no new sign convention is introduced (D-16).
- `mover_color` is the side to move on the board the generator actually searched. It is stored
  rather than re-derived because this phase's whole design premise is that the generator's own
  board is authoritative (SEED-120 Pitfall 1: the `ply - 1` / `flaw_ply + 1` conventions in this
  codebase do not obviously reconcile). It must always equal `mover_color_for_ply(ply)`; the
  generator asserts that, so any future ply-indexing drift fails loudly at generation instead of
  silently serving a wrong-POV ladder.
- Never pass `None` for `ladder` — that writes `null::jsonb`, not SQL NULL
  (`project_asyncpg_jsonb_null_vs_sql_null`). `nullable=False` plus the shape CHECK makes this
  structurally impossible; the note exists so nobody relaxes either.
- `source_played_at` and `fen`/`arriving_move_uci` are deliberate denormalized copies so the row
  survives source-game deletion self-sufficiently (D-03) — recency ordering must not require a
  `games` join.
