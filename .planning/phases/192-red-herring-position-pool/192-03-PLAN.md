  <action>
Complete the generator. Everything below is additive to Plan 01's tracer version; do not rewrite
the parts that already work.

**Phase thirds (D-19).** Add `PHASE_CODES: dict[str, int] = {"opening": 0, "middlegame": 1, "endgame": 2}`.
When `--phase` is omitted, split `--n-positions` into three buckets and run the same per-bucket
scan for each phase code, giving the remainder to the first bucket. Each bucket has its own
independent target and its own independent shortfall — a bucket that comes up short must NOT
have its quota absorbed by another bucket, because the whole point of D-19's stratification is a
phase-balanced pool. Log the per-bucket target, stored, and shortfall.

**Oversampling.** Add `HERRING_OVERSAMPLE_FACTOR: int` — the multiple of the per-bucket target the
scan is willing to examine before giving up. The qualifying rate is unknown until the first run
and is expected to be lower in endgames, so a fixed factor with an explicit "gave up at N
candidates for phase X" log line is honest; silently returning a short bucket is not. Choose the
starting value from the Plan 01 SUMMARY's measured accept rate, and state the basis in the
constant's comment.

**Sampling implementation.** Order the frame deterministically and page through it — the frame is
large (prod: 3.3M/5.3M/2.7M candidates per phase) so it must never be materialized in one query.
Use a keyset scan over the `game_positions` composite PK `(user_id, game_id, ply)` with a
`LIMIT`-per-page, not `OFFSET` (offset degrades linearly on a table this size). Randomness is not
required for correctness; a deterministic keyset walk with a randomized starting key gives a
usable spread and makes a resumed run cheap. Document the choice in the module docstring.

**Resumable top-up (D-14, ROADMAP SC2).** Before scanning a bucket, count existing rows for that
phase code and target only the shortfall. Combined with `ON CONFLICT (user_id, game_id, ply) DO NOTHING`,
this makes a re-run a top-up rather than a restart. Commit every `HERRING_COMMIT_EVERY` accepted
rows rather than once at the end, so an interrupt leaves whole valid rows behind.

**Guest exclusion (D-02).** Confirm the frame joins `users` and requires `is_guest = false`. This
is enforced at generation time only, by design: users never become guests (only the reverse), and
once the FEN is on the row the puzzle is self-sufficient. Do NOT add a serve-time guest check —
that would put a join on the hot session-composition path to guard against something that cannot
happen.

**Runbook.** Extend the module docstring with a Rollout section stating:
- **D-11:** production is generated with local Stockfish against the prod DB over
  `bin/prod_db_tunnel.sh` (`--db prod`, port 15432). Never run on the prod server — CLAUDE.md's
  only sanctioned SSH-side operation is deploy — and never wired into the backend as a background
  tier. Zero prod CPU is consumed by the search.
- **D-13:** deploy the source swap first, then run the generator. The empty-pool window needs no
  new logic: `compose_session`'s cross-backfill already fills the shortfall from the SR pool and
  `waiting_count` degrades honestly. **Record the window's start and end timestamps in the phase
  SUMMARY** — guess-accuracy data collected during it is unusable, because with no herrings the
  "one critical move" guess is always correct, and it must be excluded from any later anti-tell
  analysis.
- **D-14:** one-shot with manual top-up on demand. No cron, no scheduler, no depletion
  monitoring. Nothing erodes the pool now that the source-game link nulls instead of cascading.
- Per-environment: game ids are not portable across databases, so each environment gets its own
  run. Dev has zero rows in the superseded candidate table, so this is what makes red herrings
  locally testable for the first time.

**Tests** in `tests/scripts/test_gen_red_herring_pool.py` (a new file; `tests/scripts/` already
hosts `test_gen_*` siblings). The engine call must be stubbed — these tests assert selection and
persistence logic, not Stockfish. Cover:
`test_generator_rejects_fewer_than_five_legal_moves` (assert the engine stub is never called);
`test_generator_loose_gate_boundary` (exactly at the band -> stored; one step beyond -> rejected);
`test_generator_rerun_tops_up_without_duplicates`;
`test_generator_splits_n_into_phase_thirds`;
`test_generator_excludes_guest_sourced_positions`;
`test_generator_dry_run_writes_nothing`.

gap between PV[0] and each of PV[1]..PV[4]. Aggregate into a histogram over the gap to PV[1] (the

**Pin `HERRING_LOOSE_BAND_ES` (D-15).** It must sit comfortably above the query-time tight gate
(`INACCURACY_DROP` = 0.05) so the gate stays retunable downward with zero re-analysis, and low
enough that the pool is not filled with rows no plausible threshold would ever admit. The ~0.10
anchor from D-15 is the starting hypothesis, not the answer — confirm or move it from the
measured PV[1] histogram and say which.

**Pin `HERRING_DEGENERATE_MIN_GAP_ES` (D-17)** in `app/services/train_pool.py`: the minimum
PV[0]-to-PV[4] expected-score gap a row must have to be *served*. This is the discriminator that
excludes dead-drawn and totally-winning positions where every legal move is fine — precisely what
MultiPV-5 buys over the rejected boolean-count design. It is a query-time bound by D-17, so it
stays retunable and we can later check whether it was too aggressive. Pick it from the measured
PV[4] histogram: a value that trims the visibly degenerate tail without cutting into the body of
genuine several-fine-moves positions.

**Record the basis.** Each constant's comment must name the measurement it came from (sample
size, phase breakdown, the histogram feature that decided it) and state that it is retunable
without re-analysis because the ladder is stored raw. The plan SUMMARY carries the full
histograms. A constant with a value but no recorded basis fails this task.

Also spot-check pool quality per 192-VALIDATION.md: sample about 10 stored rows, replay each FEN,
and confirm the stored ladder matches the board's intuition — that these genuinely read as
several-fine-moves positions. Record the outcome, including any row that did not.

measurement easier. D-16 forbids it: it would freeze the `LICHESS_K` conversion at generation
time, which is the exact pre-conversion `GameBestMove`'s model docstring prohibits, and it would
make both constants un-retunable — defeating the entire loose-generation / tight-query split.
