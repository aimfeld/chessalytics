### New `theme.ts` constants (replace `TRAIN_STREAK_FLAME_MINIMUM/MEDIUM/MAXIMUM`)

Locked recommendation (Claude's Discretion item, per CONTEXT.md and RESEARCH.md `## Pip Colour Banding`) — reuse the same 3 brand colors the flame ladder already used, repurposed as **fill bands over the 7-pip count** rather than 3 discrete named states:

```typescript
// frontend/src/lib/theme.ts — replaces TRAIN_STREAK_FLAME_MINIMUM/MEDIUM/MAXIMUM
// (Phase 193 D-01 — 7-segment pip meter, banded by shield_level, not by a 3-state enum)
export const TRAIN_SHIELD_PIP_LOW = 'oklch(0.55 0.03 85)';    // 1-2 pips filled: ember, danger zone
```

**Banding thresholds** (locked): `shield_level <= 2` → `TRAIN_SHIELD_PIP_LOW`; `3 <= shield_level <= 5` → `TRAIN_SHIELD_PIP_MEDIUM`; `shield_level >= 6` → `TRAIN_SHIELD_PIP_HIGH`. **All filled pips share ONE color** (the current band's color) — this is a meter, not a per-pip gradient. Do not color pip 1 differently from pip 5; the fill color communicates "which band is the shield currently in," the pip *count* communicates the exact level.

Accent reserved for: **the shield pip meter's filled segments, and nothing else in this delta.** The "N-session streak" label text, the "This week" line, and the reset notice all render in the existing plain foreground/muted-foreground tones — none of them take the accent color.

## "This Week" Line — Decision

**Locked: KEEP the line, reworded only at the backend data-source level, not at the copy level.**

The frontend's `thisWeekHint(completed, required)` function in `TrainProgressRow.tsx` already handles both cases correctly (`required === null` → "This week: N sessions"; `required !== null` → "This week: N of M sessions") and needs **zero code changes**. What changes is what `current_week_required` *means*: today it is `required_sessions_per_week`'s special-cased value (deleted this phase); after this phase it is a plain `popcount(weekday_mask)` — "how many days are scheduled this week," finally honest, per RESEARCH.md `## Current-Week Hint`.

**Rationale, weighed against D-02:** D-02 puts *intensity* in the session count ("a 7-day/week user's count races, a 1-day/week user's crawls" per the phase Goal). The "This week" line is a complementary, narrower-scope signal — it answers "am I on pace *this specific week*," which the all-time count cannot show on its own. Dropping the line would remove the only in-week pacing cue and leave the user with nothing but the lifetime count and the shield; keeping it costs zero new frontend code and becomes MORE honest (no more 1→6 special-case cliff). Locked: keep.

## Shield Pip Meter — Component Contract

Replaces the single `lucide-react` `Flame` icon in `TrainProgressRow.tsx` (currently lines 8, 19-23, 64-68).

### Geometry
- **Exactly 7 pips**, laid out horizontally, `flex items-center gap-1` (4px gap, the `xs` spacing token).
- Each pip is a `size-2.5` (10px) circle: `rounded-full`.
- **Filled pip:** solid background fill in the current band color (`TRAIN_SHIELD_PIP_LOW/MEDIUM/HIGH`), no border.
- **Empty pip:** transparent fill, `border border-muted-foreground/50` (a visible ring, not an invisible gap) — this shape difference (solid disc vs. hollow ring) is what makes the filled/empty distinction survive a greyscale render, per the accessibility requirement (colour is never the only signal).
- Total footprint: `7 × 10px + 6 × 4px = 94px` wide, `10px` tall — fits inside the existing `flex flex-wrap items-center gap-6` stats row at any viewport ≥ 360px with no special-casing; on a genuinely cramped width the row's existing `flex-wrap` behavior (already relied on for the mastered/parked spans) lets the meter drop to its own line like any other row item. No additional responsive logic is needed — do not add a `sm:`/sub-7-pip mobile variant.

### Fill logic
```tsx
function pipBandColor(shieldLevel: number): string {
  if (shieldLevel <= 2) return TRAIN_SHIELD_PIP_LOW;
  if (shieldLevel <= 5) return TRAIN_SHIELD_PIP_MEDIUM;
  return TRAIN_SHIELD_PIP_HIGH;
}
```
Pips `0..shieldLevel-1` (left to right) render filled in `pipBandColor(shieldLevel)`; the rest render empty. At `shieldLevel === 0`, all 7 render empty (see `## Streak-Death State` — this is the same visual regardless of *why* the shield is at 0, the reset notice is the thing that distinguishes "just lost it" from "never had one").

### Accessibility contract
- Container: `role="img"` with `aria-label={\`Shield: ${shieldLevel} of 7\`}` — this is the ONE accessible name a screen reader announces for the whole meter (matches the phase brief's example, "shield: 5 of 7").
- Container also carries `data-testid="train-shield-meter"` and a `data-filled-count={shieldLevel}` attribute — the cheapest possible test hook for "assert the filled-pip count" without parsing children.
- Individual pips: `aria-hidden="true"` (the container's `role="img"`/`aria-label` already speaks for the whole group — a screen reader must not also enumerate 7 child spans) and `data-testid="train-shield-pip"` (repeated on all 7, Testing Library's `getAllByTestId` supports duplicates) with a `data-filled="true"|"false"` attribute each, so a test can do `getAllByTestId('train-shield-pip').filter(el => el.dataset.filled === 'true').length` as a second, independent assertion path from the container's `data-filled-count`.

### Sketch (illustrative — planner/executor write the real component)
```tsx
const SHIELD_PIP_COUNT = 7;

function pipBandColor(shieldLevel: number): string {
  if (shieldLevel <= 2) return TRAIN_SHIELD_PIP_LOW;
  if (shieldLevel <= 5) return TRAIN_SHIELD_PIP_MEDIUM;
  return TRAIN_SHIELD_PIP_HIGH;
}

function ShieldMeter({ shieldLevel }: { shieldLevel: number }): ReactElement {
  const color = pipBandColor(shieldLevel);
  return (
    <div
      role="img"
      aria-label={`Shield: ${shieldLevel} of ${SHIELD_PIP_COUNT}`}
      data-testid="train-shield-meter"
      data-filled-count={shieldLevel}
      className="flex items-center gap-1"
    >
      {Array.from({ length: SHIELD_PIP_COUNT }, (_, i) => {
        const filled = i < shieldLevel;
        return (
          <span
            key={i}
            aria-hidden="true"
            data-testid="train-shield-pip"
            data-filled={filled}
            className="size-2.5 rounded-full border border-muted-foreground/50"
            style={filled ? { backgroundColor: color, borderColor: color } : undefined}
          />
        );
      })}
    </div>
  );
}
```

## Streak-Death State (D-04)

When `shield_level === 0`:
1. **Meter:** all 7 pips render empty (hollow ring, no fill) — the same visual `pipBandColor` logic already produces this for free (`shieldLevel <= 2` band would apply if any were filled, but 0 filled means the loop simply never sets a fill).
2. **Count label:** renders `"0-session streak"` — NOT hidden. This is a deliberate reversal of the old `Flame`-era behavior (`data.settled_streak_weeks >= 1 &&` guard, which hid the text entirely at 0). D-04 explicitly requires "a 0 count," and always-rendering the label removes a conditional, simplifying the component.
3. **Notice:** the persistent reset notice (`"Streak reset — complete a session to start a new one."`) renders **only when the state-derived reset discriminant is true** (the renamed `streak_lost_last_week` → `streak_reset_notice` field per RESEARCH.md), never merely because `shield_level === 0`. This distinguishes "the user just lost a real streak" from "this is a brand-new user who never had one" — a brand-new user sees an empty meter and `"0-session streak"` with NO notice; a user who just dropped to 0 sees the same meter/label PLUS the notice line. Both cases are visually identical except for that one extra line — intentional, not a gap.
4. **No drain animation.** D-04 explicitly rejects an animated transition (would need a "has the user seen this" flag plus `prefers-reduced-motion` handling, out of scope). The meter simply renders its current state on each load — a page reload after the drop shows the same empty-meter + 0-count + notice trio, by construction (state-derived, not event-derived).
5. **Placement:** unchanged from the existing layout — stats row (shield meter + streak label + mastered + parked) → "This week" line → reset notice, in that order, last.

## Nav Badge Visibility (D-09 / D-10)

**Both sites in scope, per CLAUDE.md's "apply to both desktop and mobile" rule:**
- `frontend/src/App.tsx:162` (`NavHeader`, desktop) + the badge render block at `:223-240`
- `frontend/src/App.tsx:354` (`MobileBottomBar`, mobile) + the badge render block at `:408-415`

### Contract
- **No visual change to the badge itself** — same red pill, same `NAV_BADGE_MAX_DISPLAY` overflow cap ("99+" style), same number sourced from `waiting_count`. This phase changes only the **show/hide condition**, not the badge's appearance.
- **Old condition (both sites):** `to === '/train' && trainWaitingCount > 0`
- **New condition (both sites):** `to === '/train' && trainWaitingCount > 0 && (trainProgressQuery.data?.badge_visible ?? false)`
  - `badge_visible` is a new server-computed boolean on `TrainProgressResponse` (RESEARCH.md `## Badge Visibility Signal`) — the frontend has zero knowledge of `weekday_mask` today and must not attempt client-side day-of-week math (Pitfall 4 in RESEARCH.md). Do not add a second query or duplicate the mask-parsing logic client-side.
  - Semantics: `badge_visible = waiting_count > 0 AND (today is a scheduled day per weekday_mask OR an already-open session has unsolved puzzles left)` — D-09 (scheduled-day gating) OR'd with D-10 (an in-flight session's badge survives into an off-day so the user isn't left with no cue to finish it).
- **AMENDMENT (193 UAT, 2026-07-28) — cache freshness.** `badge_visible`/`waiting_count` come from the cached `TRAIN_PROGRESS_QUERY_KEY`, which nothing on the Train page invalidated. Solving the LAST puzzle of a session is exactly the tick that flips the session row to `'completed'` server-side (dropping `waiting_count` to 0) and settles the streak/shield, so `useTrainSession`'s solve mutation now invalidates that key when the solve response carries `session_complete: true`. Without it the badge dot survived session completion until a page reload. Mid-session solves deliberately do NOT invalidate — the badge is boolean, so nothing it shows changes until the session completes.
- **No-op for the two day-agnostic masks** (`weekday_mask === 0` and the `ALL_WEEKDAYS_MASK` default) — every day is scheduled under both, so `badge_visible` collapses to the old `waiting_count > 0` behavior for the vast majority of users who haven't deliberately narrowed their schedule. Only users with a narrowed mask see quieter off-days. This means the change is low-risk for the default user and should not require new default-mask test coverage beyond confirming the collapse.
