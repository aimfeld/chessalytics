<objective>
Make the two provider caches correct and correctly sized: LRU instead of FIFO, merge instead
of overwrite, capacities that hold a full search's working set, and one shared `fen|elo`
policy cache between the analysis board's Maia ELO-ladder chart and the engine's root policy
call.

Purpose: today both caches cap at 256 while a single 400-node analysis search touches 352-386
distinct FENs, so a search thrashes its own cache before cross-search reuse is even possible;
both evict FIFO, dropping the root and upper tree that a PUCT selection walk re-descends
most; and `cacheGrades` replaces the whole per-FEN map, so a same-FEN request with a shifted
candidate set destroys the prior entry. This is also the substrate that makes Phase 196's
disagreement re-run a cache replay rather than a recompute.

Output: `GRADE_CACHE_MAX` at 1024, a new shared `maiaPolicyCache.ts` module at 2048 backing
both `maiaQueue` and a write-through from `useMaiaEngine`, LRU touch-on-hit in both caches, a
merging `cacheGrades`, the CACHE-04 finding recorded at the read gate, and retention notes on
the two deliberately-kept removal candidates.
</objective>

<resolved_decisions>
Two decisions RESEARCH.md left open are settled here; do not re-open them.

**Cache capacities.** `GRADE_CACHE_MAX` 256 -> **1024**: the measured distinct-FEN ceiling of
a 400-node analysis search is 386, and 1024 is the next power of two above roughly 2.6x that,
giving one full search plus about 1.6 searches of navigation history. `MAIA_POLICY_CACHE_MAX`
(replacing `maiaQueue.ts`'s `MAIA_CACHE_MAX` 256) -> **2048**: the engine calls
`providers.policy(leaf.fen, budget.elo[leaf.side], leaf.side)`, and side-to-move is fixed per
FEN, so the engine contributes at most one entry per distinct FEN (<=386); the chart's
write-through contributes 21 entries per navigated position (`MAIA_ELO_LADDER` is 600..2600
step 100). 2048 - 386 leaves roughly 79 navigated positions of chart history. At an estimated
~2 KB per entry (a `Record<string, number>` over ~30-40 legal moves) the cap costs ~4 MB
against Maia's ~226 MB heap. `useMaiaEngine.ts`'s own `MAIA_CACHE_MAX = 256` is deliberately
left at 256 — that is the chart's 21-rung bundle cache, not a provider cache, and CACHE-01
scopes to the two provider caches.

**CACHE-05 shape.** Neither of RESEARCH.md's options (a) or (b): a new module-level shared
UCI-keyed `fen|elo` cache that `maiaQueue` owns as its cache and `useMaiaEngine`
**write-throughs** into. Option (a)'s read-through is wrong because
`MoveCurvePoint.moveProbabilities` is SAN-keyed (`useMaiaEngine.ts:64-67,112-115`), so slicing
a rung out of `perElo` would force the engine back into per-move `sanToUci` — reintroducing
exactly the cost Plan 01 deletes. The write-through costs one extra `maskAndSoftmaxUci` call
per rung (~0.04-0.08 ms x 21 rungs) against ~130 ms saved per avoided re-inference. The
ordering race RESEARCH.md flagged is resolved by construction: the shared cache is best-effort,
and a miss is byte-identical to today's behavior, so ordering can change only the magnitude of
the saving, never correctness.

**CACHE-04.** Settled by RESEARCH.md § Pattern 5's direct measurement: do NOT implement
partial-hit grading. Keep the all-or-nothing read, close only the merge gap, and record the
finding in-code.
</resolved_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| (no new boundary) | No network surface, no user-supplied input parsing, no auth/session handling, no persistence. All caches are in-memory, single-tab, ephemeral, and hold only chess evaluations derived from positions the user is already viewing. |
| cache key -> cached value | The one boundary that matters in this plan: a key that under-specifies its inputs serves a value computed for different inputs. This is a correctness and isolation concern, not a confidentiality one — but it is the real risk here and the plan's design decisions are shaped by it. |
| module-scoped singleton -> multiple consumers | New in this plan. The policy cache outlives any single `createMaiaQueue()` instance and is written by a React hook and read by the search orchestrator. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-194-07 | Tampering | Policy cache key completeness (`maiaPolicyCache.ts`) | high | mitigate | `elo` is structurally inseparable from the key: the `${fen}\|${elo}` template lives inside the module and `getCachedPolicy`/`setCachedPolicy` take `fen` and `elo` as separate required parameters, so no caller can construct a FEN-only key. A dedicated test asserts the same FEN at two different rungs yields two independent values. Serving one rung's human-move distribution for another would silently change every practical score the engine produces. |
| T-194-08 | Tampering | Grade cache all-or-nothing read gate (`workerPool.ts`) | high | mitigate | Partial-hit grading is prohibited and the reason is recorded in-code with the measured cp deltas: a `searchmoves` subset produces a different cp at the same reported depth, so mixing subset-graded and full-set-graded values under one `(fen, depth)` key would inject nondeterminism and violate ENGINE-07. The `candidateUcis.every(...)` gate stays the only read path, and a test asserts a one-UCI-short entry re-grades the full requested set. |
| T-194-09 | Denial of Service | Cache memory growth on low-memory mobile devices | medium | mitigate | Both caps are hard-bounded and evict on insert; the chosen values (1024 and 2048) are derived from a measured working set rather than raised open-endedly, and the estimated ceiling is ~4 MB against Maia's ~226 MB heap. `useMaiaEngine`'s 256-bundle cap is deliberately not raised, so the 21-rung bundle cache does not grow alongside. |
| T-194-10 | Information Disclosure | Module-scoped singleton persisting across component unmounts | low | accept | The cached data is derived from positions the same user is already viewing in the same tab; there is no multi-user or cross-origin dimension in a client-side SPA cache, and nothing is written to storage. Test isolation (not confidentiality) is the practical concern, and `clearMaiaPolicyCache()` addresses it. |
| T-194-11 | Spoofing / Repudiation / Elevation | — | low | accept | Not applicable: no identity, no session, no privileged operation in scope. Stated explicitly rather than omitted, per ASVS L1 scoping. |
