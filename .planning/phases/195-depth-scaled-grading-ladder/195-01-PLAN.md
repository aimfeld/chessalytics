<objective>
Ship the depth-scaled grading mechanism end-to-end — the pure `gradingLadder.ts` module, the
depth resolved in `mctsSearch.dispatchExpansion`, the 4th `grade()` parameter, the single
shared `go`-string builder, and the D-06 watchdog that replaces the removed movetime cap —
with the ladder table itself deliberately provisional (flat, root rung only) so this plan
changes delivered grading depth by exactly zero.

That is the point. LADDER-01 forbids shipping the 3-position 14/12/10 pilot as the ladder, so
the rungs stay undetermined until Plan 05's widened A/B run selects them. Landing the plumbing
at a flat 14 makes it byte-equivalent in delivered depth to the pre-phase
`GRADING_TARGET_DEPTH = 14`, so any strength or wall-clock change measured later is
attributable to the measured rungs and not to this refactor. Plan 05 replaces the table with
a one-line data-driven edit.

Purpose: LADDER-02's mechanism and LADDER-04's movetime resolution, with the ladder's VALUES
held open for the data.
Output: `frontend/src/lib/engine/gradingLadder.ts` plus its test, a depth-carrying
`WorkerPool.grade`, a rung-resolving `dispatchExpansion`, and a host-side watchdog.
</objective>

<assumption_delta_decision>
The phase-scope check fires `chosen` on two nouns at once, and they resolve the same way.

**Noun 1 — grading depth.** `GRADING_TARGET_DEPTH`, a flat constant, becomes
`gradingDepthForTreeDepth(d)`, a parameter of tree depth. A configuration value has become a
modelling decision: "how deep to grade" is now a property of a node's position in the search
tree, not a property of the build.
**Decision: promote.** The depth-indexed lookup becomes the primary representation and the
flat constant is demoted to one of its entries (`GRADING_ROOT_DEPTH === GRADING_DEPTH_LADDER[0]`,
D-02's pinned root). No flat `GRADING_TARGET_DEPTH` survives anywhere in the engine's own
grading path — keeping one alongside would let a caller silently opt out of the ladder.

**Noun 2 — grade-cache identity.** The cache key goes from the single noun `fen` to the
composite `(fen, grading depth)`. A grade is only meaningful paired with the depth that
produced it.
**Decision: promote** (implemented in Plan 03, not here). The composite key becomes THE key;
the `fen`-only lookup is demoted to "the composite key at the root rung" and no `fen`-only
read path is retained. Retaining one alongside is precisely SEED-126's landmine rule 2 — a
deeper cached grade satisfying a shallower request — and its failure mode is silent.

**The companion invariant test is a real task, not a suggestion:** Plan 03 Task 1's ENGINE-07
"a deeper cached grade never satisfies a shallower request, regardless of visit order" test IS
this identity model's invariant, written both directions.

What would force a later re-visit: if D-04's one-shared-ladder decision is reversed and the
analysis board gets its own ladder, the cache key must widen again — the `(fen, depth)` key
already makes two ladders safe to coexist, which is why D-04 rates reversible.
</assumption_delta_decision>
