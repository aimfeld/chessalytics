  <action>
Create `reports/grading-ladder/` and write `accept-rule.md`. It is a decision contract, not a
narrative: every number in it must be stated before the run, and every step must be executable
by someone reading only this file plus the TSVs.

It must fix, in this order:

**1. Run parameters.** Reference depth 14 (D-02 pins the root rung at 14 and takes it out of
the A/B entirely, so every number isolates the subtree rungs). Measured depth set 14, 12, 10,
8, 6 (D-03). Position set `scripts/data/grading-ladder-fens.txt`. Budget 50 nodes, 8 plies,
matching the shipped bot. State that the same reference depth is used for both stages.

**2. Which column decides.** `same_full_order` is the headline agreement measure.
`mean_abs_score_diff` is read as a tie-noise magnitude, not an error rate. `same_top_move` on
its own is NOT a decision input and must never be quoted without its row's
`reference_top2_gap` beside it.

**3. The numeric noise floor and the exact comparison.** The floor is 0.007, derived from the
measured depth-16-vs-depth-14 disagreement of 0.0067 — a pair of depths nobody claims differ in
quality, so a disagreement at or below that magnitude is indistinguishable from the ladder's own
noise. The comparison is: parse the TSV's fixed 6-decimal `mean_abs_score_diff` string as a
float and test `<= 0.007`, inclusive at the floor. State explicitly that no rounding is applied
at any point, so no half-up / half-to-even / ceil / floor / truncate choice arises. State that
grades underlying those scores are keyed by `parsed.pv[0]` and never by the `multipv` rank
field, and that only `bound === 'exact'` info lines are accepted — the same convention in
`workerPool.ts`, `calibration-providers.mjs`, and the A/B script alike.

**4. Stage A — the flat-depth frontier.** A measured flat depth `d` is ACCEPTABLE iff, across
the whole position set: the mean of its `mean_abs_score_diff` values is at or below the noise
floor, AND `same_full_order` is true on at least 90% of positions, AND every position where
`same_full_order` is false has a `reference_top2_gap` strictly below 0.010 — i.e. every
disagreement flipped a tie rather than a decision. Define `d*` as the SHALLOWEST acceptable
depth. If no depth other than 14 is acceptable, `d*` is 14 and the phase ships a flat ladder
and says so.

**5. The bridge from flat measurements to ladder rungs, stated as an argument not an
assumption.** A flat-`d` run grades EVERY node at `d`, so it bounds the damage of using `d`
anywhere in the tree. A ladder that uses `d` only below the root, with strictly deeper rungs
above it, is therefore at least as faithful as the flat-`d` run it was derived from. This is why
Stage A's flat frontier is a legitimate source of candidate rungs — and it is also exactly why
Stage B exists: the bound is an argument, and LADDER-05 requires the shipped ladder itself to be
measured, not inferred.

**6. Stage B — the three candidate ladders, constructed mechanically.** Let `m` be the
shallowest acceptable depth strictly greater than `d*`, or 14 if there is none. Then:
`L-aggressive` = table `[14]` with floor `d*`; `L-graded` = table `[14, m]` with floor `d*`;
`L-conservative` = table `[14, 14, m]` with floor `d*`. Each is run in the A/B script's ladder
mode against the flat-14 reference over the same position set at 50 nodes.

**7. Final selection and tie-break.** Among the candidate ladders that satisfy the same
predicate as step 4 (applied to their ladder-mode rows against the flat-14 reference), ship the
one with the lowest total `wall_ms` summed across positions. On an exact wall-clock tie, ship
the more conservative table (the one with more entries before the floor). If NO candidate
passes, ship `L-conservative` with `m = 14` and record in the report that the ladder is
conservative because the aggressive candidates failed the pre-declared rule — do not relax the
rule.

**8. The D-07 decision rule.** The run reports, per `(fen, depth)`, whether a hash-warm grade
differs from a hash-cleared grade at the same position and depth, via the harness's
`hash_probes` / `hash_probes_divergent` / `hash_probe_max_abs_cp` /
`hash_probe_mean_abs_score_diff` columns. The last of those is expressed in EXPECTED-SCORE units,
computed through the same `evalToExpectedScore` conversion the engine's own leaf scoring uses, so
it is directly comparable to the 0.007 noise floor defined in step 3 — the same units as
`mean_abs_score_diff`. If `hash_probes_divergent` is 0 across the run, record the question closed
and change nothing. If it is non-zero but `hash_probe_mean_abs_score_diff` stays at or below the
noise floor, record the divergence with its distribution, keep the browser's warm hash (the
cross-call reuse it was built to exploit is worth more than a difference the harness cannot
distinguish from noise), and close the question. If any pass's
`hash_probe_mean_abs_score_diff` exceeds the floor, that is a measured second determinism hole:
escalate it to the operator at Plan 05's checkpoint as a decision rather than resolving it
silently either way.

Note that a probed run costs roughly ten percent more wall clock per probed call, so the D-07
figures must come from a probe run and the LADDER-05 wall-clock figures from an unprobed one.

**9. What the LADDER-05 report must contain.** Wall clock and the three agreement measures for
the shipped ladder against flat-14 at 50 nodes over the full position set; the same at 400 nodes
over the declared 6-position subset, with the subset size stated in the report text rather than
left implicit; the per-depth Stage A frontier table; the D-07 finding; and the paths of every
committed TSV the numbers came from.

Do not name `[14, 12, 12, 10]` or any other specific ladder as the expected answer.
  </action>
