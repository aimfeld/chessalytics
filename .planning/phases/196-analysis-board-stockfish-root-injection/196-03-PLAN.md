<planner_correction>
**RESEARCH.md's recommended instrumentation point needs one adjustment, and here is why.**

`196-RESEARCH.md` § "Don't Hand-Roll" recommends adding hit/miss counters to `WorkerPool.grade`'s two
return branches and exposing `cacheStats()`. That is correct for the browser. But it does not by itself
make the harness able to measure anything: `createWorkerPool()` calls `new Worker(ENGINE_PATH)` with a
browser Web Worker, and the Phase 195 Node harness deliberately uses its own `createDepthPool`
(`scripts/engine-grading-depth-ab.mjs:380`) built on `spawnStockfish()` child processes — which has
**no grade cache at all**. A `cacheStats()` counter on `WorkerPool` would therefore be unreachable from
Node, and a harness that re-implements the read gate would be measuring a mirror, not shipped code.

**Resolution:** extract the cache that already exists in `workerPool.ts` (its `cache` Map, `cacheKey`,
`cacheGrades`, and `grade()`'s read gate) into an exported `createGradeCache()` factory in that same
file, instrument the counters inside it, and have BOTH `createWorkerPool`'s `grade()` and the harness's
Node grade provider use it. This keeps `cacheStats()` on the `WorkerPool` interface as RESEARCH
recommends, AND gives the harness the genuine shipped read gate, keying, LRU touch and merge
semantics. It also removes a second measurement error the alternative would have caused: a cacheless
harness would overstate the re-run's wall clock, because the browser's re-run does have the cache.

The extraction is behaviour-preserving and is guarded by the Phase 194 `describe('createWorkerPool: grade cache (Phase 194 CACHE-01..04)', ...)`
block already in `workerPool.test.ts` (~:695+), which must pass unmodified.
</planner_correction>

  <behavior>
    - A fresh cache reports `{ hits: 0, misses: 0 }`.
    - A `grade()` for a novel `(fen, depth)` increments `misses` by 1 and leaves `hits` at 0.
    - A repeat `grade()` for the same `(fen, depth)` with a candidate subset already present increments `hits` by 1 and leaves `misses` unchanged.
    - A repeat `grade()` for the same `fen` at a DIFFERENT depth increments `misses` (LADDER-03: a deeper cached grade never satisfies a shallower request).
    - A repeat `grade()` for the same `(fen, depth)` requesting a UCI the cached entry lacks increments `misses` (the all-or-nothing read, CACHE-04).
    - `resetCacheStats()` returns both counters to 0 without evicting any cached entry — a subsequent repeat request still reports a hit.
    - The counters are cache OUTCOME counters, not Stockfish-dispatch counters: the early returns for an empty `candidateUcis` list and for an already-aborted signal happen BEFORE the cache is consulted and increment neither.
  </behavior>
