### 1. WR-01 stale-render race in Analysis.tsx's per-position injection latch

expected: extraRootMoves for a newly-navigated position must be derived only from that position's own settled Stockfish pvLines and that position's own flawChessEngine.rankedLines — never from the previous position's stale hook outputs — and the latch must never lock in a spurious result.

how to test: On `/analysis` with the standalone Stockfish switch ON and an out-of-mass disagreement
position loaded, click through move history so two adjacent positions share side-to-move parity and
at least one Stockfish PV move from the OLD position is also legal at the NEW position (e.g. two
branches diverging two plies apart). Watch whether the FlawChess search for the NEW position gets an
`extraRootMoves` injection derived from the OLD position's data, and whether the per-position latch
then permanently suppresses any later correct re-evaluation for that position.

why human: This is a React effect-ordering race (`196-REVIEW.md` WR-01, independently re-confirmed
in `196-VERIFICATION.md`). `Analysis.tsx`'s disagreement effect and `useFlawChessEngine`'s own
FEN-reset effect fire in the SAME passive-effect flush on a position change, but a `setState` in one
effect does not retroactively update closures another effect in the same flush already captured. So
the disagreement effect can read stale `rankedLines`/`pvLines` while `position` is already the new
value. Bears on INJECT-03/INJECT-04.

FIXED since this UAT file was written — commit `eebc6d6a` (`/gsd-code-review 196 --fix`).
`useStockfishEngine` and `useFlawChessEngine` now expose `currentFen`, set in the same effect as
their line-data resets, and `Analysis.tsx`'s root-injection effect bails unless BOTH hooks'
`currentFen === position`. A new regression test was added that defers the mock's data update until
after the position-changing render (the old test at ~line 2087 pre-seeded it, which is why it never
caught this).

The fix was proven load-bearing by an independent revert-then-restore, run by the orchestrator rather
than taken from the fixer's report: removing ONLY the guard makes the new test fail with the exact
bug signature — `AssertionError: expected [ 'e2e4', 'g1f3' ] to deeply equal []` — and restoring it
makes the test pass. Full gate at the fixed tip: `tsc -b`, `lint`, `knip` clean, 2956/2956 tests.

what remains for you: confirm the fix holds in a real browser, where genuine async hook timing,
real Stockfish/Maia workers, and real navigation speed all apply — none of which jsdom reproduces.
The decision of whether to fix is already settled; this is confirmation only.
