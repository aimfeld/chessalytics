**1. Write `reports/leaf-wdl/elo-conditioning.md`** — LEAF-05's answer as a standing design
argument, not a changelog entry. It must contain:

- **The question, stated fairly.** Is an ELO-conditioned leaf value more correct for a
  practical-score engine, or does it double-count the human modelling the expectimax averaging
  already does?
- **The answer: more correct, not double-counting.** Use the two-horizons framing. The policy head
  models human play across the EXPLICIT tree (plies 0 through k, via `backupExpectation`'s
  prior-weighted average); the value head models the TAIL (ply k onward). Today's tail is
  `sigmoid(Stockfish eval)` — perfect play — so the engine has a skill discontinuity at the leaf:
  human priors for k plies, then suddenly optimal play. An ELO-conditioned WDL leaf removes that
  discontinuity and is more faithful to "expected score at your ELO". The double-counting objection
  would only hold if both heads modelled the same plies, which they do not. Reject it on that
  ground, explicitly, and not on the ground that the effect is small.
- **The locked consequence.** The leaf value uses exactly the ELO the `policy()` call already
  requested, single-sourced from that same inference — never a second `eloInputs` rung. State the
  economics as the reason this is a CONSTRAINT rather than a preference: a Maia inference measures
  roughly 123.5 ms and a second ELO rung adds roughly 100 ms (batch of two measures roughly
  223.6 ms), against roughly 82 ms for the whole batched depth-10 grade being eliminated. Any design
  that adds even one extra inference per expansion is a net wall-clock loss that defeats the phase.
  Cite SEED-126's Appendix as the source of those figures.
- **The rejected alternative.** A fixed "quasi-objective" high rung (for example 2600) was
  considered and is rejected on both counts: it loses the argument above AND costs the second rung.
- **No live ambiguity today.** Both production callers pass a symmetric per-side ELO
  (`useFlawChessEngine.ts` and `selectBotMove.ts`), so there is one ELO per search regardless of
  whose turn a node is. Note that if asymmetric self/opponent ELO ever ships, this question reopens,
  because a mover-conditioned tail would model a strong-self/weak-opponent gap inconsistently
  depending on whose turn the leaf is.
- **The boundary and precision facts** (these are acceptance criteria, write them explicitly):
  `MAIA_ELO_LADDER` spans 600 to 2600 in 100-point steps, so state what happens to a search ELO
  outside that range and what the consequence for the leaf value is; and state, from `eloToInput`'s
  own contract, whether `budget.elo[side]` reaches the model as a continuous float or is snapped to
  a ladder rung, and therefore whether the leaf value reads the WDL for the exact requested ELO.
  If reading `eloToInput` leaves genuine doubt about calibration fidelity at an off-rung value, say
  so plainly as an open assumption rather than asserting confidence.
- **What this phase measured but did not act on.** Cross-reference the D-04 per-rung
  `practicalScore` spread from `reports/leaf-wdl/report.md`: Maia's WDL is per-ELO and low rungs
  compress toward 0.5, so the spread of leaf values now varies with the search ELO in a way the
  ELO-agnostic lichess logistic never did. Name the downstream consumers that read absolute spreads
  and state that this phase deliberately retunes none of them.
