`## 1. The determinism requirement` — restate the ENGINE-07 scope exactly as `mctsSearch.ts`'s
module header states it: output is deterministic PER concurrency level; repeated runs at the same
`budget.concurrency` are bit-identical regardless of provider resolution jitter; different
concurrency levels may legitimately build different trees and a c=1 versus c=2 difference is NOT a
bug and must not be equalised. Nothing stronger is being promised, and nothing weaker is
acceptable.

`## 2. The commit-versus-resolution argument` — D-04's derivation, written as a proof sketch, not
a design note. This is the phase's intellectual deliverable and it must appear verbatim in
substance: bit-identity at fixed concurrency requires that the tree state and pending set visible
to selection number n be a deterministic function of n alone. If a dispatch slot frees on provider
RESOLUTION, then which expansions are resolved-but-uncommitted at selection n depends on arrival
jitter, so the selection input is jitter-dependent and bit-identity is lost outright. If a slot
frees on COMMIT, and commits are strictly in dispatch order, then selection n always sees exactly
commits 1 through n minus c applied, with the rest pending — deterministic by construction, and a
strict generalisation of what the current order-preserving batch resolution already gives.
Then answer SEED-127's worry that this reintroduces head-of-line blocking: it is a variance term,
not a mean term. In steady state a window of width c sustains the minimum of 1/P and c/(P+G)
expansions per second against the round loop's c/(cP+G) — exactly the U-04 win. Dispatch
continuity, not apply-order freedom, is what buys the throughput; head-of-line cost appears only
under heterogeneous latencies and is bounded by the spread, not by the mean.

`## 3. The throughput model` — U-04's algebra, citing the MEASURED P and G from
`reports/continuous-dispatch/report.md` sections 1 and 2 rather than the pre-measurement estimate.
Include U-04's counter-intuitive direction: a faster policy narrows the gap between P and G/c and
makes the overlap win bigger, so the WASM harness is the pessimistic environment. Label the ceiling
as a model, not a measurement.

`## 4. The mechanism` — the concrete shape, with the reasoning for each choice:
  - Commit window: a fixed-size ring buffer of length `budget.concurrency`, indexed by dispatch
    sequence modulo that length, drained strictly in commit-sequence order. Chosen over a map or a
    min-heap because the window can never hold more than `concurrency` outstanding dispatches by
    construction — a structure sized to the true upper bound makes unbounded growth from a future
    bug structurally impossible. Stays inside `mctsSearch.ts`; no new module.
  - Wait mechanism: a single manual wake signal, one shared promise replaced on every wake, with
    exactly ONE handler attached to each dispatched promise at dispatch time. Explicitly NOT a race
    over a mutating promise set: each such call attaches a fresh subscriber to every still-pending
    promise, so over a long search a slow promise accumulates dozens of dangling subscriptions.
    State the hard requirement plainly — nothing in the wait mechanism may leak arrival order into
    selection, and the wake signal satisfies it because it carries no identity, only the fact that
    SOMETHING settled; which commit becomes visible is decided solely by the commit sequence.
  - State the eight statement-by-statement changes from RESEARCH.md's mechanical-delta section, so
    a reviewer can check the design against the diff that will follow.

`## 5. Consequences for the four renegotiated invariants` — one subsection each:
  - `selectPath` returning null is disambiguated by in-flight count (D-05): null with work in
    flight means the tree is saturated, so await the next commit and retry; null with nothing in
    flight means the tree is genuinely fully searched, so break with today's WR-05 semantics, which
    is not budget exhaustion by itself. State that `isPending` must clear at COMMIT and never at
    resolution, or a later selection can re-pick a node whose result is still queued.
  - Node-budget accounting (D-06): the guard becomes committed-nodes plus in-flight against
    `budget.maxNodes`, preserving today's conservatism. The rare WR-04 under-dispatch when a
    dispatched expansion turns out degenerate is preserved deliberately, not fixed — fixing it here
    would be an unattributed strength change riding along with the rewrite.
  - Early stop and abort (D-07): stop dispatching and discard uncommitted results; do not drain.
    This preserves today's semantics exactly, and it falls out of the mechanism rather than being a
    special case — nothing anywhere awaits all outstanding promises.
  - Stop rule (D-08): structurally unchanged, still firing once per applied expansion in a strictly
    ordered sequence, but WHICH nodes get selected changes, so the rolling stable-check counter
    fires at different node counts. That number is published as a calibration input, not tuned here.

`## 6. What is genuinely new exposure` — two items, named as new rather than inherited:
  - A never-settling provider promise. Today the batch barrier already hangs the whole round, so
    the failure mode exists; a longer-lived window widens the exposure. The mechanism must contain
    no wait-for-all step anywhere, and that must be proven by a test with one permanently-stuck
    provider promise alongside normally-resolving ones.
  - An unhandled rejection in the wake-signal wiring. `dispatchExpansion` adds no try/catch of its
    own and relies on providers never rejecting; the wake-signal handler must attach a rejection
    path that degrades to an empty candidate map, matching the existing degenerate-provider
    handling, rather than letting a rejection escape.

`## 7. What this design does NOT change` — `dispatchExpansion`'s body (verified by an extraction
diff, not by argument), `fallbackExpectimax.ts`, `treeCommon.ts`, `select.ts`, the frozen
`SearchRunner` contract in `guardrail.ts`, and the shipped concurrency values. State that the
priority queue activation cannot affect output because commit order is dispatch order independent
of queue order, so it introduces no new ENGINE-07 surface and is a pure latency knob.

`## 8. Rejected alternatives` — the prefetch-only variant (rejected 2026-07-30; reachable only as
a recorded operator override, never a default), arrival-order apply under a weakened determinism
contract (the only way to buy real apply-order freedom, and it breaks DISPATCH-04/08 and the
reproducibility the bot-ELO map rests on), Maia batching over positions (measured and rejected in
SEED-126), and a dependency for the wait primitive or the queue.

`## 9. Reviewer findings and dispositions` — created empty in this task with a one-line note that
Task 2 populates it.
