<objective>
The tracer slice for Phase 204: a device that went dark because the server pruned its
`push_subscriptions` row re-registers itself on the next app load, with no user action and
without touching the one-shot notification permission.

Purpose: this is the phase's single highest-value fix (SEED-135 calls D2 "the one that
actually matters") and the only path in the phase that crosses every layer — browser probe,
`push.ts`, the HTTP client, the existing `POST /push/subscribe` endpoint, and the
`ON CONFLICT DO UPDATE` upsert. Proving that one path end to end first means the remaining
three fixes expand from a slice already known to work. Plan 02 (backend TTL + claim release)
runs in the same wave rather than after this one: it shares zero files and carries zero
architectural uncertainty (RESEARCH.md is HIGH confidence with every integration point read
from the file), so serializing it would buy no information — but note the composition, since
it is what makes this plan pay off *today*: prune at 16:05 → user opens the app at 18:00 →
this plan's re-sync restores the row → Plan 02's released claim lets the 18:15 tick send.

Output: two new `push.ts` exports plus one extracted private helper, a new app-wide hook
mounted in `ProtectedLayout`, an `enabled` gate on `usePushCapability`, and automated proof
at both ends — a Vitest suite for the fire conditions and the PERM-01 negative, and a pytest
HTTP integration test for the desync-and-recover round trip.

**Criterion 4 is deliberately narrowed here.** ROADMAP success criterion 4 reads "a VAPID
public-key change causes devices to detect the mismatch and re-subscribe". CONTEXT.md D-04
narrows it to "…on the user's next reminder-related gesture". This plan builds the
*detection* half (`subscriptionKeyMatches`) and wires it into the passive path as a
**suppressor only**: on a mismatch the passive path does nothing — no re-POST, no
`unsubscribe()`, no `subscribe()` (D-05). The *repair* half lands in Plan 03, inside
`ensureDeviceSubscribed`, which only runs on an explicit user gesture. The reasoning is in
CONTEXT.md D-04: Phase 201's D-02 locked rotation as accepted mass invalidation and
explicitly rejected a passive self-heal; the real bug in `existing ??` is that it makes even
the *manual* toggle-off/toggle-on unable to recover, and fixing the comparison restores
exactly the recovery D-02 promised. Do not satisfy the unnarrowed wording by adding a
passive-path `subscribe()`. The escape hatch, if the rotation story ever needs it, is
documented in CONTEXT.md D-04 (a repair guarded on `Notification.permission === 'granted'`
provably cannot spend the one-shot resource) and is declined here on D-02 grounds, not on
PERM-01 grounds.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/push/subscribe` | An authenticated but client-controlled request body carrying an endpoint URL and two key strings crosses here. |
| browser ↔ push service (`navigator.serviceWorker` / `PushManager`) | The `PushSubscription` object, whose `endpoint` is a bearer capability, is minted on the far side of this boundary and read by our code. |
| app code → Sentry | Any value passed to `captureException` leaves the trust domain. |
