<objective>
Land the sharp-filler spine end to end: one lichess CC0 position composed into a Train
session, served, solved, graded, and revealed — with the frontend correctly refusing to
frame it as one of the user's own games.

Purpose: this is the architectural proof for the whole phase. A `SHARP_FILLER` row has no
`games` row, no `game_flaws` row, and no `drill_items` row; every branch in the Train
repository that today assumes "not a herring implies an SR item" must become an explicit
three-way branch before anything else in the phase is worth building. Proving that on one
position, with a five-row seed data file, costs one commit; discovering it after the
200-position authoring pass and the warm-up label have landed costs the phase.

Output: the phase migration (third `DrillSource`, `drill_solves.sharp_puzzle_id`,
`drill_sessions.is_warmup`), `app/services/sharp_filler.py` with its committed data file
and the D-14 serve-order contract, the composition herring cap (D-02) plus sharp backfill
(D-03), the solve/reveal three-way branches (D-15/D-19/D-20), and the `source`-based
your-game predicate at all three `TrainReveal.tsx` sites.
</objective>

<assumption_delta_decision>
**The noun that is now primary:** *puzzle identity on a `drill_solves` row*. Before this
phase a solve row was identified by one of two nullable columns (`game_id` for an SR item,
`herring_pool_id` for a red herring). This phase adds a third (`sharp_puzzle_id`) and takes
`DrillSource` from two members to three — so "which column identifies this puzzle" is now a
three-arm discriminated union keyed on `source`.

**Decision: `add-alongside`.** `sharp_puzzle_id` joins `game_id` and `herring_pool_id` as a
third nullable identity column rather than being promoted into a single polymorphic
`puzzle_ref` representation. Rationale: D-10 (a committed data file, no `sharp_pool` table)
and D-17 (`SHARP_FILLER` as a third `DrillSource` member) are both locked, and a promotion
would require rewriting `herring_stmt`'s exclusion clause, `uq_drill_solves_session_puzzle`,
and every Phase-189/192 contract that reads those columns — a migration of live prod data to
buy uniformity this phase does not need.

**Accepted debt.** `drill_solves` now carries a three-arm union expressed as three
independent nullable columns with no database-level "exactly one non-null" constraint, and
`uq_drill_solves_session_puzzle` covers only the `(session_id, game_id, ply)` arm (Postgres
treats NULLs as distinct, so two filler rows cannot collide there — D-18). Composition must
dedupe sharp picks itself.

**What would force a later promote:** (a) a fourth `DrillSource` — three nullable columns is
already at the readable ceiling; (b) any source whose identity is not expressible as a single
scalar column (a composite external key); or (c) a need to resolve "the puzzle behind this
solve" polymorphically without branching on `source`.

**Invariant test encoding the generalized intent** (Task 2): `tests/repositories/
test_train_repository.py::test_drill_solve_identity_column_matches_source` builds a mapping
from every `DrillSource` member to its identity column, asserts the mapping's key set equals
`set(DrillSource)` *before* asserting per-source non-nullness, and therefore goes red the
instant a fourth member lands without a matching identity column.
</assumption_delta_decision>
