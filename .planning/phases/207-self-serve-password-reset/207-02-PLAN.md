<objective>
Put the two user-facing surfaces onto the backend contract Plan 01 proved: a forgot-password
form that is honest about revealing nothing, and a reset-password page that turns an emailed
link into a new credential.

Purpose: the backend path is already verified end to end, so this plan's risk is entirely in
the UI contract — the route path must match what the email link points at, the copy must not
leak existence, and the project's frontend rules (testids, type floor, button variants,
375px, explicit error branches) must hold. All of that is cheap to get right and expensive to
discover from a broken production link.

Output: `/auth/forgot-password` and `/auth/reset-password` render, submit, and error
correctly; `/login` links to the first; both are covered by Vitest suites that go red when the
behavior is reverted.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| browser → `POST /api/auth/forgot-password` | Attacker-chosen email leaves the browser; the response must carry no existence signal back into the DOM. |
| emailed link → browser URL bar | The reset token arrives as a query parameter, so it is exposed to browser history, the `Referer` header of any subresource, and any browser extension with tab access. |
| browser → `POST /api/auth/reset-password` | The token plus a new plaintext password crosses to the API over the same TLS channel as the rest of the app. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-207-14 | Information Disclosure | `ForgotPasswordForm` success rendering | medium | mitigate | Exactly one confirmation rendering with no status-dependent branch. Pinned by Case B, which compares captured `textContent` across a 202 and a 404 run and goes red if any branch is added. |
| T-207-15 | Information Disclosure | reset token in browser history / `Referer` | medium | accept | Inherent to emailed-link reset flows and to fastapi-users' router contract, which takes the token from the request body after the page has read it from the URL. The compensating controls are the 1-hour TTL, single-use fingerprint invalidation (T-207-07), and this plan's prohibition on persisting the token anywhere. Eliminating it would require a token-exchange redirect this phase does not scope. |
| T-207-16 | Information Disclosure | reset token persisted to storage or a console statement | medium | mitigate | Prohibited outright and enforced by Task 2's negative grep over both new files. |
| T-207-17 | Information Disclosure | reset token forwarded to Sentry via an error report | medium | mitigate | Sentry is called only on unexpected statuses, and the reported value is the axios error, whose request body is not attached by the project's client configuration. The component never places the token into a tag, a context, or a message. |
| T-207-18 | Spoofing | phishing-shaped UX training users to click password links | low | accept | Standard for the pattern. The mail is plain, from a configured `MAIL_FROM` on a DKIM-aligned domain, with no attachment and no link rewriting (COVERAGE.md declines open/click tracking precisely for this reason). |

No `high` threat is introduced by this plan; the `high` items for the phase are all backend
and are mitigated in Plan 01.
