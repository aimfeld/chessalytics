**`docs/email-resend-runbook.md`.** New operational runbook mirroring
`docs/push-vapid-rotation-runbook.md`'s structure. Sections:
  1. *What this covers and why it exists* — the project sends one transactional message
     (password reset), roughly five times a year; there is deliberately no canary (D-07), so
     the first symptom of breakage is a locked-out user and this document is the recovery path.
  2. *Step 0 — first-time setup* — transcribe the ROADMAP's operative record set exactly: the
     apex domain is what gets verified; three additive records (MX on `send`, SPF TXT on `send`
     with the amazonses include token, DKIM TXT at `resend._domainkey`); the load-bearing
     confirmation that DKIM lands at the apex level and the `MAIL_FROM` fallback if it does not;
     the empty-MX check on the sending subdomain; and the additive DMARC record.
     State prominently that the apex SPF record is never read and never modified, and record
     *why* (SPF is evaluated against the envelope-from, which Resend points at the `send.`
     subdomain, while DKIM signs at the apex, so DMARC passes on strict DKIM alignment). Note
     that the seed's original apex-merge instruction and its `_spf.resend.com` token are both
     wrong and superseded, so a future reader who finds the archived seed does not follow it.
  3. *Key rotation* — create a new sending-permission key in the dashboard, put it in the local
     `.prod.env`, run `bin/deploy.sh`, verify, then delete the old key. Never SSH-edit
     `/opt/flawchess/.env` directly.
  4. *Diagnosing a reported failure* — the ordered checks: is the Sentry `email_service` tag
     showing captures (and with what `status_code` in context); is the key present in
     `/opt/flawchess/.env`; is the domain still verified in the dashboard; do the three DNS
     records still resolve; did the address hard-bounce onto the suppression list. Map the
     Resend status codes to causes: 401/403 to a missing or revoked key, 422 to a `MAIL_FROM`
     that does not match the verified domain, 429 to the per-team request rate.
  5. *Deliberately not automated* — a short list pointing at `COVERAGE.md` for the reasoning:
     no canary, no webhooks, no retry, no SDK, no key-lifecycle automation. Include the
     escalation trigger from D-07 verbatim in spirit: if a reset ever fails in the wild,
     revisit the canary decision rather than debugging in place. Name Postmark as the
     designated provider fallback (D-03) so the swap decision is not re-derived under pressure.

8. Request a second reset for the same address within the hour and confirm the rate limit is
   observable in practice: after the configured maximum, no further message arrives, while the
   form still shows the same confirmation.
