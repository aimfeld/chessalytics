## SC-7 post-commit failure window (revision 1 — checker warning 1)

`store_pasted_game` commits the game row and only then calls `enqueue_tier1_game`, which is the
correct ordering (that function opens its own session, so an uncommitted row is invisible to it).
That leaves a window: if the enqueue raises AFTER the commit, a `platform='pgn'` row exists
durably with no `eval_jobs` row and a NULL `full_evals_completed_at` — the exact state SC-7 forbids.

**Resolution: handle it (option (a)). Accepting it as residual risk is NOT available**, and the
evidence is specific rather than precautionary. The only background mechanism that could heal such
a row is the tier-3 recency-weighted lottery, `_claim_tier3_derived`
(`app/services/eval_queue_service.py:458`). It claims games DIRECTLY from `games` with no
`eval_jobs` row required and no platform filter, so a pasted row is in its population — but its
predicate is a two-branch union (`:600-613`, mirrored for the per-game pick at `:629-638`):

| Branch | Predicate | Reaches a pasted row? |
|---|---|---|
| (a) needs-engine | `u.is_guest = false AND full_evals_completed_at IS NULL AND lichess_evals_at IS NULL` (`:601-606`) | **Non-guest only.** A pasted row satisfies both game-level conditions, so a non-guest's orphaned row IS eventually picked up. |
| (b) lichess-eval-pv-incomplete | `full_pv_completed_at IS NULL AND lichess_evals_at IS NOT NULL` (`:608-613`) — unguarded, guests qualify | **Never.** A pasted game's `lichess_evals_at` is always NULL, so this branch cannot match it. |

So a **guest's** orphaned pasted row is healed by nothing at all: branch (a) excludes it by
`is_guest`, branch (b) excludes it by `lichess_evals_at`. It stays `evals_completed_at IS NULL`
permanently, feeding `ix_games_user_evals_pending` and the `users_with_zero_pending` gate. D-08
puts guests squarely in scope for this feature, so this is a live case, not a theoretical one.
Even for a non-guest, branch (a) is a global random Efraimidis-Spirakis lottery, not a deterministic
sweep, so it carries no bound on when the row is picked up.

Note also that this module's own top-level docstring (`:53-55`) claims "enqueue_tier1_game also
refuses to enqueue a guest's game (no-op)". That line is stale: the function's code and docstring
(`:1088-1110`) return False only for a MISSING user row, and the queued-job claim path admits
tier-1 for guests (`:252`, `AND (u.is_guest = false OR ej.tier = 1)`). Guests genuinely do get
tier-1, which is what D-08 relies on. Do not "fix" the code to match the stale docstring.

**Handling** (Task 1 step 6): the enqueue failure is caught, reported to Sentry, and returned as
`eval_status="enqueue_failed"` on a 200 — the save really did succeed, so failing the request would
both lie and orphan the row behind an error the user cannot act on. **Healing path**: re-submitting
the same PGN resolves to the same row through the D-16 identity hash and re-enqueues, because the
skip condition is `full_evals_completed_at` being already set. Task 2 surfaces the state so the user
knows to do that; Task 3 tests the whole path, including that the second submit heals it.
