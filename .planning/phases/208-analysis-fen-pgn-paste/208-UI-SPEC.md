**Two weights declared: 400 (regular) and 500 (medium).** `font-semibold` (600) appears on the
pre-existing `CardHeader` ("Moves") this phase's trigger button sits inside — that weight

**Binding constraint — the `text-sm` floor (CLAUDE.md § Frontend) applies to every new
element below, with one concrete trap already measured in this codebase:** the shadcn
`Button` `size="sm"`/`size="xs"` and `Toggle`/`ToggleGroupItem` `size="sm"` variants render at

stay compliant (`FilterPanel.tsx:289-290`) — copy that override verbatim wherever this phase
reuses a `sm`-sized primitive. **Simpler default: use `size="default"` for every new button in
this phase** (its base class already carries `text-sm`, untouched by the size variant) and
avoid `sm`/`xs` sizes entirely except where explicitly noted below.

Mobile note (informational, not a new rule): `index.css:363-367` globally bumps `.text-sm` to
16px and `.text-xs` to 14px below the `sm:` breakpoint (639px). This is existing, unrelated
infrastructure — it does not license `text-xs` in new code; the CLAUDE.md prohibition is
absolute regardless of the mobile bump.

## Interaction Contract (phase-specific — beyond the template's copy/color/type axes)

This phase is dense in interaction decisions the template's static sections don't capture on
their own. Recorded here because the checker and the executor both need them, and CONTEXT.md
explicitly left two of them at "Claude's discretion."

### 1. Trigger placement and style

- **Site:** `analysis-movelist-header` (`Analysis.tsx:3607`), a `CardHeader size="compact"`
  currently rendering only an icon + "Moves". Per the component's own doc comment
  (`card.tsx:9-11`): `<CardHeader size="compact">Title <RightControls className="ml-auto" /></CardHeader>`
  — this phase's trigger is exactly that `RightControls` slot.
- **Component:** `<Button variant="ghost" size="default" className="ml-auto gap-1" data-testid="analysis-btn-paste">` with `<ClipboardPaste />` + "Paste" text.
  - `variant="ghost"` (not `default`/`brand-outline`): this is a header *utility* action, not
    a page-level CTA — reserving the phase's one `variant="default"` slot for the modal's
    primary "Load" button (see Color § Accent reserved-for).
  - `size="default"` (not `sm`): avoids the `text-[0.8rem]` trap documented in Typography.
- **Visible in every mode, including `?game_id=` game mode (D-20).** No conditional hiding.

### 2. Modal shell

- `Dialog` / `DialogContent` reused verbatim from `dialog.tsx`. Width: override the default
  `sm:max-w-sm` to `sm:max-w-md` (roomier for a pasted movetext block — `SuggestionsModal.tsx`
  already sets a precedent for widening past the `sm` default: `max-w-lg`). Below the `sm:`
  breakpoint the base class's `max-w-[calc(100%-2rem)]` applies unconditionally, so the modal
  is 343px wide at a 375px viewport with no extra work (SC-9's 375px requirement is met by
  the primitive, not by new code).
- **The modal's interactive body is a `<form>`, and BOTH the `DialogContent` and the `<form>`
  carry their own `data-testid`** — `data-testid="paste-modal"` on `DialogContent`,
  `data-testid="paste-form"` on the nested `<form>`. This reading of SC-9 ("the modal is a
  `<form>` with its own container testid") matches the codebase's one existing precedent
  exactly: `FeedbackModal.tsx` already nests `<form onSubmit=...>` inside `DialogContent
  data-testid="feedback-modal"` — this phase's only addition is giving the inner `<form>`
  element its own testid too, which `FeedbackModal` does not currently do. **Rejected
  alternative:** making `DialogContent` itself the `<form>` via Radix `asChild` composition —
  no precedent anywhere in this codebase, and no functional benefit over the div-wraps-form
  shape every other modal here already uses.
- **Outside-dismiss guard while a draft exists.** Reuse `FeedbackModal`'s
  `onInteractOutside` pattern verbatim (`FeedbackModal.tsx:90-97`): block outside-tap dismissal
  while the textarea has non-empty content, so an accidental tap-to-dismiss-keyboard on mobile
  doesn't discard a half-pasted game. The X button and (once implemented) an explicit close
  remain the deliberate ways out.
- **Draft is cleared on close** (mirrors `FeedbackModal.handleOpenChange`): closing the modal
  (X, outside-tap when empty, or a successful Load/Analyze) resets textarea text, side
  selection, and any inline error — the modal never reopens with stale state.

### 3. Textarea (D-01 — one box, sniffed, not toggled)

- `<Textarea>` reused verbatim from `textarea.tsx`. `rows={6}` for a visible starting height
  generous enough for a pasted game (the component's own `field-sizing-content` grows it
  further as content is typed/pasted).
- **Bounded growth (locked).** `field-sizing-content` (`textarea.tsx:10`) grows the box with its
  content, so a several-hundred-ply PGN would otherwise push `DialogContent` past the viewport.
  Add an explicit `max-h` with internal scroll (`overflow-y-auto`) on the textarea so the modal
  height stays bounded regardless of paste size. This supersedes an earlier draft claim that the
  dialog's inherited behavior already handled it — that claim was not verifiable against the
  primitives, and the cap is cheap and deterministic.
- `id="paste-input"`, `data-testid="paste-textarea"`, `aria-label="FEN or PGN"`,
  paired with a visible `<label htmlFor="paste-input" className="text-sm font-medium">` reading
  "Position or game" (matches `FeedbackModal`'s label pattern exactly: `text-sm font-medium`
  visible label, not a placeholder-only field).
- **No format toggle anywhere in the modal** — locked by D-01.

### 4. Live-sniffed state machine (drives which controls are visible — resolves "two buttons
   vs. checkbox")

Validation runs on every `onChange` (a paste is a single event, not per-keystroke typing, so
live validation does not flicker mid-type). Exactly one of four states holds at any time:

| State | Trigger | Side selector | Footer |
|-------|---------|----------------|--------|
| **Empty** | Textarea has no non-whitespace content | Hidden | "Load" only, `disabled` |
| **Valid FEN** | `loadPgn()` throws (bare-FEN shape) AND `parseAnalysisFenParam` succeeds | **Hidden** — D-06/D-04/D-05/D-08 do not apply to a bare FEN (no moves = no game; see SEED-144 note under D-10) | "Load" only, enabled. Label stays "Load" (not "Load position") — one constant label across states avoids footer text flicker |
| **Valid PGN with ≥1 move** | `loadPgn()` succeeds AND `history().length > 0` | **Shown**, defaulting to White (D-06) | Both buttons: secondary "Analyze full game" (`variant="brand-outline"`) + primary "Load" (`variant="default"`), DOM order secondary-then-primary (see § 5) |
| **Error** | `loadPgn()` throws AND `parseAnalysisFenParam` fails; OR `loadPgn()` succeeds with 0 moves (empty string / headers-only — CONTEXT.md's explicit "must be rejected" case, since the throw-based path never fires for these) | Hidden | "Load" only, `disabled`. Inline error renders (see § Copywriting) |

**Why two buttons, not one button + a checkbox (open item, resolved):** a checkbox model
("Load" + a "count as full game" checkbox) implies both actions are always simultaneously
available and merely toggled — false for the Valid-FEN state, where "Analyze full game"
categorically cannot apply (no moves, nothing to persist). Two conditionally-rendered buttons
correctly express that asymmetry without a dead, always-visible checkbox that sometimes does
nothing. It also maps cleanly onto the project's existing primary/`brand-outline` two-button
footer convention (`FeedbackModal`'s Cancel+Submit shape), rather than inventing a new
composite control.

**Which button is primary (resolved):** "Load" is `variant="default"` (the phase's one accent
slot), "Analyze full game" is `variant="brand-outline"`. Rationale: D-03/D-04 frame
paste-and-look as the *default*, safe, no-side-effect path ("Paste-and-look persists
nothing"), with "Analyze full game" as the *explicit*, deliberate escalation that writes a row
and spends engine budget. The button hierarchy should read the same way — the low-commitment
action is visually dominant, the higher-commitment action is present but secondary. This is
Claude's discretion (not locked by CONTEXT.md); the alternative (Analyze primary) is
defensible too, but D-04's own framing order ("Paste-and-look... An explicit 'Analyze full
game'...") supports this reading.

**DOM order:** `[secondary "Analyze full game", primary "Load"]`, matching `DialogFooter`'s
existing `flex-col-reverse ... sm:flex-row sm:justify-end` behavior
(`dialog.tsx:96`) — on desktop this right-aligns "Load" last/rightmost (primary-on-the-right
convention, same as `FeedbackModal`); on mobile the `flex-col-reverse` puts "Load" visually
first/top (thumb-reachable primary action), exactly mirroring `FeedbackModal`'s existing
Cancel/Submit DOM order.

### 5. Side selector (D-06)

Direct structural analog: `FilterPanel`'s White/Black "Played as" toggle
(`FilterPanel.tsx:283-291`). Reuse the same shape:

```
<ToggleGroup type="single" variant="outline" size="sm" value={userColor}
  onValueChange={...} data-testid="paste-side-selector" className="w-full">
  <ToggleGroupItem value="white" data-testid="paste-side-white"
    className="min-h-11 sm:min-h-0 flex-1 text-sm">White</ToggleGroupItem>
  <ToggleGroupItem value="black" data-testid="paste-side-black"
    className="min-h-11 sm:min-h-0 flex-1 text-sm">Black</ToggleGroupItem>
</ToggleGroup>
```

The `text-sm` override on each item is **mandatory**, not decorative — `size="sm"` on
`ToggleGroupItem` renders `text-[0.8rem]` (12.8px) without it (see Typography's binding
constraint). Default selection: White (D-06). No "Either" third option here (unlike
`FilterPanel`'s tri-state) — a pasted game always has exactly one user side, never "don't
care".

**Pre-fill / labeling when neither header name matches the user (deferred item 1,
recommendation):** keep the toggle items themselves generic "White"/"Black" (stable width,
matches the reused pattern exactly) and add one compact meta line directly below the toggle,
`text-sm text-muted-foreground`, e.g. "White: {WhiteName} ({WhiteElo}) · Black: {BlackName}
({BlackElo})" — populated from parsed PGN headers, omitting the rating parenthetical when a
header's Elo is absent, truncating each name individually (not the whole line) if it overflows
375px. This is a recommendation, not a lock: CONTEXT.md explicitly left this as a planning
detail.

### 6. Player info for an ephemeral (unsaved) pasted PGN — resolves deferred item 2

SC-2 requires names, ratings, result, and date to "reach the PlayerBar" for a pasted PGN, but
`PlayerBar`'s existing prop contract (`isWhite, name, rating, clockSeconds, testId`) has no
`result`/`date` fields, and the component is currently gated on `isGameMode && gameData`
(`Analysis.tsx:3180`) — a real fetched row that an ephemeral paste does not have.

**Design requirement (locked): all four fields must be visible in the board's player-info area
without navigating away — whether or not the game was ever saved.**

**Recommended mechanism (Claude's discretion, not a hard lock — CONTEXT.md left this open):**

- Render `PlayerBar` unchanged, sourcing `name`/`rating` from the parsed PGN headers
  (`White`/`WhiteElo`/`Black`/`BlackElo`) instead of `gameData` when in ephemeral paste-display
  mode — no prop-shape change needed, since `name: string | null` and `rating: number | null`
  already tolerate a header-sourced value exactly like a `gameData`-sourced one.
- `clockSeconds` is always `null` for a pasted game (D-07: untimed) — `PlayerBar` already
  hides the clock silently when `clockSeconds === null` (`PlayerBar.tsx:42`). This leaves the
  clock's right-aligned slot empty in paste mode, which is exactly the slot to reuse for
  result + date rather than opening new vertical space (the desktop layout explicitly clips
  overflow past the board's floor height — Phase 161 — so a whole new row is the wrong
  instinct here).
- Show `"{Result} · {Date}"` (e.g. `"1-0 · 2024-03-15"`) in that slot, `text-sm
  text-muted-foreground` (matching the existing rating-parenthetical color), on the **top**
  player row only (not duplicated on both rows).
- Applies only to Valid-PGN ephemeral display; a bare-FEN paste has no result/date/players to
  show and `PlayerBar` should not render at all for it (matching today's free-play behavior,
  where `PlayerBar` is absent outside game mode).

### 7. Library visibility, filter chip, and badge (D-11..D-14 — already locked by CONTEXT.md, restated here as the visual contract)

- **Filter chip:** reuse `ToggleChipButton` exactly as `FilterPanel`'s existing platform chips
  do (`FilterPanel.tsx:432-443`), added to a Library-scoped platform list — **not** the shared
  `PLATFORMS` constant (D-14 forbids widening it; Openings/Endgames/GlobalStats must never
  render this chip). `data-testid="filter-platform-pasted"`, icon `ClipboardPaste`, label
  "Pasted", **off by default** (D-11 — opt-in, not opt-out).
- **Card badge:** `<Badge variant="outline" className="text-sm" data-testid={\`library-pasted-badge-${gameId}\`}>Pasted</Badge>`
  in the existing empty `ml-auto shrink-0` slot at `LibraryGameCard.tsx:818-820` (confirmed
  empty for `platform='pgn'` today — `PlatformIcon` returns `null` for an unregistered
  platform and `gameUrl` is null with no `platform_url`). **`className="text-sm"` is
  mandatory** — the stock `Badge` component's base class is `text-xs` (`badge.tsx:8`), below
  the floor; `cn()`'s tailwind-merge (project convention, `project_frontend_no_prettier`
  memory) resolves the conflict correctly because `className` is passed last into `cn()`.
  `variant="outline"` (not `default`/`secondary`) — a neutral label, not a status/severity
  signal, and specifically not brand-brown (would violate the accent reserved-for list above).
- **Scope:** this chip and badge render on Library (Games + Flaws tabs) only — never on
  Openings, Endgames, or GlobalStats (D-14).

### 8. Navigation (D-09/D-10 — already fully specified by SEED-144's checklist; visual contract only)

No new visual treatment: the `/analysis` entry inherits the exact same styling every other
`NAV_ITEMS` entry gets — desktop header link (`App.tsx:195-201`, active state `bg-white/10
text-foreground font-medium`, **not** brand-brown) and `MobileMoreDrawer` link
(`App.tsx:483-495`). `data-testid`s are automatic from the array (`nav-analysis`,
`drawer-nav-analysis`) — no new naming needed. Icon: pick any unused, chess/analysis-flavored
lucide icon distinct from the five existing nav icons (`FolderOpen`, `Dumbbell`, `Bot`,
`BookOpenIcon`, `TrophyIcon`) and from `ClipboardPaste` (reserved for the paste
trigger/filter/badge's visual through-line, not the nav item itself — the nav item represents
the whole `/analysis` page, not specifically the paste feature). Exact icon choice is Claude's
discretion; `Microscope`, `SearchCode`, or `Cpu` (already imported in `Analysis.tsx` for the
engine card) are reasonable candidates — avoid re-using `Cpu` if it would read as
"Stockfish-specific" given `STOCKFISH_ACCENT` styling elsewhere on the same page.

### 9. Guest vs. authenticated — no difference

Confirmed by CONTEXT.md's scout (Integration Point 2): anonymous users never reach
`/analysis` at all (`App.tsx:610` redirects tokenless visitors to `/login`), and tier-1 enqueue
is already open to guests for their own games. **The modal renders identically for guests and
authenticated users — no guest-specific copy, no disabled state, no upsell.**
