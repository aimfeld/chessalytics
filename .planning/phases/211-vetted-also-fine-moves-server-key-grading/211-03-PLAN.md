# Plan 211-03: Re-establish the Phase 205 free-play guarantee on the server key

<objective>
Make the free-play board's first move read the same answer key the "Also fine" row does.

Purpose: Phase 205 (SEED-137 case 2) fixed a real, reported contradiction — a move the
reveal advertised as fine was badged a mistake the moment you played it — by grading the
free-play ROOT ply from the mount search's own ranks. Plan 02 deleted those ranks. The
guarantee must be re-established the new way (D-06), not regressed: one key, read by both
the list and the badge. This plan also closes the last two rows of Plan 02's consumer
ledger.

Output: `FreePlaySeedEval` carrying the served vetted moves instead of mount ranks; a
squares-only matcher living beside the move type it matches; the grading result's rank array
and the old squares-only rank matcher deleted; a new hook test file carrying the D-06
regression guard; and one operator check covering the two manual-only verifications.
</objective>

## Background

The mechanism being replaced (verified during planning, `useTrainFreePlay.ts` lines 289-326):
the root-ply branch fires only when `terminal === null && currentNode.parentId === null`,
looks the played squares up in the seeded mount ranks, and — on a hit — takes the CHILD eval
from that rank line while the PARENT eval still comes from `evalByFen`. Under Phase 211 that
mixed-source shape is a trap: the parent eval is the client engine's rank-1 reading, while a
server rank line's eval comes from the deep stored key. Subtracting one from the other can
produce a drop neither grader would produce on its own — a NEW way for the badge to
contradict the list.

So this plan does not merge the server key into the seeded lines. It reads the entry's own
server-computed `quality` directly. That is the most literal satisfaction of D-06 ("list and
root-ply grading both read the same server key"): the badge is not re-derived from evals at
all for a key move, so it cannot round differently from the list.
