This is unattended fleet time measured in days, driven by long-lived server and worker
processes on the operator's own box — it cannot be carried out inside an agent task. Everything
automatable has already been built: the selection table, the snapshot, the gate, the dual-URL
worker, and the `status` command.

Steps, all detailed in `docs/benchmark-lane-runbook.md`:

1. Launch the second backend on :8001 per runbook section 3, with all five environment flags
   on the command line and none of them in `.env`.
2. Confirm Maia loaded from the startup log (runbook section 4). Do not proceed past a
   Maia-absent start — the tranche would produce PV with no gem tiers and would have to be
   partially re-run.
3. Add `--fallback-url` and `--fallback-token` to the fleet's worker invocations (runbook
   section 5). Prod keeps strict per-claim priority; the benchmark backend receives only the
   cycles where prod's whole ladder had nothing to do.
4. Monitor with `scripts/benchmark_lane.py status --tranche classical` (runbook section 6).
   Watch specifically for the Maia warning line, and for `best_moves_done` tracking
   `full_pv_done` rather than lagging at zero.
5. Watch free disk on the benchmark volume through the run; these are UPDATEs, so dead row
   versions roughly double the transient footprint.

Stopping is a first-class outcome, not a failure. The TC tranches exist precisely so the
program is stoppable at a boundary. If you choose to stop after classical rather than continue
to rapid, that satisfies SC6 as written — say so, and Task 3 records it.

Do NOT run `bin/benchmark_db.sh reset` or `bin/reset_db.sh` at any point during this task.
`reset` on the benchmark DB destroys the entire 641,855-game corpus, not just the tranche.
