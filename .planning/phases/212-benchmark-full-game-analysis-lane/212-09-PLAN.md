<objective>
Materialize the real classical tranche and preserve what the drain will overwrite, so that
212-10's one-way decision is taken on measured, current numbers.

Purpose: `benchmark_selection` still holds only 212-01's 20-row smoke tranche. Every downstream
claim the gate makes is scoped to that table, so until the real selection exists there is
nothing for the fleet to work on. And D-05 is unambiguous that the snapshot must complete before
the fleet touches a tranche containing lichess-arm games — 212-06 discovered the hard way that
presenting the start decision before the snapshot exists makes the only safe answer "hold".

Output: a populated classical selection, full snapshot coverage for its lichess arm, and a
readiness file carrying the exact numbers the next plan's checkpoint has to present.

**Run this plan inline rather than as a dispatched subagent.** The selection pass and especially
the snapshot pass are long database-bound operations, and this project has recorded losing
long-running work when an agent backgrounds it or when a subagent's connection drops mid-plan.
</objective>

Run the snapshot subcommand for the classical tranche against the benchmark database. Expect
this pass to be long: the phase's sizing puts the classical lichess arm at roughly 27,000 games

Record the reported inserted and skipped counts, then run the identical command again and record

row count, which is the idempotency D-05 relies on and which 212-06 already observed at smoke
scale.

Then verify coverage directly against the database, because the count that matters is not the
number of snapshot rows but the number of selected lichess-arm games with at least one:

- The number of classical `benchmark_selection` rows whose `lichess_arm` is true.
- The number of distinct game ids in `benchmark_lichess_eval_snapshot` that appear in that set.
- The difference between the two. This must be exactly zero. A non-zero difference means some
  selected lichess-arm games have no preserved evals, and starting the drain would destroy them
  permanently — lichess's stored values for those positions exist nowhere else in this project
  and re-fetching them is out of scope for this phase.

If the difference is non-zero, re-run the snapshot subcommand and re-check. Record both passes.
Do not proceed to Task 3 with a non-zero gap; that number is the one thing 212-10's decision
checkpoint is not permitted to override.

Also record the total snapshot row count and the table's on-disk size, so 212-10's post-run
vacuum has a meaningful before figure for the storage the tranche adds.
