<objective>
Give the Stockfish side of the engine the readiness and download-progress
surfaces Maia gained in Plan 01, then turn on gating for blend > 0 personas.

Two asymmetries drive this plan and must not be flattened:
1. `WorkerPool` has **no readiness concept at all** today (only a per-slot
   `isReady` flag read by `dispatchNext()`), so this is genuinely new
   pool-level code, not the ~10-line forwarding job `MaiaQueue` was.
2. Stockfish's download progress must **not** be an owned streaming fetch. The
   vendored `stockfish-18-lite-single.js` already ships a working, unused
   `progressPort` protocol; the app side is wiring only.

Purpose: a blend > 0 persona (rungs 1600/1800) never starts its clock against
an engine that has not finished downloading either of its two assets.
Output: `WorkerPool.whenReady()`, `progressPort` wiring in `createSlot()`, and
the blend > 0 branch of the D-04 gate predicate switched on.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vendored Stockfish glue → app | `progressPort` `MessageChannel` payloads `{percent, loaded, total, ...}` cross from third-party glue into app state. |
| CDN/Caddy → vendored glue | The `.wasm` response is gzip-encoded with no `Content-Length`; the glue uses a hardcoded raw total instead. |

## STRIDE Threat Register (ASVS L1, block on `high`)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-213-01 | Denial of Service | `progressPort` payload → `reportEngineAssetProgress` | medium | mitigate | The glue's `total` is a hardcoded constant today, but the app must not assume it. Discard the glue's `percent` entirely and re-derive it in the store, where `Number.isFinite(total) && total > 0` falls back to `STOCKFISH_WASM_BYTES_FALLBACK` and the result is clamped to `[0, 100]`. Task 2's zero-`total` case is the proof. |
| T-213-07 | Denial of Service | `createSlot()` | medium | mitigate | A `MessageChannel` construction failure must not break engine spawn. Feature-detect and skip the wiring; `ensureSpawned()`'s existing per-slot try/catch remains the graceful-degradation floor. |
| T-213-08 | Denial of Service | `WorkerPool.terminate()` + `poolReadyWaiters` | medium | mitigate | Waiters left hanging across a terminate/re-spawn would deadlock any consumer awaiting readiness (Plan 05's `useFlawChessEngine`). `terminate()` settles and clears them; Task 1's reset case is the proof. |
| T-213-SC | Tampering | package installs | low | accept | No new packages in this plan. The `progressPort` protocol is already inside the vendored glue and the vendored file is not modified (proved by an empty `git diff --stat`). No install task, so no legitimacy checkpoint. |

ASVS V2/V3/V4/V6 do not apply. V5 applies at T-213-01 only.
