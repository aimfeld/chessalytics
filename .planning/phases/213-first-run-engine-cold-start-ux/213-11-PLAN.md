<objective>
Fix a regression this phase introduced, and let the analysis board get out of the
user's way once the engine is up.

**Part 1 — `G-213-36`, a blocker introduced by plan 213-09.** The user hit this in both
Chrome and Brave:

```
Uncaught (in promise) DataCloneError: Failed to execute 'postMessage' on 'Worker':
ArrayBuffer at index 0 is already detached.
    at constructWorker (maiaWorkerHost.ts:379:5)
    at maiaWorkerHost.ts:321:5
```

`ensureOrtRuntime()` caches ONE promise resolving `{ backend, buffer }`.
`constructWorker` pushes that `buffer` into `postMessage`'s transfer list, which
DETACHES it. Every later spawn resolves the same cached promise, gets the same
now-detached ArrayBuffer, and throws.

Plan 213-09 chose "transfer, not copy" on the reasoning that the only path needing the
bytes twice was the WebGPU->wasm respawn, which needs a *different* build anyway. That
reasoning covered one respawn path and missed the ordinary one: navigating
/analysis -> /bots releases the last lease, tears down module state, and the next
`analyze()` spawns again — straight into the detached buffer.

The user-visible damage is severe and does not look like a crash. `new Worker()`
succeeds, so the worker script loads; then `postMessage` throws inside a `.then()` as
an unhandled rejection, so the worker NEVER receives its init message, never posts
`ready`, and `dispatchNext()` never runs. The move only appears when something else
times out into a fallback: the user measured ~60s for Sheldon the Snail (850) and
~3 minutes for Cackle the Hyena (~1800) on the first move, then normal speed after.

**The fix is retain-and-copy, and the alternative must be rejected explicitly.**
Detecting detachment (`byteLength === 0`) and re-fetching would be more memory-lean and
is the tempting fix — but it issues a fresh network request on the /bots hop, which
fails the both-surfaces zero-refetch criterion outright when DevTools has "Disable
cache" ticked, which is exactly how this phase is verified. Retain the master, transfer
a copy.

**Part 2 — `D-18`, a user decision.** On the analysis board the gate should close itself
once the engine is ready: no footer, no Start button. On bot games the modal and its
Start button stay. The `surface` prop already carries the distinction, so this is a
branch, not a new component.
</objective>

    - Calling the runtime source twice returns usable bytes BOTH times. The second call
      never returns a detached buffer.
    - Two sequential spawns each deliver an init message carrying a runtime buffer of
      the correct byte length; neither throws.
    - The second spawn issues NO new `fetch` for the runtime binary — asserted on the
      fetch stub's call count, since this is the criterion that rules out the
      refetch-on-detach alternative.
    - Each worker receives its OWN buffer instance: mutating or detaching one worker's
      copy cannot affect another's, and cannot affect the retained master.
    - The retained master is never placed in a transfer list.
    - The wasm-only respawn path (`fetchWasmOnlyOrtRuntime`) has the same property —
      it is a second reader of a cached value by construction and must not detach it
      either.
    - A spawn whose runtime buffer is null still constructs the worker and still posts
      an init message (the degraded path from 213-09 is unchanged).
    - `modelBuffer` continues to be transferred, and the audit conclusion is recorded.
  </behavior>
  <action>
Keep the fetched ArrayBuffer as a retained master inside `ortRuntimeSource.ts` and hand
out a fresh copy per consumer — `master.slice(0)` — so the value placed in the transfer
list is always a copy the caller owns. The master is never transferred and therefore
never detaches.

Prefer doing this INSIDE the runtime source rather than at the `constructWorker` call
site: the source owns the cache, so it is the only place that can guarantee the
invariant for every current and future consumer. A fix applied only at the call site
would leave the next caller free to reintroduce the bug.

Apply the same treatment to `fetchWasmOnlyOrtRuntime` — it is a cached second reader by
construction and has the identical failure mode on a second respawn.

Add a comment at the fix site recording what broke and why (CLAUDE.md comment-bug-fixes
rule): the buffer was transferred to the first worker, detaching the cached copy, so
the second spawn — the ordinary /analysis -> /bots navigation, not the exotic WebGPU
respawn plan 213-09 reasoned about — threw `DataCloneError` and left a worker that
never received its init message.

**Rejected alternative, record it in the summary:** detect `byteLength === 0` and
re-fetch. It is more memory-lean, but it puts a network request on the second spawn,
which breaks the both-surfaces zero-refetch acceptance criterion under `Disable cache`.
The accepted cost of retain-and-copy is ~13.5 MB held for the page session (24.3 MB on
the WebGPU path) against an ORT heap already near 226 MB, plus one transient copy per
spawn. Record that trade explicitly; it is the FLAWCHESS-92 memory context that made
213-09 choose transfer in the first place.

Audit the `modelBuffer` transfer in the same call site. It arrives from the dying
worker's `webgpu-unavailable` message and is not read from any cache, so it is
genuinely one-shot and transferring it is correct. State that conclusion in the summary
rather than leaving it unexamined — if the audit finds a second reader, fix it the same
way and say so.

Extend `ortRuntimeSource.test.ts`: two sequential calls both yield non-detached buffers
of the right length, with exactly ONE fetch; the returned buffers are distinct
instances; detaching one does not affect the next call.

Extend `maiaWorkerHost.test.ts` with the actual regression: spawn, tear down module
state as a /analysis -> /bots navigation does, spawn again, and assert the second
worker RECEIVED its init message with a runtime buffer — and that no error was thrown.
A test that only asserts "no throw" is not enough; assert the init message landed,
because the observed failure was a worker that started and then silently never
initialised.

Prove load-bearing: revert to transferring the cached master, confirm the second-spawn
test fails with the detached-buffer error, restore it, and record the revert.
