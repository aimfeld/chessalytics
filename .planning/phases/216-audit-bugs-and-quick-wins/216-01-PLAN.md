<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet -> Cloudflare edge | Untrusted client traffic; Cloudflare injects `Cf-Connecting-Ip` |
| Cloudflare edge -> Caddy (origin :443) | Origin is directly reachable from any IP per `docs/production-runbook.md`; the peer address is the only trustworthy discriminator |
| Caddy -> backend:8000 | Docker-internal; uvicorn trusts `X-Forwarded-For` from its only peer (D-12) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-216-01 | Spoofing | `deploy/Caddyfile` global `servers` block | high | mitigate | `trusted_proxies static <published CF ranges>` means Caddy honors `Cf-Connecting-Ip` only when the socket peer is inside a Cloudflare range. A client connecting directly to the origin has a peer address outside those ranges, so its forged header is ignored and its real peer IP is used. Task 1 forbids widening a range or writing a catch-all. |
| T-216-01B | Tampering | inline CIDR list in `deploy/Caddyfile` | medium | mitigate | Ranges are fetched live in Task 1, never hand-copied, and `bin/check_cloudflare_ips.sh` (Task 3) fails loudly on drift or on a broken parse, so a stale list cannot silently reopen F-01. |
| T-216-01C | Information disclosure | Caddy access log (`request.client_ip`) | medium | mitigate | Task 2 raises the posture change explicitly instead of silently starting to log visitor IPs; either option corrects the now-false comment, and option B filters the field out of both log blocks. |
| T-216-01D | Denial of service | guest-creation limiter (`app/routers/auth.py`) | low | accept | Correct per-visitor IPs make the 5/hour limiter effective again; visitors sharing a NAT/CGNAT address can still collide. That is the limiter's pre-existing design, unchanged by this phase. |
</threat_model>
