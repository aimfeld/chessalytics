## Tests

### 1. Fresh navigation: self.crossOriginIsolated
expected: `self.crossOriginIsolated === true` in the page console.
result: **pending** — requires reading a live page's console; not
  measurable via curl. Precondition (both headers on the document response)
  confirmed present above.

### 1b. Service-worker-served offline navigation: self.crossOriginIsolated
expected: `true` after loading once online (populates the `html-shell`
  Workbox runtime cache), then going offline in DevTools and reloading —
  per 219-RESEARCH.md Pitfall 2, the `NetworkFirst` route stores whatever
  headers were present on the last successful online fetch, so a shell
  cached AFTER this phase's headers shipped should still read `true` when
  served from cache. A device that goes offline before ever loading this
  build gets a pre-change cached shell without the headers and degrades to
  one thread via `chooseWasmThreadCount()`'s fail-safe — expected, not a bug.
result: **pending** — requires DevTools Offline throttling in a real
  browser tab; not measurable via curl (CacheStorage is browser-internal
  state, not reachable from this session).

### 2. Google login round-trip under COOP
expected: opening the login page and starting the Google flow performs a
  full-page redirect to the identity provider and returns (COOP
  `same-origin` only governs popup/opener relationships, so a redirect flow
  is structurally unaffected — 219-RESEARCH.md "State of the Art",
  `LoginForm.tsx`/`RegisterForm.tsx` verified as `window.location.href =
  ...` at research time).
result: **pending** — requires driving the OAuth flow in a real browser and
  observing the navigation; not measurable via curl (the flow needs a live
  Google identity-provider round trip and cookies/session state this
  session cannot drive).

### 3. Umami script load under COEP
expected: a network entry for `analytics.flawchess.com/script.js` with a
  200 status and no COEP-blocking console error.
result: **pending** for the actual browser network-panel/console
  observation. Supporting `curl` evidence gathered this session:
  ```
  $ curl -sI --max-time 5 https://analytics.flawchess.com/script.js
  HTTP/2 200
  content-type: application/javascript; charset=UTF-8
  access-control-allow-origin: *
  ```
  The response does **not yet** carry `cross-origin-resource-policy:
  cross-origin` — expected, since this phase's `deploy/Caddyfile` change has
  not been deployed to production yet (this phase ends at the squash-merge,
  per D-14/219-02-PLAN.md Task 4 — the Caddy CORP header is a post-deploy
  item). The `access-control-allow-origin: *` the response already sends is
  what the `crossorigin="anonymous"` attribute added to `frontend/index.html`
  this task (219-02 Task 2) relies on to satisfy COEP via CORS in dev,
  preview, and pre-deploy production, ahead of the Caddy fix landing.
  Tracking itself (events reaching the Umami dashboard) is a separate,
  post-deploy-only check — `data-domains="flawchess.com"` on the script tag
  suppresses tracking on localhost regardless of headers, so this is
  HUMAN-UAT deferred to the eventual release, not something any pre-deploy
  session (browser or headless) can observe.
