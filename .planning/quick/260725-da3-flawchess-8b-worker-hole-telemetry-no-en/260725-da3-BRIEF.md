# Quick Task 260725-da3 — Brief

**Task:** FLAWCHESS-8B worker hole telemetry + no engine restart on timeout

## Investigation context (already done, do not redo)

Sentry issue **FLAWCHESS-8B** — `atomic-submit: stamping complete after MAX_EVAL_ATTEMPTS with residual holes`, ~1602 events since 2026-07-03, a few per hour, `level=warning`, culprit `/api/eval/remote/atomic-submit`.

Prod measurement (2026-07-25, via the read-only prod tunnel) over engine games with `full_eval_attempts >= 1`:

| metric | value |
|---|---|
| games with genuine mid-game holes | 2351 |
| median holes/game | 25 |
| avg holes/game | 27.4 |
| games with exactly 1 hole | 40 |
| games with >= 5 holes | 2238 |
| max holes | 111 |

This contradicts the code comments and the earlier triage, which assumed "1-2 terminal-only holes/game". Example: game 1867392 has NULL-eval plies 9, 11-22, 31, 32 with `max_ply = 32`, i.e. 13 genuine mid-game holes (plies 31/32 are the excluded game-ending/terminal plies) matching the event's `hole_count: 13`.

**Root cause (worker capacity, NOT a keying/convergence bug):** `scripts/remote_eval_worker.py:_eval_positions` fans the WHOLE game out in one `asyncio.gather`, and each eval is capped at `_NODES_TIMEOUT_S = 5.0s` for a 1M-node search (`app/services/engine.py`). A slow box therefore loses a large *fraction* of one game at once, rather than failing 1-2 genuinely hard positions.

**Attribution is currently impossible:**
- `_report_path_c_capacity_reached` sets only `game_id` / `hole_count` / `attempts` context plus a `source` tag. No worker identity.
- `eval_jobs.leased_by` exists but is empty for this population: **0 of the 2351 holed games have an `eval_jobs` row** (all tier-3 idle-lottery derived claims, `job_id=None`).
- `worker_heartbeats` is fleet-level aggregate only, no per-game rows.
- Fleet note: `31.10.131.115` shows 97 distinct `worker_id`s (58 with <= 5 submits) because `--worker-id` is optional and a random 8-char id is minted per process start, so each watchdog restart looks like a brand-new worker. Named boxes (`amalie-nb`, `amalie-pc`, `ai-slim`, `ws80`) pass an explicit id.

## ITEM 1 — per-worker hole counters on `worker_heartbeats`

The item that actually answers "is it one slow worker".

- Add two columns to `app/models/worker_heartbeat.py`: `holes_submitted` and `plies_leased`. Follow the existing `submit_count` / `evals_submitted` pattern exactly (`BigInteger`, `nullable=False`, `default=0`).
- Alembic migration with `server_default='0'` so the ~120 existing prod rows backfill.
- Wire them into `upsert_worker_heartbeat` (`app/repositories/worker_heartbeat_repository.py`) as **accumulating** counters, same as `submit_count` / `evals_submitted`.
- Feed them from the atomic-submit lane in `app/routers/eval_remote.py:_apply_atomic_submit`, where `failed_ply_count` and the submitted ply count are both known.
  - `holes_submitted` accumulates `failed_ply_count` for **EVERY** submit that has holes, not just the Path-C cap path. That is the whole point: per-attempt telemetry makes a slow worker visible before it burns all 3 attempts.
  - `plies_leased` accumulates the submitted ply count so a per-worker hole **rate** can be computed.
- Passive telemetry only: no gate, no authz decision, no behavior change. Mirror the existing PRUNE-06 / D-01/D-04 "passive telemetry only" comment convention and the T-123-03 note that `worker_id` is advisory and never used for authz.

## ITEM 2 — stop restarting the Stockfish process on a timeout

Highest-value fix for hole VOLUME.

- In `app/services/engine.py:_acquire_and_analyse` (~line 505), `asyncio.TimeoutError` currently shares an `except` tuple with `chess.engine.EngineError` and `chess.engine.EngineTerminatedError`, and all three trigger `await self._restart_worker(idx)`.
- A timeout means "this box is slow", NOT "the engine is broken". Restarting spawns a fresh Stockfish process on an already-slow box, plausibly amplifying one slow position into a block of holes.
- Split the handling: on `asyncio.TimeoutError` return `None` **without** restarting the worker (the slot still returns to the queue via the existing `finally`). Keep the restart for `EngineError` / `EngineTerminatedError`, which are genuine engine failures.
- **MANDATORY correctness check — verify, do not assume.** After a python-chess `analyse()` call is cancelled by `asyncio.wait_for`, confirm whether the protocol object is left in a usable state for the NEXT `analyse()` on that same slot. If a cancelled `analyse` can desync the UCI protocol, then skipping the restart is UNSAFE: report ITEM 2 as **blocked with evidence** and ship only items 1 and 3. Check python-chess's own behavior/docs for cancellation of `analyse()` (the vendored-WASM headless verification trick from project memory is for Stockfish WASM and does NOT apply here). Do not hand-wave this.
- Add a comment at the fix site explaining what broke and why (CLAUDE.md bug-fix comment rule).

## ITEM 3 — `worker_id`/`last_ip` on the Path-C Sentry event

- `app/routers/eval_remote.py:_report_path_c_capacity_reached` currently sets only `game_id`/`hole_count`/`attempts` context plus a `source` tag.
- Thread `worker_id` and `last_ip` through so the event carries them. The callback is the shared `on_path_c_capacity_reached: Callable[[int, int, int, str], None]` parameter of `app/services/eval_apply.py:apply_completion_decision`, used by BOTH lanes:
  - the atomic-submit router lane (`sentry_sdk.capture_message`), and
  - `eval_drain.py`'s in-process tick (`logger.warning` — **FLAWCHESS-5V: it MUST stay `logger.warning`; do NOT convert it to a Sentry call**, an earlier per-tick Sentry call burned the error quota).
- Pick the least invasive way to get worker identity into the router lane's callback without changing the drain lane's reporting mechanism. Prefer a `functools.partial` / closure over `worker_id` + `last_ip` built in `_apply_atomic_submit` rather than widening the shared signature for a value the drain lane does not have.
- Variables go via `sentry_sdk.set_tag` / `set_context`, **NEVER** embedded in the message string (CLAUDE.md Sentry grouping rule). The message must stay byte-identical so all 1602 existing events keep grouping into FLAWCHESS-8B.
- Add a code comment noting the tag names only the **LAST** of the 3 attempters, so a future reader does not over-trust it for attribution (item 1's counters are the real attribution mechanism).
