<objective>
Rewrite `_claim_tier3_derived`'s Step-1 user pick from one EXISTS-with-an-OR into two
correlated EXISTS with the `u.is_guest` guard distributed outward, so PostgreSQL can do a
per-user index-only probe against the two already-existing partial indexes instead of
heap-fetching the entire backlog.

Purpose: this query is 89.8% of production DB time (10,376 calls x 221 ms mean over 7.5h,
71k shared buffers/call). Its cost is O(backlog), so it grows with the corpus. Prod
EXPLAIN (ANALYZE, BUFFERS) already measured on the live DB via the read-only MCP:

- before: 360.478 ms, shared hit=71612, Bitmap Heap Scan on games rows=255,218,
  Heap Blocks exact=70,274, Hash Right Semi Join just to evaluate `u.is_guest`.
- after: 8.574 ms, shared hit=2235 read=5. Seq Scan on users (418 rows) +
  `Index Only Scan using ix_games_needs_engine_full_evals` (loops=178) +
  `Index Only Scan using ix_games_lichess_pv_backfill_pending` (loops=400).
- ~42x faster, ~32x fewer buffers, cost becomes O(users).

Semantic equivalence was also already proven on prod with EXCEPT in both directions:
orig_n=21, rewritten_n=21, only_in_orig=0, only_in_rewritten=0. **Do not re-derive or
re-litigate the approach** — plan and implement the code change, its guest-asymmetry
preservation, and its tests.

Output: a rewritten Step-1 predicate, a `candidate_where_sql` seam on the shared helper,
corrected docstrings, and tests pinning both the new predicate semantics and the
byte-identity of the two untouched tier-4 call sites.

**Note on the directory slug:** `...user-id-leading-partial-indexes...` is stale framing.
Both indexes already exist and are already `btree(user_id)`. This is a query-SHAPE fix.
</objective>

<design_decision>
**How tier-3 passes a full WHERE predicate without forking the helper.**

`_es_weighted_user_pick` gains a second, mutually-exclusive fragment parameter
`candidate_where_sql: str | None = None`, alongside the existing
`candidate_exists_sql: str | None = None`. Exactly one must be supplied (raise `ValueError`
otherwise). The helper computes a single local `where_body` and the SQL template becomes
`WHERE {where_body}` — one template, one ES key, one ORDER BY, one LIMIT, one emitter.

- When `candidate_where_sql` is given (tier-3 only): `where_body` is that fragment verbatim.
  The caller owns the whole predicate, including the guest guard.
- Otherwise (tier-4 blob, tier-4 bestmove): `where_body` is rebuilt from the existing
  `{guest_clause}` + `EXISTS (...)` composition, reproducing the current template's exact
  whitespace so the emitted string stays byte-identical.

Rejected alternatives: a second helper (forks the ES logic — explicitly forbidden); a
`shape=` enum (same two-parameter reality with more indirection); making tier-4 also pass a
full WHERE (churns two known-good prod plans for no benefit).
</design_decision>
