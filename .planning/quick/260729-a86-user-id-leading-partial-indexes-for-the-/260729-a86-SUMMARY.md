# Quick 260729-a86: Tier-3 Step-1 query-shape fix Summary

**Rewrote `_claim_tier3_derived`'s Step-1 predicate from one EXISTS-with-an-OR into two correlated EXISTS with the guest guard distributed outward, cutting the query from 360ms/71.6k buffers to 8.6ms/2.2k buffers on prod (measured pre-change via the read-only MCP), turning its cost from O(backlog) to O(users) — no migration, both partial indexes already existed.**

## Performance

- **Duration:** ~15 min
- **Completed:** 2026-07-29
- **Tasks:** 3 (tracer + tdd test task + pre-merge gate)
- **Files modified:** 2 (`app/services/eval_queue_service.py`, `tests/services/test_eval_queue.py`)

## Accomplishments

- `_claim_tier3_derived` Step 1 now emits two correlated `EXISTS` subqueries (needs-engine branch guarded by `u.is_guest = false` as an outer conjunct; lichess-eval-pv-incomplete branch unguarded) instead of a single `EXISTS` containing an internal `OR` — each branch can now be satisfied by an index-only scan on its own existing partial index (`ix_games_needs_engine_full_evals`, `ix_games_lichess_pv_backfill_pending`) instead of forcing a bitmap-or plus a full heap fetch of the entire matching backlog.
- `_es_weighted_user_pick` gained a second, mutually-exclusive `candidate_where_sql` parameter alongside the existing `candidate_exists_sql`. Exactly one must be supplied (`ValueError` otherwise); the helper computes one local `where_body` either way, so the ES key / `ORDER BY` / `LIMIT` logic stays defined in exactly one place, not forked across a second helper.
- Tier-4 blob and tier-4 bestmove callers were left completely untouched (still using `candidate_exists_sql`) — pinned byte-identical to the pre-rewrite HEAD template via new exact-`==` string-equality tests, since both prod query plans are already known-good.
- QUEUE-08 guest asymmetry re-proven in both directions on the new predicate shape: a guest's needs-engine-only game is never picked; a guest's lichess-eval pv-pending game is pickable; a non-guest is pickable via either branch; a fully-complete non-guest game is picked via neither.
- Docstrings for `_es_weighted_user_pick` and `_claim_tier3_derived` rewritten to describe the new shape, record the measured prod numbers (360.478ms/71,612 buffers before -> 8.574ms/2,235 buffers after, EXCEPT-verified equivalence 21=21/0/0), and explicitly warn against "simplifying" back into a single EXISTS-with-OR (which would not regress visibly on the dev DB, since `games` there is small enough to seq-scan either shape).

## Decisions Made

- Distributed the `u.is_guest = false` guard onto branch (a) as an outer conjunct rather than leaving it inside a single `EXISTS(... OR ...)` — this is the load-bearing change that lets PostgreSQL probe each branch's own partial index per user (verified on prod: 360ms/71.6k buffers -> 8.6ms/2.2k buffers, EXCEPT-verified equivalence in both directions).
- Added `candidate_where_sql` as a second mutually-exclusive parameter on the shared `_es_weighted_user_pick` helper (guarded by a `ValueError` if both or neither are supplied) rather than forking a second helper function or adding a `shape=` enum — keeps the ES key/`ORDER BY`/`LIMIT` logic single-sourced across all three callers (tier-3, tier-4 blob, tier-4 bestmove).
- Left the tier-4 blob and tier-4 bestmove call sites completely untouched on the `candidate_exists_sql` branch — both prod query plans are already known-good (previously measured and fixed via SEED-125/174-07), so churning their SQL text for no behavioral gain would be pure risk; pinned with exact byte-identity tests instead.
