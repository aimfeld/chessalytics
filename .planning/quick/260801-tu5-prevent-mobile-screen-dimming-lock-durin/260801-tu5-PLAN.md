# Quick Task 260801-tu5: Screen wake lock on the Train solve screen

## Problem

On mobile, the OS dims and then locks the screen while a user studies a Train
puzzle or reads its reveal. Both are long, low-interaction reading states — no
touch input for 30s+ is normal — so the default auto-lock timer fires mid-task.

## Approach

Screen Wake Lock API (`navigator.wakeLock.request('screen')`), held only while
`TrainSolveScreen` is mounted. No user setting, no toggle (locked decision).

### Decisions

- **Scope: `TrainSolveScreen` only.** Covers solving and the reveal
  (`TrainReveal` renders inside it). Deliberately excludes `TrainStartScreen`
  and `TrainScoreScreen` — holding the lock there would keep the screen awake
  after a user walks away mid-session.
- **Unconditional.** No `enabled` prop, no settings row in
  `TrainScheduleSettings`. The lock's lifetime is already bounded by the
  component's mount.
- **Silent failure.** `request()` rejects on unsupported browsers (iOS < 16.4),
  insecure contexts, and iOS Low Power Mode. All are expected conditions, not
  bugs: swallow in `try/catch`, no `Sentry.captureException`, no user-facing
  error (per CLAUDE.md "skip expected failures").
- **Re-acquire on visibility.** The browser auto-releases the sentinel whenever
  the document becomes hidden (tab switch, app backgrounded, manual lock). This
  is the primary failure mode of this API: without a `visibilitychange`
  listener re-requesting on `visible`, the lock silently stops working after
  the first interruption and never comes back.

## Tasks

### Task 1 — `frontend/src/hooks/useWakeLock.ts`

- `files`: `frontend/src/hooks/useWakeLock.ts` (new)
- `action`: Add a no-arg `useWakeLock(): void` hook. One `useEffect` with an
  empty dep array that:
  1. Requests a `'screen'` sentinel on mount, guarded by an `'wakeLock' in
     navigator` feature check and a `try/catch`.
  2. Stores the sentinel in a ref; clears the ref from the sentinel's own
     `release` event so a browser-initiated release does not leave a stale
     handle that blocks re-acquisition.
  3. Registers a `visibilitychange` listener that re-requests when
     `document.visibilityState === 'visible'`.
  4. On cleanup: removes the listener, sets a `cancelled` flag (so an in-flight
     request that resolves after unmount releases itself instead of leaking),
     and releases any held sentinel.
- `verify`: `npm run build` (tsc) passes; hook has an explicit `: void` return
  type.
- `done`: File exists and exports `useWakeLock`.

### Task 2 — Wire into `TrainSolveScreen`

- `files`: `frontend/src/components/train/TrainSolveScreen.tsx`
- `action`: Import and call `useWakeLock()` alongside the existing
  `useMarkPlayActive()` call at the top of the component body, with a short
  comment stating why the scope is this component only.
- `verify`: `npm run lint`, `npm run build`.
- `done`: `useWakeLock()` called unconditionally in `TrainSolveScreen`.

### Task 3 — `frontend/src/hooks/__tests__/useWakeLock.test.ts`

- `files`: `frontend/src/hooks/__tests__/useWakeLock.test.ts` (new)
- `action`: jsdom test with a mocked `navigator.wakeLock`. Cases:
  1. Acquires on mount (`request` called once with `'screen'`).
  2. Releases on unmount.
  3. Re-acquires after the browser releases the lock and the document returns
     to `visible` (fire the sentinel's `release` event, flip
     `document.visibilityState` to `hidden` then `visible`, dispatch
     `visibilitychange`) — the regression guard for the primary failure mode.
  4. Does not re-acquire on a `visibilitychange` to `hidden`.
  5. No throw when `navigator.wakeLock` is absent (unsupported browser).
  6. No throw when `request()` rejects (iOS Low Power Mode).
- `verify`: `npm test -- --run useWakeLock`.
- `done`: All cases pass.
