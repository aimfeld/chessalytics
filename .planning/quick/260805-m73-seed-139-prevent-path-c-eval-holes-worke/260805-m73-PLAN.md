<objective>
Close SEED-139: stop Path-C eval holes from being created, instead of resweeping them away by hand.

The seed's measurement is the spec and is not re-litigated here. One root cause (`_NODES_TIMEOUT_S = 5.0`,
a defensive wall-clock guard on a search that always terminates), one concentrated source (~99% of every
hole ever submitted came from two oversubscribed volunteer boxes), and five cheap mitigations, three of
which need no cooperation from the machines causing the problem:

1. **Docs** — REMOTE_WORKER.md advertises CPU oversubscription. Under a node-budget search with a 5s wall
   clock, a position that overruns is discarded rather than merely slowed, so oversubscription converts a
   fast machine into one that submits gaps.
2. **Worker-side retry** — one extra pass, at a longer wall clock, over the positions that came back as
   the all-None engine-failure tuple. On a healthy box this never fires. Preferred over raising
   `_NODES_TIMEOUT_S` globally, which would slow the prod server pool for no benefit.
3. **Stop burning a retry on a submit that made progress** — `apply_completion_decision` increments
   `full_eval_attempts` per *submit*, not per *round*. Prod logs show one game Path-C-submitted by two
   different workers seconds apart (a slow worker overruns `LEASE_TTL_SECONDS = 120`, a second worker
   re-claims, both submit), so two of the three attempts vanish in a single round.
4. **`MAX_EVAL_ATTEMPTS` 3 -> 5** — nearly free since SEED-076 made re-leases incremental. Today *every*
   game that reached attempt 3 succeeded and there is no 4th behind it: the budget is the binding
   constraint, not the engine.
5. **Automate the resweep** — a safety net that stops being a manual chore. Keep it even after 2-4 land.

Purpose: the holed-stamped population stops being replenished, and the repair stops depending on a human
noticing.
Output: a progress-aware attempt charge, a bigger budget, a bounded worker-side retry pass, honest
operator guidance, a daily in-process resweep, regression tests for all five, and SEED-139 closed.

**Not tracer-shaped, deliberately.** These are five independent changes to three already-architected
layers. There is no new end-to-end path to prove with a thin slice; the vertical slice would be the whole
plan. Tasks are grouped by lane (server decision path / worker+engine+docs / periodic task) so each is
independently revertible.

**Explicitly NOT in scope** (the seed's own "deliberately not included"): a server-side worker quality
gate refusing atomic leases to a high-hole-rate worker. `worker_heartbeats` counters are lifetime-
cumulative and documented as passive telemetry only (D-01/D-04); a gate needs a windowed rate plus a
lease-time check, which is a phase, not a seed item. Also out of scope: contacting the two slow-box
operators to lower `--workers` (the seed states this is not a prerequisite for anything here).
</objective>

<decisions>
Recorded here so the executor does not re-derive them.

**D-01 — the no-progress carve-out applies ONLY to the atomic lane (`preserve_existing_evals=True`).**
The seed's own monotonicity argument is scoped to that lane, and the drain lane cannot use it:
`_apply_full_eval_results` counts a hole whenever this pass resolved `None`, but under
`preserve_existing_evals=False` it does not NULL out the row's surviving stored eval, so the drain's
`failed_ply_count` over-counts relative to the DB. Worse, the drain never threads `stored_best_move`, so on
a lichess-eval game its prior-hole count would be *every* non-terminal ply, `post < prior` would hold on
every tick, and the loop would never charge an attempt. That is a D-116-07 violation. Passing `None` from
the drain lane keeps today's per-submit charge with zero blast radius.

**D-02 — the prior count comes from `targets`, not from a query.** `_FullPlyEvalTarget` already carries the
row's pre-write DB `eval_cp`/`eval_mate`/`stored_best_move`; a fresh post-write query would read the state
the write just produced and could never show progress. A new pure helper mirrors the two existing hole
predicates rather than duplicating their logic inline.

**D-03 — termination proof (write it into the docstring).** Under `preserve_existing_evals=True` the write
never replaces a non-NULL eval with NULL, so `failed_ply_count < prior_failed_ply_count` implies the game's
persistent DB hole count strictly decreased. That count is bounded below by 0, so at most `ply_count`
charge-free rounds can occur; every round that does not reduce it charges an attempt, so the game still
reaches Path C after at most `ply_count + MAX_EVAL_ATTEMPTS` submits. The retry loop still terminates.

**D-04 — an optional `timeout_s` on two EnginePool methods, not a global raise.** The worker calls
`EnginePool` directly, so the longer retry wall clock has to come through the method. `timeout_s=None`
resolves to `_NODES_TIMEOUT_S`, so every server-side caller is byte-unchanged. `evaluate`,
`evaluate_nodes`, `evaluate_nodes_multipv5` and the module-level wrappers are NOT touched.

**D-05 — the retry budget is per CYCLE, capped at 8 positions, and `STALL_THRESHOLD_S` rises with it.**
This is the one number the watchdog constrains, so it is derived, not guessed. `STALL_THRESHOLD_S = 600`
already only clears its worst legitimate cycle (~500s at `--workers 1`) by ~100s. A per-*pass* retry cap
would multiply by the three passes `_eval_atomic_game` runs and blow that headroom, and a watchdog kill is
strictly worse than a hole (it discards in-progress analysis and forces an EnginePool rebuild on an
already-slow box). So: `EVAL_RETRY_MAX_POSITIONS = 8` shared across the whole cycle, `EVAL_RETRY_TIMEOUT_S
= 15.0` (3x the pool default), worst-case added wall clock `8 x 15 = 120s` at `--workers 1`, and
`STALL_THRESHOLD_S` goes 600 -> 720 to preserve the same ~100s margin. `STALL_THRESHOLD_S`'s own docstring
already sanctions raising it ("raising it only delays recovery from a GENUINE wedge").

**D-06 — retry the four passes the seed names, and record why the other two are excluded.** Covered:
`_eval_positions` (the actual eval-hole source), `_eval_flaw_blob_positions`, `_eval_atomic_blob_nodes`,
`_eval_targeted_second_best`. Excluded, deliberately: `_eval_entry_positions` (depth-15 / `_TIMEOUT_S`, the
cold entry-ply lane, not the Path-C mechanism the seed measured) and `_eval_bestmove_positions` (tier-4b
gem-candidate rung; a miss costs a candidate the server's own fallback covers, and it is not a
"blob/second-best analogue"). Neither can produce a `game_positions` eval hole.

**D-07 — the automated resweep is unconditional but bounded per tick.** Per the seed's watch-out, the
resweep resets `full_eval_attempts` to 0, so a genuinely unevaluable game would be re-armed every cycle.
Current prod evidence (every swept game gets fixed; the dry run returns 0) makes that acceptable to start.
Do NOT add a `resweep_count` column now; record the escalation path in the docstring instead. The per-tick
`limit` is a burst guard on the drain and the volunteer fleet, not a correctness device.
</decisions>
