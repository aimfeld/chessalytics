<objective>
On mobile, while a Train puzzle reveal is in free-move mode, the fixed bottom bar shows the
board controls instead of the main nav buttons — matching the analysis board's mobile footer.

Purpose: the board controls currently sit at the bottom of the free-play move list, which is
scrolled well below the sticky board on a phone. Putting them in the footer keeps them in
reach exactly like `/analysis` does.

Output: a small cross-tree store (`lib/mobileBoardControls.ts`), a swapped `MobileBottomBar`,
a publisher in `TrainSolveScreen`, and the in-card control strip hidden below `sm`.
</objective>

## Findings from investigation (trust these, re-verify only if something does not match)

**How `/analysis` does it (the pattern to imitate visually, NOT structurally):**
`ProtectedLayout` (App.tsx ~line 631) branches on `isAnalysisRoute` and renders a completely
different shell with NO `MobileBottomBar` at all; the Analysis page then renders its own
in-flow footer (`data-testid="analysis-mobile-footer"`, App-side classes
`shrink-0 border-t border-border bg-background px-2 py-2 pb-safe`) containing
`<BoardControls flat />` with no `size` prop, which makes each button `flex-1 h-12` with `h-5`
icons (see `navStyle` in BoardControls.tsx).

A route-level takeover is NOT viable for `/train`: the Train page scrolls normally, keeps the
standard shell, and free-move mode is a transient state deep inside `TrainSolveScreen`, not a
property of the route. So keep the fixed bar owned by `MobileBottomBar` and swap its contents.

**Cross-tree communication:** `ProtectedLayout` wraps the router `Outlet`, so a page component
cannot pass props up to the bar. The repo already solves exactly this with a module-level
store: `frontend/src/lib/playActive.ts` (`useSyncExternalStore` + a `Set` of listeners, written
by `useMarkPlayActive()` in `TrainSolveScreen` line 211 and `BotsGame`, read by
`usePlayActive()` in App.tsx line 563). Follow that file's shape and docstring style.

**Breakpoint:** the bar is `fixed bottom-0 inset-x-0 flex sm:hidden z-40 bg-background
border-t border-border pb-safe` (App.tsx line 399), i.e. "mobile" here is `< sm` (640px), NOT
the `md` used by the Analysis takeover. The Train reveal only goes two-column at `lg`, so
between `sm` and `lg` the layout is still stacked but the bottom bar is gone — the in-card
control strip must therefore stay visible from `sm` up.

**Where the in-card controls live today:** `TrainExplorationPanel` in
`frontend/src/components/train/TrainReveal.tsx` (~lines 482-501): a
`<div className="border-t border-border px-1 py-1">` wrapping `<BoardControls flat size="md" />`
inside the `train-exploration-moves-card`.

**Free-play state:** `TrainSolveScreen` owns `freePlay = useTrainFreePlay(...)` (line 293) and
`handleFlipBoard` (line 316, a `useCallback` with `[]` deps). `freePlay.goBack` / `goForward` /
`goToRoot` come from `useAnalysisBoard` and are all `useCallback`s. `freePlay.isExploring`,
`canGoBack`, `canGoForward` are booleans. `canReset` is deliberately passed as
`freePlay.canGoBack` at the existing call site (Reset returns to the puzzle position without
leaving free play — do not change that semantic).

**Test harnesses that already exist:**
- `frontend/src/App.test.tsx` renders `MobileBottomBar` standalone via `renderMobileBottomBar()`
  (line 123) inside a router, with the profile/readiness hooks mocked.
- `frontend/src/components/train/__tests__/TrainSolveScreen.test.tsx` starts free-move mode by
  clicking the mocked board's `drop-e2e4` button after a verdict lands (see the Phase 200
  exploration block around line 1284) and wraps renders in `MemoryRouter`.
- `frontend/src/components/train/__tests__/TrainReveal.test.tsx` has `renderReveal({ isExploring: true,
  freePlay: makeFreePlayState() })` (around line 1743).
