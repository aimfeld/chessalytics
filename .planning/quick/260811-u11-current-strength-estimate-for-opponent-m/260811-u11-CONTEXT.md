<decisions>
## Implementation Decisions

### Activity floor — LOCKED

**≥20 qualifying games within the last 90 days** for a rung to be eligible.

Rationale (from the seed's user-3 data): cleanly separates the real rungs (chess.com blitz 317,
lichess blitz 152, lichess rapid 75) from noise (chess.com rapid 11). Wide enough for a stable
median, short enough to track a climb — the anchor's 36-month window is what produced the
190-point error this task fixes.

"Qualifying" means passing the filter in Task Boundary item 4.

### Estimator — LOCKED

**Median of the last 20 qualifying games** in the selected rung.

Rationale: user 3's last-100 rating range was 1482–1567, so a single most-recent sample carries
~±40 of noise and the displayed number would visibly jitter between visits. A 20-game median
damps that while still reacting to a climb within ~20 games. Same statistic as the anchor —
only the window changes, which is precisely the seed's thesis.

### Rung selection — LOCKED (recency-ranked, native-blitz tiebreak)

The seed proposed a fixed ladder (lichess blitz → chess.com blitz → nearest TC). **Superseded.**
See "Cross-platform disagreement is an artifact" below — because every rung normalizes onto the
same lichess-blitz scale, no platform or TC *preference* is needed. The rule is:

1. Enumerate every `(platform, TC)` rung that passes the activity floor.
2. Normalize each rung's 20-game median to lichess-blitz via
   `normalize_to_lichess_blitz(rating, platform, source_tc, is_correspondence=...)`.
3. Rank by **recency** — the `played_at` of the rung's most recent qualifying game.
4. **Native-blitz tiebreak:** when a native lichess-blitz rung is effectively as current as the
   top-ranked rung and their normalized estimates agree closely, prefer the native lichess-blitz
   rung — it carries zero conversion error.

Worked example the user approved (user 3, prod):

```
rungs passing floor (>=20 games / 90d), normalized to lichess-blitz:
  cc blitz    n=317  latest 2026-08-11  -> 1493
  li blitz    n=152  latest 2026-08-10  -> 1532
  li rapid    n=75   latest 2026-07-29  -> 1349
  cc rapid    n=11    FAILS FLOOR

most recent -> cc blitz (1493)
near-tie with li blitz (39 pts, both active) -> native tiebreak -> 1532
```

The user's driving concern, in their words: *"Recency is a big factor here. Current active
chess.com rapid rating beats a 2 year old lichess blitz rating."* Note the 90-day floor already
guarantees this — a 2-year-old rung fails the floor and never competes. The recency ranking
additionally handles the within-window case (a rung whose 20 games all sit at the far edge of
the 90 days loses to one active this week).

<specifics>
## Specific Ideas

### Cross-platform disagreement is an artifact — seed correction

The seed's fourth open question ("user 3's native medians differ by ~400 points, chess.com blitz
1118 vs lichess blitz 1532") compares **native** ratings on two different scales. Running both
through `normalize_to_lichess_blitz` (verified 2026-08-11 against the real conversion service):

| rung | native | → lichess-blitz |
|---|---|---|
| chess.com blitz, 90d | 1118 | **1493** |
| lichess blitz, 90d | 1532 | **1532** |

**39 points apart, not 400** — inside the ±40 single-sample noise band. Cross-check on the
anchor window from the seed: chess.com native 941 → 1370, lichess native 1372 → 1372, a 2-point
agreement. That is exactly *why* the seed observed "the blend lands on the lichess median" — the
platforms were never disagreeing.

Two consequences the plan should carry:

1. The seed's "worth sanity-checking the converted chess.com rung against the lichess rung
   before trusting rung 2 alone" is **already answered** for the motivating user. No separate
   research step needed.
2. Because normalization puts every rung on one scale, TC is not a barrier either
   (lichess rapid 1532 → 1349). This is what removes the need for a platform/TC preference
   ladder and leaves recency as the only ordering signal.

### Verification target

Prod user 3 is the regression case: anchor says **~1370**, lichess blitz reality is **~1560**,
and the deleted `get_current_rating_by_platform` said **1340**. The new estimate should land
near 1532 per the worked example above. Verify against the dev DB or via the prod read-only
tunnel (`bin/prod_db_tunnel.sh`); do NOT gate completion on `bin/reset_db.sh`.

### Out of scope

- `store_bot_game_service` keeps stamping finished bot games with the **anchor** rating. Bot
  games are `rated=false, is_computer_game=true` and are excluded from both the anchor pipeline
  and the new estimator, so there is no feedback loop to fix here.
- No live platform API fetch (seed locked decision 4).
