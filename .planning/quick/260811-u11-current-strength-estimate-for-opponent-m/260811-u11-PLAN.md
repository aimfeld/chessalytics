<objective>
Add a current-strength estimate — median of the last 20 rated human games on the most
recent sufficiently-active (platform, time-control) rung, normalized to the Lichess blitz
scale — and repoint all three opponent-matching surfaces at it, replacing the 36-month
career rating anchor there.

Purpose: the Bots page currently tells an improving player they are ~190 points weaker
than they are, and that number is pointed straight at a decision ("pick a bot near this
for an even game"). The career-median anchor is the right input for the percentile chip
and the wrong input for "who should I play right now".

Output: one repository query, one service holding the whole selection policy, one nested
wire field, three repointed frontend call sites, and a popover that names the rung the
number came from.
</objective>

<locked_decisions>
From `260811-u11-CONTEXT.md` (which supersedes the seed's open questions). Final — do not
revisit, do not substitute a simpler alternative.

- **D-01 Activity floor:** a rung is eligible only with **>=20 qualifying games in the
  last 90 days**.
- **D-02 Estimator:** **median of the last 20 qualifying games** on the selected rung.
- **D-03 Rung selection:** enumerate every `(platform, TC)` rung passing the floor,
  normalize each rung's median to lichess-blitz via `normalize_to_lichess_blitz`, rank by
  **recency** (the `played_at` of the rung's most recent qualifying game), then apply a
  **native-blitz tiebreak**: a native lichess-blitz rung that is effectively as current as
  the top rung and whose normalized estimate agrees closely wins, because it carries zero
  conversion error. No platform or TC *preference* ladder — normalization already puts
  every rung on one scale, so recency is the only ordering signal.
- **D-04 Qualifying games:** sourced through `apply_game_filters` — `rated=True`,
  `opponent_type="human"`, `platform=None` (which applies the
  `DEFAULT_EXCLUDED_PLATFORMS` exclusion). Never a hand-rolled predicate, and never an
  unfiltered "rating from the most recent game" query: that exact shape read FlawChess's
  own bot-game rating stamps back as the user's rating (1340 for prod user 3) and was
  deleted on 2026-08-11.
- **D-05 Surfaces repointed (all three):** the PersonaGrid rating line
  (`Bots.tsx:757` -> `PersonaGrid`), the custom-bot ELO default (`Bots.tsx:741` ->
  `resolveDefaultBotElo`), and the analysis free-play ELO default
  (`useMaiaEloDefault.deriveRawDefault`).
- **D-06 Untouched:** `user_rating_anchors` (schema, pipeline, and every percentile
  reader — `user_benchmark_percentiles_service`, `feedback_service`),
  `canonical_slice_sql.py`, `store_bot_game_service` (it keeps stamping bot games with the
  anchor; bot games are excluded from both pipelines so there is no feedback loop), and
  `useMaiaEloDefault`'s **game-mode** branch (rating-at-game-time from `gameData` — a
  different question). **No Alembic migration** — this is a derived read-time value.
- **D-07 Fallback:** when no rung passes the floor, fall back to the existing blitz-bucket
  anchor so low-activity and newly-imported users are unaffected.

## Planner discretion, exercised (CONTEXT §Claude's Discretion)

- **P-01 `lichess_blitz_equivalent_rating` is REMOVED from the wire.** All three of its
  consumers repoint (D-05) and the anchor fallback (D-07) now happens server-side inside
  `current_strength`, so the field would be left on the wire with zero readers. That is
  precisely the WR-04 / `current_rating` trap the seed spent a section closing. The anchor
  itself is untouched (D-06) and still read from the DB by `store_bot_game_service`; only
  the profile response field, the `_lichess_blitz_equivalent_rating` router helper, and the
  frontend `UserProfile` field go away.
- **P-02 Tiebreak constants:** native lichess blitz wins when its most recent qualifying
  game is within **7 days** of the top rung's AND the two normalized estimates are within
  **50 points**. Named constants, not literals at the comparison site.
- **P-03 Wire shape:** one nested object with a discriminated rung — `{ rating, source,
  rung }` where `rung` is non-null exactly when `source == "recent_games"`. Every field
  inside `rung` is then non-optional and meaningful; no tri-state siblings.
- **P-04 Layering:** SQL in a new dedicated repository module (generic — takes the window
  and sample size as arguments), all policy constants and the whole ranking decision in a
  new service module, service returns the Pydantic response schema (the established
  pattern — `library_service` returns `GameFlawCard`).
- **P-05 Correspondence + window source:** correspondence games are excluded in the
  repository via `normalization.CORRESPONDENCE_TC_SEPARATOR` (the module's own canonical
  signal), so the service always calls `normalize_to_lichess_blitz(...,
  is_correspondence=False)`. "Now" comes from the `dev_now_utc` dependency, never an inline
  clock read inside the service or repository (CLAUDE.md dev-clock rule — the profile
  endpoint becomes time-dependent with this change).
