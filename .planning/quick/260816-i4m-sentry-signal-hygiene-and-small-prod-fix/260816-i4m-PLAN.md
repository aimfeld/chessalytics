<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Sentry ingest | Client-side error payloads leave the user's browser for a third-party service |
| vendored ORT WebGPU bundle → worker host | Third-party runtime errors cross into our error-handling path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-i4m-01 | Information Disclosure | `sentryBeforeSend` request attachment (`instrument.ts`) | low | mitigate | Attach `config.url` + `config.method` only. No headers, no request body, no cookies, no auth token — the three `RequestEventData` fields that could carry credentials are never populated. URLs are app-relative API paths already visible in the user's own network tab. |
| T-i4m-02 | Denial of Service | Maia wasm-fallback respawn (`maiaWorkerHost.ts`) | low | mitigate | Fallback is gated on `backend === 'webgpu'` and the replacement is pinned to wasm, so it is structurally one-shot per worker lifetime — a repeated-error respawn loop (each spawn costing a fresh ~226 MB ONNX heap) cannot occur. |
| T-i4m-03 | Repudiation | `ignoreErrors` / `denyUrls` additions | low | accept | Both patterns drop events that are unactionable by construction (a `sw.js` fetch failing means the network is gone; `beacon.min.js` frames are third-party analytics code). Accepted: the deliberate outage-signal keep at `instrument.ts:27-49` is left untouched, so the one filter that could mask a real Caddy/host outage is unchanged. |

No package-manager installs in this plan, so no package-legitimacy gate applies.
</threat_model>
