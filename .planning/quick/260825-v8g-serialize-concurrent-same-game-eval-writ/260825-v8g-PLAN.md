<objective>
Serialize concurrent same-game eval writes by taking a per-game, transaction-scoped
PostgreSQL advisory lock at the top of `apply_full_eval`.

Purpose: Sentry FLAWCHESS-9F and FLAWCHESS-8G are the two victims of one PostgreSQL
deadlock cycle (2026-08-23 08:02:04/05), both on `POST /api/eval/remote/atomic-submit`,
both for `game_id=2361356`. Three concurrent submits for the same game landed at once.
`_apply_full_eval_results` emits two separate `UPDATE game_positions ... FROM (VALUES ...)`
statements — `_batch_update_best_move_rows` (line 361, called at 732) then
`_batch_update_eval_rows` (line 439, called at 733) — with partially overlapping ply sets.
Row-lock acquisition order across two separate statements is planner-dependent, so
transaction A can hold ply 9 and want ply 55 while B holds 55 and wants 9. The same window
also contains `_classify_and_fill_oracle` (line 940), whose per-ply DELETE/INSERT/UPDATE
diff against `game_flaws` is a correctness hazard under a same-game race, not merely a
deadlock one. One lock covers both.

Output: a named namespace constant + key helper and one `pg_advisory_xact_lock` call in
`app/services/eval_apply.py`, a docstring paragraph explaining the bug, and two real-database
tests in `tests/services/test_eval_apply.py` that fail if the lock line is removed.
</objective>

Already diagnosed — do NOT re-derive any of this.

| PID | txid | statement |
|---|---|---|
| 1731133 | 3321961 | `_batch_update_eval_rows`, plies 0-58 (FLAWCHESS-8G) |

Why concurrent same-game submits happen at all: `_apply_atomic_submit`
(`app/routers/eval_remote.py:1162`) takes `game_id` straight from the request body and does
NO lease-ownership check. The tier-3 atomic-lease lottery releases its lease at commit, well
before the worker's engine gather runs, so TTL reclaim / a re-lottery hands the same game to
several workers, all of which eventually submit. That is intentional — submits are meant to be
idempotent — and this task does NOT change the lease model.

Impact today is low: 5 events in ~7 weeks, 0 users. The write session is one transaction
(T-117-11) so rollback is clean — no partial state, `full_eval_attempts` is not incremented,
the game stays pending and is re-leased. The cost is wasted worker CPU plus a 500.

One correction to the original brief: `_classify_and_fill_oracle` is no longer a blanket
delete-then-insert. Phase 150 R3 replaced that with a per-ply 4-way diff/upsert (DELETE for
plies that are no longer flaws, INSERT for new ones, two UPDATE buckets). It is still a
read-then-write sequence over `game_flaws` for one game, so it is still a same-game race
hazard and still needs to be inside the lock. Describe it accurately in the docstring — do not
call it delete-then-insert.

Rationale for this fix shape (already decided — do not re-litigate):
- `pg_advisory_xact_lock` releases automatically at COMMIT or ROLLBACK. No leak path, no
  explicit unlock, safe under the WR-01 fail-closed contract where exceptions propagate.
- A namespace keeps the key space disjoint from any future advisory-lock user.
- Placing it inside `apply_full_eval` covers BOTH lanes (router + drain).
- Sorting the VALUES lists by ply is strictly weaker: it does not bind the planner and does
  nothing across two separate statements. Rejected.
</investigation_notes>

| Boundary | Description |

| application → PostgreSQL | The advisory key is derived from that worker-supplied `game_id`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-V8G-01 | Denial of Service | `apply_full_eval` advisory lock | low | mitigate | The lock is `pg_advisory_xact_lock`, released at COMMIT/ROLLBACK, and is scoped to one `game_id`. A hostile or looping worker can stall only writers for the same game, for the length of one already-bounded write transaction. It cannot leak a lock, because there is no session-scoped acquisition and no explicit unlock path to skip. |
| T-V8G-02 | Tampering | advisory key derivation from request-body `game_id` | low | accept | The key is an integer derived arithmetically from `game_id` and passed as a bound parameter — never interpolated into SQL, so there is no injection surface. A forged `game_id` can only contend for a lock; every write it would then attempt is already governed by the pre-existing FK and ownership constraints on `game_positions` / `game_flaws`. Ownership enforcement at submit is out of scope for this task and is deferred by explicit decision. |
| T-V8G-03 | Denial of Service | key-space collision with `tests/conftest.py`'s template lock | low | mitigate | Namespace constant places production keys at `namespace << 32` ≈ 5.07e18, disjoint from the conftest key `7_777_777_777`; the namespace is a named constant precisely so the disjointness stays checkable. |
