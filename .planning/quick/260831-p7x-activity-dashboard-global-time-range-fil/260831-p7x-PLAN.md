<objective>
Add a global time-range filter to the superuser Activity Pulse dashboard at `/activity`.

Four presets in a fixed order (All time, Last 90 days, Last 30 days, Last 7 days), all
aggregation done server-side against the requested window only, the whole page responding
with no exempt card, and the existing Audience toggle left structurally untouched.

Purpose: make the dashboard answerable for "what is happening now" instead of only
"what has happened ever", without moving aggregation into the browser and without
paying for four windows on every request.

Output: a range-parameterised `GET /api/admin/activity/stats`, a range-keyed `StatsCache`,
a window-aware and empty-safe render layer, and a React-owned range control.

<architecture_notes>
Read this before Task 1. It records decisions already settled with the developer and the
verified facts they rest on. Do not re-open them.

**Locked decisions (non-negotiable):**
- D1 — exactly four presets, in the order All time (default), Last 90 days, Last 30 days,
  Last 7 days. No `Today`. No custom ranges, now or ever.
- D2 — hard global cut. Every card responds. No exemptions.
- D3 — cohort cards window on cohort ENTRY and follow forward to today, not on event date.
  Where a short window makes a point undefined, show fewer points. Never fabricate, never
  zero-fill a truncated tail.
- D4 — fetch only the current window. One request builds one window.
- D5 — all aggregation in SQL. The client renders what it is given.
- D6 — range is React state and part of the query key. Audience stays a render.js module
  variable exactly as it is today.

**Why the cohort cards need almost no SQL change.** `fetch_funnel`, `fetch_time_to_import`,
`fetch_stickiness`, `fetch_conversion` and `fetch_conversion_compare` already take a
`first_day` and already constrain only `users.created_at`; their joined `import_jobs`,
`games`, `bot_game_settings` and `user_activity` CTEs are already unfiltered. That is
exactly D3's "entry-windowed, followed forward to today". Passing the window start instead
of the data start is the entire change for those five.

**Why the rolling metrics get a lead-in instead of a SQL rewrite.** DAU/WAU/MAU are
computed in `render.js`'s `sets()`/`rolling()` from the per-(user, day) activity rows,
because the Audience toggle re-filters those same rows client-side. Moving the rolling
counts into SQL would force three precomputed audience variants or lifting Audience to the
server, and D6 forbids lifting Audience. So the server instead ships
`ROLLING_LEAD_IN_DAYS` extra days before the window start for the two series that feed a
rolling computation (activity, solves) plus a `window_start_index` marker, and render.js
trims those lead-in days off before plotting. The lead-in is 29 days: the widest rolling
window in the page is the 30-day MAU, so 29 prior days make the window's first visible day
already correct.

**Why adding a date cutoff is safe for range=all.** For `range="all"` the window start
equals `min(user_activity.activity_date)`. Today `fetch_bot_games`, `fetch_bot_players`,
`fetch_train`, `fetch_solves`, `fetch_persona` and `fetch_elo` have no date predicate at
all, but `render.js`'s `expand()` resolves each series' first day with
`DAYS.indexOf(first)` and would return -1 for any row predating `days[0]` — so the client
already assumes no event row predates the activity-tracking start. Adding the cutoff
enforces that assumption rather than changing behaviour. Verified against the dev DB on
2026-08-31: activity starts 2026-06-26; first bot game 2026-07-29, first drill session and
first solve 2026-08-04, all after it. `games.played_at` is nullable in the model but no bot
game has a NULL value and `app/services/bot_game_pgn.py` raises rather than storing one.
`import_jobs.started_at` and `users.created_at` DO predate activity tracking, which is
precisely why those queries already carry the `first_day` predicate; leave that behaviour
alone.

**Verified crash sites in the current render layer (an empty window hits all of them).**
`render.js` `expand()` reads `rows[0][0]`; `chrome()` reads `BOT[0][0]` and `TRAIN[0][0]`;
`tiles()` divides by `T.botGames` and by `T.done + T.expired`; the funnel table and the
time-to-import chart divide by `FUNNEL[0][1]` / `FUNNEL[0][2]`; stickiness divides by
`r[1]`/`r[3]`; conversion divides by `CONV.sessions` and by `CONV.avg_days_guest`;
conversion-compare divides by `r[2]`/`r[4]`. `charts.js` `funnel()` divides by
`rows[0].value`. These must be guarded regardless of architecture.

**The layout harness is a regression guard only.** `frontend/scripts/check-activity-layout.mjs`
loads only `charts.js` and `styles.css` and drives them with synthetic fixtures. It never
renders `ActivityPage.tsx` or `render.js`. Run it; budget no work for extending it.

**Already applied, do not touch.** A one-line fix to the `#conv-exp` snake_case field names
is already in the working tree. Do not revert it and do not re-apply it.
