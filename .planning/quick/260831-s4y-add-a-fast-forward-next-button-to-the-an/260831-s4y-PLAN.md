Create `frontend/src/hooks/useFastForward.ts`.

Module constants, both exported and both consumed in-file (satisfies knip's `ignoreExportsUsedInFile`):
- `FAST_FORWARD_STEP_MS = 200` with a comment explaining it is the per-ply replay cadence (D-01) and that it is the ONE knob controlling replay speed.

Export a pure helper `nextStopPly(currentPly: number, stopPlies: ReadonlySet&lt;number&gt;, lastPly: number): number | null`. Semantics: scan `currentPly + 1 .. lastPly` ascending and return the first member of `stopPlies`; if none is found and `lastPly &gt; currentPly` return `lastPly` (D-04 — the final position is the implicit terminal stop); otherwise return `null`. Pure and total, so the whole target-selection rule is unit-testable without React.

Export the hook `useFastForward(options: UseFastForwardOptions): UseFastForwardReturn` with these exported interfaces:
- `UseFastForwardOptions`: `enabled: boolean`, `mainLine: readonly NodeId[]`, `currentNodeId: NodeId | null`, `currentPly: number | null`, `stopPlies: ReadonlySet&lt;number&gt;`, `goToNode: (id: NodeId, opts?: { silent?: boolean }) =&gt; void`.
- `UseFastForwardReturn`: `start: () =&gt; void`, `isRunning: boolean`, `canFastForward: boolean`.

Implementation shape:
- `canFastForward = enabled && mainLine.length &gt; 0 && (currentPly ?? -1) &lt; mainLine.length - 1`. The `?? -1` is load-bearing: `currentPly` is null at the root, which is one ply BEFORE ply 0, so the root must still be able to fast-forward (D-04 — disabled only at the very end).
- `start()` is a no-op when `!canFastForward` or a run is already in flight (guard on a `runningRef`, not on the `isRunning` state, so a double click within one commit cannot start two timer chains). Compute `target = nextStopPly(currentPly ?? -1, stopPlies, mainLine.length - 1)`; bail when null. SNAPSHOT `mainLine` and `target` into a run-plan ref at start time and drive the ticks off that snapshot — the loop then needs no ref-sync effect and no stale-closure dance, and a mid-run `loadMainLine` is caught by the cancellation guard below anyway.
- Drive the replay with a self-rescheduling `setTimeout` chain stored in a `timerRef` (not `setInterval`): each tick advances a cursor ply, resolves `mainLine[ply]`, and calls `goToNode`. Guard the index for `noUncheckedIndexedAccess` and stop the run if a node id is missing rather than skipping ahead.
- Intermediate steps call `goToNode(id, { silent: true })`; the LANDING step (cursor reaches `target`) calls `goToNode(id)` unsilenced. Rationale in a comment: five sounds per second for a long replay is the exact machine-gun failure `handleEvalChartPlyChange` documents, but the arrival is a single deliberate event worth hearing.
- Cancellation (D-05): keep an `expectedNodeIdRef`. `start()` seeds it with the current `currentNodeId`; each tick sets it to the id it is about to command. An effect on `currentNodeId` stops the run whenever a run is in flight and `currentNodeId !== expectedNodeIdRef.current`. This single guard covers back, forward, reset, move-list clicks, eval-chart scrub, arrow keys and the wheel WITHOUT touching any existing handler — a foreign navigation is by definition a committed node the hook did not command.
- `stop()` clears `timerRef`, clears `runningRef`, and sets `isRunning` false. Register a mount-scoped cleanup effect (`useEffect(() =&gt; () =&gt; clearTimeout(...), [])`) so unmount kills the pending timer.
- No rewind command exists anywhere in this file (D-03).

Write the failing tests in `frontend/src/hooks/__tests__/useFastForward.test.ts` FIRST, covering the `<behavior>` cases. Use `vi.useFakeTimers()` in `beforeEach`, `vi.useRealTimers()` in `afterEach`, and advance with `act(() =&gt; { vi.advanceTimersByTime(...) })`. Do NOT reach for a bare `waitFor` on a timer-driven transition — testing-library's 1000ms waitFor ceiling is independent of the 5s test timeout and is a known flake source in this repo. Drive `renderHook` with a rerender-able props object so `currentNodeId` can be moved between assertions.

Then add the two optional props to `frontend/src/components/board/BoardControls.tsx`:
- `onFastForward?: () =&gt; void` with a doc comment stating the button renders only when this is supplied, and that Openings/Bots/Train deliberately share this bar without it (D-07).
- `canFastForward?: boolean`.
Render the new button between the existing Forward and Flip buttons (D-06), guarded by `{onFastForward && ( ... )}`. Copy the exact shape of the Forward button: `<Tooltip content="Fast forward to next key moment">`, `variant="ghost"`, `size="icon"`, `className={`${buttonSizeClass} hover:bg-accent`}`, `disabled={!canFastForward}`, `aria-label="Fast forward to next key moment"`, `data-testid="board-btn-fast-forward"`, and `<FastForward className={iconSize} />` from the existing lucide-react import line. No hand-rolled colors or sizes.

Then wire `frontend/src/pages/Analysis.tsx`. Insert immediately after the `flawMarkerByNodeId` memo (~line 1743), so every dependency is already in scope and hook order stays unconditional:
- A `fastForwardStopPlies = useMemo&lt;Set&lt;number&gt;&gt;(...)` over `gameData?.flaw_markers` (add `fm.ply` when `fm.severity` is `blunder` or `mistake`) and `gameData?.eval_series` (add `point.ply` when `isRareMoveTier(point.best_move_tier)`). Return an empty set when `!isGameMode`. Deps `[isGameMode, gameData?.flaw_markers, gameData?.eval_series]`. Comment WHY there is no `is_user` / `user_color` filter: the stop set is both-sides by decision (D-02), matching the analysis board's existing both-sides gem display. Also comment WHY this derives tiers from `eval_series` directly rather than reusing the nearby `storedTierByPly` map: that map additionally requires `maia_prob != null`, a TypeScript-narrowing artifact that could silently drop a legitimate stop.
- `const fastForward = useFastForward({ enabled: isGameMode, mainLine, currentNodeId, currentPly: evalChartPly, stopPlies: fastForwardStopPlies, goToNode })`. Passing `evalChartPly` (not a raw `currentPly`) is deliberate: from a sideline it resolves to the fork point, so a fast-forward from a sideline resumes along the main line and leaves the sideline in the tree one click away — the same behavior the eval-chart scrub already has.
- In the `boardControls(flat, size)` helper (~3232), pass `onFastForward={isGameMode ? fastForward.start : undefined}` and `canFastForward={fastForward.canFastForward}`. This one helper feeds both the desktop card (~3416) and the mobile footer (~4029), which is what delivers mobile/desktop parity (D-08).
