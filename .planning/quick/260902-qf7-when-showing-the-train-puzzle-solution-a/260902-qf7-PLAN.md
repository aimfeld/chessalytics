<objective>
On the Train puzzle reveal, show the played-in-game move by default: the thin white
arrow plus its move-quality corner badge, on the pristine (un-spotlit) solution board.

Purpose: when a puzzle is mined from the user's own game, "what did I actually play
here" is the single most instructive comparison on the reveal board — and today it is
invisible unless the user happens to hover or tap the "Played in game" legend card.
Phase 200 UAT deliberately made the game arrow hover-only; the developer is reversing
that call now. This plan is that reversal, scoped to the game move only.

Output: a one-line behavior change plus the doc comments and the regression test that
currently lock in the opposite contract.
</objective>

1. **The data already exists end to end.** `PuzzleRevealResponse.played_in_game_move_uci`

   (SAN parsed to UCI, `None` when unparseable or absent). No backend or schema change
   is needed. `frontend/src/types/train.ts:163` already types it.

2. **The arrow already exists.** `buildTrainRevealOverlay` in
   `frontend/src/lib/trainArrows.ts` unconditionally pushes the thin white game arrow
   (`NEXT_MOVE_ARROW`, `TRAIN_GAME_MOVE_ARROW_WIDTH = 0.18`, `onTop: true`,
   `layerKey: 'game'`) whenever `gameMove !== null`, and already calls
   `pushMarker(gameMove.uci, gameMove.quality)` under precedence
   played > best > fine > game.

3. **The badge already exists.** `TrainSolveScreen.tsx`'s `gameMoveQuality` memo
   (~line 681) derives it: `'best'` when the game move IS the engine best, the played
   move's own quality when they coincide, otherwise `classifyTrainMoveQuality` over the
   reveal-time search's eval (`gameMoveLine`, reported up from `TrainReveal` via
   `onGameMoveLineChange`). `markerForQuality` renders the shared `SquareMarker` corner
   glyphs — the same set the analysis board uses.

4. **The ONLY thing hiding it is the default spotlight set.** `pristineOverlayUcis`
   (`TrainSolveScreen.tsx` ~line 731) is `[lastPlayedUci, bestMoveUci]`, and
   `applyTrainSpotlight` filters the overlay down to it whenever nothing is spotlit.
   Its own docblock says so explicitly ("The played-in-game arrow and the 'Also fine'
   alternatives are hover/tap-only"). Adding `gameMoveUci` to that array is the whole
   behavior change.

5. **One existing test asserts the OPPOSITE contract** and will fail — by design:
   `frontend/src/components/train/__tests__/TrainSolveScreen.test.tsx`, the test named
   `'the pristine board draws ONLY the your-move and best-move arrows — the
   played-in-game arrow appears only while its own box is hovered (Phase 200 UAT)'`
   (~line 892). It asserts `data-arrows-count === '2'` and `data-markers-count === '2'`
   pristine. This is the Phase 200 UAT decision being reversed; rewrite it, do not
   delete it.

6. **Tests that must keep passing unchanged** (verified as unaffected by planning-time
   reading, but re-run them):

     Its reveal mock has `played_in_game_move_uci: null`, so the new set contributes
