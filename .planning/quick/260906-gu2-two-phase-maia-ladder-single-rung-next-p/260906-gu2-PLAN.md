# Two-phase Maia ladder + single-rung next-ply prefetch on the analysis board

## Problem (measured 2026-09-06, wasm backend, 16-core Linux desktop)

The Maia chart's `useMaiaEngine` requests all 21 `MAIA_ELO_LADDER` rungs in one batch. On the
single-threaded wasm backend batching amortizes nothing: ~200 ms per rung, ~4 s for the ladder
(2 s on the user's machine). The FlawChess engine's root `policy()` call (non-priority lease on the
same worker) waits behind the whole ladder, so the engine card lands ~300 ms after the chart.

| batch | wasm time |
|---|---|
| 21 rungs | 3.9–4.5 s |
| 1 rung | 185–220 ms |

A 400-node engine search is ~400 `policy()` calls ≈ 60–80 s of serialized Maia time, so the worker
is never idle while a position is displayed. Any prefetch must be a fixed, small tax (one rung).

## Design (locked in chat)

1. **Two-phase ladder** in `useMaiaEngine`: request `[selectedElo]` (exact, un-snapped — the engine
   calls `policy(fen, selectedElo)` with the exact slider value, so this is the only rung that can
   serve it through `maiaPolicyCache`) → paint `wdl`/`expectedScoreAtSelectedElo` → then the
   remaining ladder rungs. `perElo` keeps its contract: ladder rungs only, complete or `[]`, so the
   chart / quality bar / verdict / gem classification / `maiaCurveByFen` are byte-identical in what
   they see, just ~200 ms later than today. The eval bar and the engine's root policy arrive at
   ~200 ms instead of ~4 s.
2. **Single-rung prefetch** of the next ply on the current line: `[selectedElo]` for `prefetchFen`,
   issued between phase 1 and phase 2 of the current position (so a quick forward step hits the
   cache even before the chart lands). Cost: one ~200 ms inference per navigation.
3. **Pending-policy coordination** in `maiaPolicyCache`: the hook marks `(fen, elo)` pending when
   it issues a request; `maiaQueue.policy()` awaits a pending entry instead of issuing a duplicate
   inference (today the engine's root call and the chart both infer the same FEN — the duplicate
   would otherwise cost the engine an extra 200 ms on every navigation).
4. `useGemSweep` passes `ladderOnly: true` — its instance never needs phase 1 or a prefetch, so the
   sweep stays byte-identical.

Pipeline order per position (single request in flight from the hook, re-planned on every
completion / input change): `live exact rung` → `prefetch exact rung` → `live remaining ladder`.
A FEN change mid-pipeline simply re-plans for the new FEN; nothing is cancelled (ORT can't) but
nothing further is issued for the old FEN.

## Tasks

### Task 1 — `maiaPolicyCache` pending registry + `maiaQueue.policy()` awaits it
- `frontend/src/lib/engine/maiaPolicyCache.ts`: `markPolicyPending(fen, elo)`, `getPendingPolicy(fen, elo)`,
  `failPolicyPending(fen, elo, err)`; `setCachedPolicy` resolves a pending entry; `clearMaiaPolicyCache` clears both.
- `frontend/src/lib/engine/maiaQueue.ts`: `policy()` → cached ? resolve : pending ? await (fall back to own request on rejection) : own request.
- Tests: `maiaPolicyCache.test.ts` (pending lifecycle), `maiaQueue.test.ts` (pending path issues zero `analyze()` calls; rejection falls back).

### Task 2 — `useMaiaEngine` two-phase pipeline + prefetch
- `frontend/src/hooks/useMaiaEngine.ts`: per-FEN cache holds `rungs: Map<elo, {moveProbabilities, wdl, uci}>` + derived `ladder` (complete-or-empty);
  `planNextRequest()` pure planner; new options `prefetchFen?: string | null`, `ladderOnly?: boolean`.
  `isAnalyzing` = a request for the CURRENT fen is in flight (prefetch excluded). `perElo` = ladder. `wdl` = nearest over all inferred rungs (exact rung wins at distance 0).
- Tests: update ladder expectations; add phase-order, prefetch-hit-on-navigation, ladderOnly, pending-mark tests.

### Task 3 — Wire the analysis board
- `frontend/src/lib/nextLineFen.ts` (+ test): mainline child if on the main line, else first child.
- `frontend/src/pages/Analysis.tsx`: `prefetchFen` memo → `useMaiaEngine({ prefetchFen })`.
- `frontend/src/hooks/useGemSweep.ts`: `ladderOnly: true`.
- Gate: `npm run lint && npm test -- --run && npm run build` (tsc -b), then CHANGELOG `[Unreleased]` bullet.
