# Cap the Maia ORT wasm memory reservation at 1 GB (iOS OOM), and send COOP/COEP on dev 304s

Fixes FLAWCHESS-9V (`no available backend found. ERR: [wasm] RangeError: Out of memory`).

## Problem A: WebKit's three-reservation budget (prod defect)

Verified 2026-09-06 on the reporter's iPhone 14 Pro (iOS 26.6.1, Safari; Sentry labels it "iOS 18.7"
because Apple froze the UA token) with a throwaway diag page:

1. WebKit lets ONE page hold only **three** large wasm memory reservations. A 4th
   `new WebAssembly.Memory({initial:256, maximum:65536, shared:true})` throws
   `RangeError: Out of memory`. Six 1 GB shared memories fit at once, so the binding constraint is
   address space, not device RAM (the phone has 6 GB).
2. Both vendored ORT binaries (`ort-wasm-simd-threaded.wasm`, `ort-wasm-simd-threaded.asyncify.wasm`)
   IMPORT a shared memory declared `min 256 / max 65536` pages, so each glue loader
   (`ort-wasm-simd-threaded.mjs`, `ort-wasm-simd-threaded.asyncify.mjs`) contains exactly ONE literal
   `new WebAssembly.Memory({initial:256,maximum:65536,shared:!0})` and reserves 4 GB even at
   `numThreads = 1`.
3. The Stockfish pool (2 workers on mobile) takes two of the three slots. On iOS 26 (WebGPU with
   `shader-f16` present) the Maia host tries a WebGPU worker first (reservation 3), then on
   `webgpu-unavailable` respawns a wasm-pinned worker (reservation 4) while the first is still dying.
   That 4th reservation is FLAWCHESS-9V.

A smaller `maximum` on an IMPORTED memory is legal as long as it stays `<=` the module's declared max.
`shared:false` is NOT legal (import type mismatch), so the shared flag must stay. Patching
`maximum:65536` to `maximum:16384` (1 GB) was tested on the phone with the real 45 MB model: the
session created fine while one Stockfish worker plus a leftover 4 GB reservation were alive, which is
exactly the situation that fails with stock glue.

## Problem B: Vite answers 304 without the configured headers (dev-only defect)

Reproduced 2026-09-06 against the running dev server (`http://127.0.0.1:5173`):

```
$ curl -sI .../engine/stockfish-18-lite-single.js          # 200
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
ETag: W/"21429-1782500182991"
Cache-Control: no-cache

$ curl -s -D - -o /dev/null -H 'If-None-Match: W/"21429-1782500182991"' ...   # 304
HTTP/1.1 304 Not Modified
Vary: Origin
Date: ...
Connection: keep-alive
```

`server.headers` (Phase 219 D-05) is applied on the 200 path only. Because dev sends
`Cache-Control: no-cache`, every second load revalidates, and WebKit blocks a worker script whose 304
lacks COEP (WebKit bug 245346). Symptom: the SECOND Stockfish pool worker (same glue URL) dies within
~10 ms with a bare `error` Event while distinct URLs start fine. Prod is unaffected: Caddy's `header`
directive does emit on 304s (`referrer-policy` is visible on prod 304s).

## Task 2: send COOP/COEP on every dev and preview response, including 304

**Files**

- `frontend/vite.config.ts`

**Action**

1. Add a module-level `const CROSS_ORIGIN_ISOLATION_HEADERS: Record<string, string>` holding
   `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, and
   use it as the value of both `server.headers` and `preview.headers` (single source of truth, both
   existing blocks stay as a second line of defense on the 200 path).

2. Add a small inline plugin next to `ogImageHashPlugin`/`forceExitAfterBuild`:

   ```
   crossOriginIsolationPlugin(): Plugin
     - one shared handler typed (server: ViteDevServer | PreviewServer) => void
     - server.middlewares.use((_req, res, next) => { set both headers via res.setHeader; next() })
     - returned from BOTH configureServer and configurePreviewServer
   ```

   Register it FIRST in the `plugins` array so its middleware is installed ahead of Vite's static and
   transform middlewares and ahead of VitePWA's dev middleware. Registering inside the hook body (not
   returning a function from the hook) is what makes it a pre-middleware. Extend the existing `vite`
   import with `type ViteDevServer, type PreviewServer` (`verbatimModuleSyntax` requires the inline
   `type` modifiers); both interfaces expose `middlewares: Connect.Server` in Vite 8.2.2 (verified).
   `noUnusedParameters` is on, so the unused request parameter must be named `_req`.

3. Replace the Phase 219 D-05 comment on `server.headers` with one that explains the gap this plugin
   closes: `server.headers` is applied on the 200 path only, dev sends `Cache-Control: no-cache` so
   every second load revalidates, and WebKit blocks a worker script whose 304 lacks COEP (WebKit bug
   245346), which killed the second Stockfish pool worker (same glue URL) within ~10 ms with a bare
   `error` Event. Note that prod Caddy does emit its `header` directives on 304s, so this is a
   dev-and-preview-only gap. Keep it short and free of em-dashes.

**Verify**

Do NOT kill the dev server the user is running on 5173 (Vite restarts it by itself when
`vite.config.ts` changes, which is expected). Use a throwaway port instead:


  WebGPU worker is still dying). The 1 GB cap makes that overlap survivable, which is what was tested
  on the phone. Awaiting termination first is a separate, riskier change; flag it as a follow-up
  rather than folding it in here.
- The `.wasm` binaries, the API bundles, and prod `deploy/Caddyfile` (already correct on 304s).
