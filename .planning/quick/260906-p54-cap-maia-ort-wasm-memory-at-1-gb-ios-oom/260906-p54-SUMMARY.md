# Quick task 260906-p54: cap Maia ORT wasm memory at 1 GB (iOS OOM) Summary

Patched both vendored onnxruntime-web glue loaders to reserve 1 GiB instead of 4 GiB of wasm memory address space (fixing FLAWCHESS-9V, an iPhone `RangeError: Out of memory` under WebKit's three-large-reservation-per-page budget), added a vitest gate that fails CI if a future re-vendor drops the patch, and closed a dev-only gap where Vite's COOP/COEP headers were missing from 304 Not Modified responses (which killed the second Stockfish pool worker in WebKit).

## What was built

**Task 1 — cap the ORT wasm memory reservation at 1 GB:**

- Patched the single `new WebAssembly.Memory({initial:256,maximum:65536,shared:!0})` literal in both `ort-wasm-simd-threaded.mjs` and `ort-wasm-simd-threaded.asyncify.mjs` down to `maximum:16384` via the plan's exact `sed` one-liner. Confirmed via `grep -o` counts: each file reads `16384=1 65536=0`, and `git diff --numstat` reports exactly `1 1` per file (one changed line each). The second, unrelated `new WebAssembly.Memory({initial:0,maximum:0,shared:!0})` literal in each file is untouched.
- Added `frontend/src/lib/engine/__tests__/ortRuntimeMemoryCap.test.ts`, a new vitest gate resolving both loaders the same way `maiaWorkerScript.test.ts` does (`fileURLToPath` + `readFileSync`). Per file it asserts exactly ONE match of `/new WebAssembly\.Memory\(\{initial:256,maximum:(\d+),shared:!0\}\)/g` (a re-vendor introducing a second large reservation, or dropping the pattern, fails loudly) and that the captured `maximum` is `<= 16384` (`MAX_ORT_WASM_MEMORY_PAGES`), not `=== 16384`, so a future tighter cap doesn't need a test edit.
- Bumped `ENGINE_ASSET_CACHE_VERSION` 4 -> 5 in `engineAssetCache.ts` with a bump-log paragraph in the existing style, so every returning browser discards the cached 4 GiB-reserving loaders (and the `?v=<n>` bump re-keys the Cloudflare edge — no manual purge needed). Confirmed `engineAssetCache.test.ts` derives its expectations from the constant (no hardcoded `4` literal to update).
- Added a `## Local patch: 1 GB wasm memory cap (quick 260906-p54)` section to `public/maia/README.md` between the WebGPU-preferred-path section and the "Runtime binary ownership" section, covering what/why/legality/re-apply recipe/verify commands/post-patch SHA-256 hashes/residual risk.
- Added a `CHANGELOG.md` bullet under `## [Unreleased]` -> `### Fixed`.

**Task 2 — send COOP/COEP on every dev and preview response, including 304:**

- Added a module-level `CROSS_ORIGIN_ISOLATION_HEADERS` constant in `vite.config.ts`, now the single source feeding both `server.headers`/`preview.headers` (kept as a second line of defense on the 200 path) and the new `crossOriginIsolationPlugin()`.
- The new plugin's `configureServer`/`configurePreviewServer` hooks call `server.middlewares.use(...)` directly in the hook body (not returning a function), which is what installs the middleware ahead of Vite's own static/transform middlewares and VitePWA's dev middleware — necessary because those internal handlers are what produce the unheadered 304. Registered FIRST in the `plugins` array.
- Extended the existing `vite` import with `type ViteDevServer, type PreviewServer` (verbatimModuleSyntax requires the inline `type` modifiers on a mixed import); both interfaces expose `middlewares: Connect.Server` in Vite 8.2.2 (verified directly against `node_modules/vite/dist/node/index.d.ts`). The unused request parameter is named `_req` (`noUnusedParameters`).
- Replaced the Phase 219 D-05 comment on `server.headers` with one explaining the 304 gap this plugin closes and that prod Caddy is unaffected.

## Deviations from Plan

### Process note (not a Rule 1-4 deviation)

A plain `git commit -m "..."` for Task 1 initially swept in a pre-staged, orchestrator-owned rename (`.planning/seeds/SEED-158-*.md`) that the environment instructions explicitly forbade touching or committing — because that rename was already in the index before this task started, and an unqualified `git commit` commits the entire index, not just newly `git add`-ed paths. Caught immediately via `git show --stat HEAD` on the resulting commit. Fixed with `git reset --soft HEAD~1` (which restores the index to its exact pre-commit state, i.e. both the seed rename and this task's six files staged) followed by a pathspec-limited `git commit -m "..." -- <task files>`, which commits only the named paths and leaves everything else — including the seed rename — staged exactly as before. Applied the same pathspec-limited commit pattern for Task 2 from the start. Verified after both commits that `git status --short` still shows the seed rename as `RM ...` (staged, untouched) and neither commit's `--stat` lists it.

No other deviations. Plan executed as written otherwise.
