**Context.** FlawChess is a free, open-source chess analysis platform at flawchess.com. Users import their game history from chess.com and lichess; the platform matches positions by 64-bit Zobrist hash rather than opening name, then reports win/draw/loss rates, blunder and tactic tagging, endgame conversion rates, time-management leaks, and spaced-repetition drills built from the user's own mistakes. Its differentiator is an in-browser engine that fuses Stockfish evaluation with Maia human-move prediction to rank moves by expected *practical* score against an opponent at your rating. The stack is FastAPI + Python 3.13 + SQLAlchemy 2 async + PostgreSQL 18 behind a React 19 / Vite 8 PWA, deployed as Docker Compose on a single Hetzner CPX42 behind Caddy, promoted through a GitLab-Flow `main` → `production` branch pair. Single maintainer, AGPL-3.0, five months old with 3,067 commits.

## 3. What the App Actually Does — Operational Picture

1. **Auth and session** via `../../app/routers/auth.py` and `app/users.py:152-292`: FastAPI-Users with a `BearerTransport` JWT (7-day lifetime, `app/users.py:285`), email/password plus Google OAuth. The OAuth round-trip uses a double-submit CSRF cookie whose token is embedded in the state JWT and compared with `hmac.compare_digest` on callback (`app/routers/auth.py:146-178`, fix for CVE-2025-68481). Anonymous "guest" accounts exist and can be promoted in place to a Google identity.
2. **Import** via `../../app/services/import_service.py` (1,620 LOC): background async tasks fetch chess.com monthly archives sequentially with rate-limit delays, and stream lichess NDJSON line-by-line. Both normalize into one schema (`../../app/schemas/normalization.py`, `app/services/normalization.py:980 LOC`) before storage, filtering to Standard-variant games only.
3. **Position indexing** via `../../app/services/zobrist.py`: for every half-move of every game, three 64-bit Zobrist hashes are computed — `white_hash` (white pieces only), `black_hash`, and `full_hash` — and stored in `game_positions` (`app/models/game_position.py:129-140`). This turns every position query into an indexed integer equality lookup, and makes "my pieces only" system-opening queries (the London across all Black replies) a single-column filter.
4. **Engine analysis** via `../../app/services/engine.py` + `../../app/routers/eval_remote.py`: a long-lived Stockfish UCI pool starts in the FastAPI lifespan (`app/main.py:118`) and is supplemented by volunteer remote workers that lease work over an operator-token-gated API (`app/routers/eval_remote.py:168-198`, fail-closed 403 when the token is unset). Results are applied by `../../app/services/eval_apply.py` (2,664 LOC) and classified into blunders/mistakes plus 20+ tactic motifs by `../../app/services/tactic_detector.py` (2,587 LOC, precision-gated against a committed CC0 lichess puzzle fixture in CI at `ci.yml:141`).
5. **In-browser practical engine** via `../../frontend/src/lib/engine`: Stockfish WASM and a Maia-3 ONNX policy network run in Web Workers (`../../frontend/src/lib/engine/workerPool.ts`, 865 LOC), fused by an expectimax search inside an MCTS budget allocator to rank moves by expected practical score at the user's rating. The same engine drives 24 pinned bot personalities.
6. **Analytics surfaces** via `../../app/services/endgame_service.py` (3,797 LOC), `../../app/services/opening_insights_service.py`, and `../../app/services/stats_service.py`, with per-user percentiles computed against a separate benchmark population database. LLM-narrated feedback goes through pydantic-ai (`../../app/services/insights_llm.py`, 2,578 LOC) with every call logged to `llm_logs` for cost attribution.
7. **Spaced-repetition training** via `../../app/services/train_scheduler.py` + `../../app/repositories/train_repository.py` (2,852 LOC): drills built from the user's own blunders, on a due-date ladder with weekday masks and Monday-start streak weeks. Time-dependent endpoints take `now` from a `dev_now_utc` dependency (`../../app/core/dev_clock.py`) that honors an `X-Dev-Clock-Offset-Minutes` header only when `ENVIRONMENT == "development"`.
8. **Delivery** via `../../deploy/Caddyfile`: Caddy serves the prerendered SPA from `/srv` with per-asset-class cache policy and reverse-proxies `/api/*` to the backend container. Alembic migrations run automatically on backend container start (`../../deploy/entrypoint.sh`).

### Deployment & infrastructure

- Stack: Python 3.13 / FastAPI 0.115 / SQLAlchemy 2 async / asyncpg / PostgreSQL 18; React 19 / TypeScript 6 / Vite 8 / Tailwind 4; Caddy 2.11.2 reverse proxy with auto-TLS.
- Host: single Hetzner Cloud CPX42 (8 vCPU, 16 GB RAM, 160 GB NVMe) running Docker Compose. Postgres tuning lives in `docker-compose.yml:40-62` (`shared_buffers=2GB`, `max_wal_size=8GB`, `shm_size: "256m"`), with explicit `mem_limit`/`memswap_limit` on db (12g) and backend (4g) so an OOM contains itself to a container restart.
- Deploy flow: GitLab Flow. `main` is the integration trunk; a long-lived `production` branch is exactly what runs. Release = PR `main` → `production`, then `../../bin/deploy.sh` triggers `workflow_dispatch` on CI, which re-runs the full gate and only then SSHes to the box for `git reset --hard origin/production` + `docker compose build --no-cache backend caddy`. The workflow aborts on a dirty server working tree (`ci.yml:210-215`) and health-checks `https://flawchess.com/api/health` for 180 s afterwards.
- CI workflow: `../../.github/workflows/ci.yml` — 4 generated-file drift gates, pip-audit, ruff check, ruff format --check, ty, Stockfish install, pytest, tagger precision gate, npm ci, audit-ci, eslint, `tsc -b && vite build`, vitest, a COOP/COEP header guard, knip, docker build, Trivy. Plus `../../.github/workflows/codeql.yml` on Python and TypeScript, weekly + per-PR.

### Disaster Recovery & Backups

- **Database backups:** Hetzner automatic daily whole-server backups (managed by the provider, not a repo cron). Documented at `README.md:142-148`. No logical `pg_dump` layer.
- **Offsite storage:** Yes — Hetzner-managed snapshots are stored off the VM.
- **Point-in-time recovery:** Off. Explicitly stated at `README.md:148`: "PITR: not enabled (point-in-time recovery would require WAL archiving in addition to the daily snapshot)".
- **Restore procedure documented:** Partially — `README.md:144` says recovery happens "via the Hetzner Cloud Console", but there is no step-by-step runbook comparable to the ones that exist for VAPID rotation (`../../docs/push-vapid-rotation-runbook.md`) and email delivery (`../../docs/email-resend-runbook.md`).
- **Last tested restore:** Not tested — no evidence in repo, CI, or docs.
- **RPO / RTO targets:** RPO stated as "up to 24 hours" (`README.md:147`). RTO not defined.

The README is commendably honest about the gap, and even names the missing second layer: "a logical `pg_dump` retained separately would be a useful second layer but is not currently configured" (`README.md:150`). That candor is worth more than a padded claim, but it doesn't change the grade — 24-hour RPO with an untested restore path is the weakest operational dimension here.

**Key insight.** The central architectural bet is Zobrist-hash position matching (`../../app/services/zobrist.py`, `app/models/game_position.py:129-160`): three precomputed 64-bit integers per half-move replace FEN string comparison and named-opening taxonomies entirely. It holds up, and it is the reason the product can do things competitors can't — "show me every game where I reached *this exact structure*, regardless of move order" and "show me the London across all Black setups" are the same indexed integer lookup. The cost is a very high-cardinality `game_positions` table, and the codebase has clearly paid that cost deliberately: natural composite PK `(user_id, game_id, ply)` instead of a surrogate `id` (`app/models/game_position.py:120-131`), `SmallInteger` for `ply`, and partial indexes gated on `ply <= MAX_EXPLORER_PLY` (`app/models/game_position.py:74-94`). The bet is sound and the schema follows through on it.

## 4. Code Quality Findings

### 4.1 Architecture and layering

- The convention is stated explicitly in `../../CLAUDE.md` ("routers = HTTP layer only, no business logic; services = business logic; repositories = DB access, no SQL in services") and the directory shape matches: 16 routers, 52 services, 22 repositories, 30 models, 19 schemas.
- Router prefix discipline is uniform. Every router uses `APIRouter(prefix="/resource", tags=[...])` with relative decorator paths — `app/routers/admin.py:21`, `../../app/routers/eval_remote.py`, `app/routers/users.py:103`. 72 route decorators across 16 files, zero embedding the resource prefix twice.
- **The layering rule is broken in exactly two places, both large.** `../../app/routers/eval_remote.py` is 1,484 LOC with roughly 25 inline `session.execute(select(...))` calls (`:487`, `:496`, `:565`, `:658`, `:759`, `:856`, `:902`, `:909`, `:916`, `:1155`, `:1170`, and more). This is the remote-worker lease/submit protocol, where transaction boundaries genuinely matter and pushing them into a repository would obscure them — a defensible trade, but it is a documented rule with an undocumented exception. The other three routers touching SQL do so trivially (1-3 statements each: `app/routers/imports.py:506-510` is a bulk user-data delete, `app/routers/position_bookmarks.py:74-89` two lookups).
- **`../../frontend/src/pages/Analysis.tsx` is 4,049 LOC with 93 `useState`/`useMemo`/`useCallback`/`useEffect` calls.** The file does declare ~10 small pure helpers at module scope (`fenToRootPly:385`, `flawKey:413`, `bestSanFromPv:433`, `buildFocusedPvLine:508`) and the JSX return doesn't begin until line 3,928 — so roughly 3,400 lines are logic, not markup. CLAUDE.md sets a hard limit of 200 logic LOC per function and mandates extracting data-shaping into a `useXyzData` hook. This file is 17× that limit and is the project's own rule being violated at its largest scale.
- Cross-cutting concerns are properly shared rather than re-derived: one `LastActivityMiddleware` (`../../app/middleware/last_activity.py`, 154 LOC), one rate-limiter family (`../../app/core/rate_limiters.py`, `ip_rate_limiter.py`, `feedback_rate_limiter.py`, `reset_password_rate_limiter.py`), one dev-clock dependency.
- Domain logic is genuinely pure and DB-free where it should be: `../../app/services/endgame_service.py` has 39 functions of which the vast majority are `_aggregate_*` / `_compute_*` / `_build_*` operating on already-fetched rows, with only two `async def` entry points that touch a session (`:1042`, `:1112`).

### 4.2 Code duplication

- **Single source of truth for game filtering.** `../../app/repositories/query_utils.py` defines `apply_game_filters()` and it has **44 call sites** across 8 modules (`openings_repository.py`, `stats_repository.py`, `endgame_repository.py`, `library_repository.py`, `library_service.py`, `train_pool.py`, `schemas/normalization.py`). Time control, platform, rated, opponent-type, recency, and color filtering exist in exactly one implementation. This is the strongest anti-duplication evidence in the codebase.
- **Generated files are gated against drift in CI.** Four separate steps regenerate a TypeScript file from its Python source and fail on any diff: `endgameZones.ts` (`ci.yml:47-50`), `flawThresholds.ts` (`:52-55`), `botStrengthCurves.ts` (`:57-60`), `personaCalibration.ts` (`:62-65`). Threshold constants therefore cannot silently diverge between the Python that computes them and the TypeScript that renders them — a duplication class most projects never close.
- Only 3 `relationship()` declarations exist across 28 tables (`../../app/models`). The codebase deliberately avoids ORM relationship traversal in favor of explicit joins in repositories, which removes an entire category of "same eager-load spelled four ways" duplication.
- Vendoring is used surgically rather than by copy-paste habit: `../../app/services/push_crypto.py` vendors ~110 MIT-licensed lines from webpush-py rather than take the dependency, and `pyproject.toml:50-58` documents why, with a differential test (`../../tests/services/test_push_crypto.py`) pinning the behavior against the original.

### 4.3 Error handling and observability

- **107 `capture_exception()` / `capture_message()` sites in `../../app` against 161 `except` blocks** — a ~66% capture rate, and the uncaptured third is precisely the category CLAUDE.md exempts (expected `ValueError` from parsing user input, `UserAlreadyExists`, retry-loop transients). `app/routers/admin.py:1-6` documents this exemption at the file level: "403/404s raised by `current_superuser` are EXPECTED conditions — do NOT wrap in try/except + capture_exception (would fragment Sentry issues)."
- **121 `captureException` sites on the frontend**, on top of the global `QueryCache.onError` / `MutationCache.onError` handlers in `../../frontend/src/lib/queryClient.ts` that cover every TanStack Query call without per-component boilerplate.
- **Sentry grouping is actively curated, not left at defaults.** `_sentry_before_send` (`app/main.py:71-88`) walks the `__cause__` chain up to a depth bound and collapses every transient asyncpg connection error into a single `db-connection-lost` fingerprint. `_sentry_traces_sampler` (`app/main.py:57-69`) returns 0.0 for the remote-worker poll path prefix so high-frequency lease polling doesn't drown the trace budget, while still reporting errors from those endpoints.
- Frontend noise suppression is equally deliberate and, importantly, fails *open* to reporting: `frontend/src/instrument.ts:20-45` suppresses `ERR_NETWORK`/`ERR_CANCELED` only when the page is unloading or offline, each browser global read behind its own `typeof` guard so an unavailable global reads as "not suppressible."
- Shutdown paths log rather than swallow: six background lifespan loops each get `logger.exception(...)` on teardown failure (`app/main.py:170-200`).
- The one real gap: `../../app/main.py` has a module logger but there is **no `logging.basicConfig` / `dictConfig` / structlog anywhere in `../../app`** (0 grep hits). Log level and format are whatever uvicorn's defaults produce, which is why (per the project's own operational notes) only WARNING+ from `../../app` reaches container logs. See §4.10.

### 4.4 Secrets and configuration

- **No hardcoded credentials in tracked files.** A regex sweep for `(password|secret|api_key|token)\s*=\s*["'][A-Za-z0-9_-]{12,}` across `../../app` and `../../scripts` returned zero hits. The stats script's credential-file sweep returned `CREDENTIAL_FILES_HIGH_CONFIDENCE_COUNT: 0`.
- `../../.env` and `../../.prod.env` exist in the working tree but are **not tracked** — `git ls-files` returns only `../../.env.example`, and `.gitignore:154-156` covers `../../.env`, `../../.prod.env`, `prod.env`, `.envrc`.
- **Boot-time deploy blocker on the default secret.** `app/core/config.py:16` defines `DEFAULT_SECRET_KEY = "change-me-in-production"` and `assert_secret_key_configured()` runs as the *first* statement in the FastAPI lifespan (`app/main.py:96`), before engine startup or job cleanup, so a misconfigured deploy fails fast rather than serving forgeable JWTs. There is a dedicated test for it (`../../tests/test_config_secret_key.py`).
- Config is a single typed `pydantic-settings` `Settings` class with `Literal` types on enumerated knobs (`GEMINI_THINKING_LEVEL: Literal["minimal","low","medium","high"]`, `../../app/core/config.py`), and `../../.env.example` is 6.7 KB of documented keys.
- Four separate `DATABASE_URL_*` variants (dev/test/prod/benchmark) are declared as the single source of truth for maintenance scripts, with an explicit instruction not to port-swap `DATABASE_URL` (`app/core/config.py:20-25`) — the kind of guardrail that prevents a `--db prod` accident.
- Production secrets live only at `/opt/flawchess/.env` on the server; CI injects deploy credentials from GitHub Actions secrets (`ci.yml:196-199`).

### 4.5 Code smells

- **Effectively zero debt markers.** Grepping `TODO|FIXME|HACK|XXX` across `../../app` and `../../frontend/src` returns 4 hits, and all 4 are the literal string `X.XXX` inside p-value formatting docs (`frontend/src/components/popovers/MetricStatTooltip.tsx:72`, `frontend/src/lib/flawComparisonMeta.ts:272`, and two test comments). There is one genuine forward-looking note, correctly scoped and dated to a version: `frontend/tsconfig.app.json:29-31` — `TODO(TS7): baseUrl is slated for removal in TS7 — migrate the @/* paths before upgrading`.
- The reason the count is near-zero is structural, not cosmetic: forward-looking work is captured as numbered seeds in `../../.planning/seeds` rather than as inline comments. That's a healthier location — seeds get triaged at milestone boundaries; inline TODOs rot.

### 4.7 Security

- **OAuth CSRF is correctly implemented, and the fix is documented at the site.** `app/routers/auth.py:146-178` generates a 32-byte `secrets.token_urlsafe` token, embeds it in the state JWT *and* sets it as a cookie with `httponly=True`, `secure=settings.ENVIRONMENT != "development"`, `samesite="lax"`, `max_age=600` matching the state JWT lifetime; the callback compares them with a timing-safe comparison. The comment names the CVE it closes (CVE-2025-68481). There is a dedicated test file (`../../tests/test_oauth_csrf.py`).
- **The remote-worker API fails closed.** `require_operator_token` (`app/routers/eval_remote.py:168-198`) returns 403 when no token is configured on the *server* — so an unconfigured deploy makes the endpoint unreachable rather than open — and 401 on a wrong token, compared via `hmac.compare_digest`. Missing header and wrong token return the same status so the response doesn't leak which.
- Admin surface is minimal and uniformly gated: 3 routes, all `Depends(current_superuser)`, and user search excludes superusers (`app/routers/admin.py:23-30`).
- **SQL injection surface is effectively nil.** 117 `text()` uses across `../../app`, of which 8 are f-strings; every one interpolates a module-level constant or an internally-constructed clause, never request data. `app/models/game_position.py:74-120` interpolates `MAX_EXPLORER_PLY`/`DEDUP_MAX_PLY` into partial-index predicates; `app/services/eval_queue_service.py:369` and `:430` interpolate `guest_clause` and `game_where_sql`, both built from fixed string literals, with all actual values passed as bound parameters (`:tau_s`, `:floor`, `:tc_classical`, …).
- CORS is added **only** when `ENVIRONMENT == "development"`, scoped to `http://localhost:5173` (`app/main.py:223-231`); production is same-origin through Caddy with no CORS middleware at all.
- Vulnerability scanning is layered and each exception is justified in a comment rather than silently allowlisted: `pip-audit --strict` with two ignores (both explained across 12 lines at `ci.yml:67-78` — a pip-internal CVE with no fix, and a vendor-disputed pyjwt advisory), `audit-ci` with a per-advisory allowlist (`../../frontend/audit-ci.jsonc`), Trivy on the built image with `exit-code: 1` on HIGH/CRITICAL, and CodeQL on both languages weekly and per-PR.
- **Gap 1 — production serves no security response headers.** Verified live: `curl -I https://flawchess.com` returns `accept-ranges`, `alt-svc`, `content-type`, `etag`, `last-modified`, `server`, `vary` — and nothing else. There is no `Strict-Transport-Security`, no `Content-Security-Policy`, no `X-Content-Type-Options: nosniff`, no `Referrer-Policy`, no frame-ancestors control. `deploy/Caddyfile:1-80` contains six `header` directives and all six are `Cache-Control`. Caddy does not add any of these by default.
- **Gap 2 — a 7-day JWT lives in `localStorage`.** `app/users.py:285` sets `lifetime_seconds=604800`; `frontend/src/hooks/useAuth.ts:64,101` do `localStorage.setItem('auth_token', access_token)`. There is no revocation list and no refresh-token rotation, so a leaked token is valid for a week and cannot be invalidated server-side. On its own this is a common, defensible SPA trade-off. Combined with Gap 1 — no CSP to constrain script injection — any XSS anywhere in a 98,900-line frontend converts directly into a seven-day account takeover. The two gaps are individually Medium and jointly High.
- Rate limiting exists for the sensitive paths (`../../app/core/ip_rate_limiter.py`, `reset_password_rate_limiter.py`, `feedback_rate_limiter.py`) but is in-process, so it resets on every deploy and would not survive horizontal scaling. Acceptable for a single-box deployment; worth noting if that changes.

### 4.8 Database design

- **Foreign-key discipline is total.** All 26 `ForeignKey()` declarations in `../../app/models` carry an explicit `ondelete` — a grep for `ForeignKey(` minus `ondelete` returns zero. 18 of them point at `users.id`, and the two non-CASCADE cases are deliberate: `benchmark_ingest_checkpoint.py:68` uses `SET NULL` (the checkpoint outlives the cohort user), and `oauth_account.py:15` uses lowercase `"cascade"` (equivalent, just inconsistent casing).
- The apparent exception is not one. `app/models/game_position.py:129-130` declares `game_id` and `user_id` as bare `Mapped[int]`, but the FKs are declared at table level in `__table_args__` via `ForeignKeyConstraint` (`:60`) — required because the table uses a natural composite PK — and the constraint is enforced in the database, added by `alembic/versions/20260324_185335_..._add_foreign_key_constraints_on_user_id_.py:44` after a data-cleanup step at `:30`. The model comment (`:127-128`) explains exactly this.
- 21 `UniqueConstraint` and 24 `CheckConstraint` declarations across 28 tables. The CHECK constraints back the project's stated enum convention: high-cardinality tables use `SMALLINT` + Python `IntEnum` + `CHECK (col IN (...))` (`app/services/endgame_service.py:108` `class EndgameClassInt(IntEnum)`), low-volume domain columns use `TEXT` + `CHECK`. Native PostgreSQL `ENUM` is avoided entirely — the right call, since Alembic doesn't autogenerate enum changes.
- Column types are chosen deliberately, not defaulted: `SmallInteger` for `ply` with the range documented inline ("half-move number (0 = initial), max ~600", `app/models/game_position.py:131-133`), explicit `BIGINT` for the 64-bit Zobrist values, `String(100)` / `String(30)` / `String(16)` sized to their content.
- 28 `Index()` declarations including partial indexes gated on ply bounds (`app/models/game_position.py:74-120`), which keeps the largest table's index footprint proportional to the queried range rather than the stored range.
- **121 migrations, every one with a `downgrade()` function.** 10 of them have a no-op body — and reading the filenames, 8 are one-way data repairs where a reverse is meaningless (`repair_bookmark_hashes_and_sort_order`, `fix_time_control_bucket_for_600s_games`, `wipe_eval_only_residue`, `eval_convention_cleanslate`) and 2 are benchmark-table reshapes. This is the acknowledged outlier that holds the grade at A− rather than A: the pattern is defensible per-migration but nothing in the repo distinguishes "deliberately irreversible" from "downgrade not written yet."

### 4.12 Disaster recovery and backups

- The only backup mechanism is Hetzner's managed daily whole-server snapshot with 7-day rolling retention (`README.md:142-148`). It is offsite and provider-managed, which covers the dominant failure mode (disk or VM loss) well.
- **PITR is off.** Stated explicitly at `README.md:148`. Combined with daily snapshots this means an RPO of up to 24 hours: a failure at 23:00 loses a full day of imports, analyses, and drill progress.
- **No logical backup layer.** No `pg_dump` cron, no script in `../../bin` (14 scripts, none backup-related), no compose service. The README names this gap itself at `:150`. It matters for the failure mode snapshots don't cover: silent logical corruption discovered more than 7 days later, at which point every retained snapshot already contains the corruption.
- **No tested restore.** No runbook, no restore drill record, no CI job. The project has runbooks for narrower operations — `../../docs/push-vapid-rotation-runbook.md`, `../../docs/email-resend-runbook.md` — which makes the absence of a restore runbook conspicuous rather than accidental.
- RTO is undefined. A Hetzner console restore of a 160 GB volume is plausibly 30-60 minutes, but that's an estimate, not a measured or stated target.
- One useful mitigating fact: `../../temp` contains dated `pg_dump` gzips (`flawchess-prod-2026-05-29_083320.sql.gz`), so ad-hoc logical dumps have been taken manually at least once. That's a habit, not a mechanism.

### 4.16 CI/CD execution speed

- **Observed workflow duration:** 8 minutes median across the last 10 runs (7, 7, 7, 7, 8, 9, 9, 9, 9 min; one 3-minute failure). ## 6. Substantial Problems Worth Addressing

1. **Production serves no security response headers.** Verified live: `curl -I https://flawchess.com` returns ten headers, every one of them cache or transport related. There is no `Strict-Transport-Security`, no `Content-Security-Policy`, no `X-Content-Type-Options: nosniff`, no `Referrer-Policy`, and no frame-ancestors control — Caddy adds none of these by default, and all six `header` directives in `../../deploy/Caddyfile` are `Cache-Control`. Minimal fix: one `header` block in the `flawchess.com` site block setting HSTS with a long max-age, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `frame-ancestors 'none'` CSP. A full script-src CSP is a larger job because of the WASM workers and inline prerender output — ship the cheap four first, then iterate toward script-src in report-only mode. *(effort: ≈30 minutes for the four headers, ≈half a day for a report-only CSP; maps to §5 F-01)*

2. **A 7-day JWT in `localStorage` with no revocation, behind no CSP.** `app/users.py:285` issues a 604,800-second token and `frontend/src/hooks/useAuth.ts:64,101` persist it to `localStorage`. There is no server-side revocation list and no refresh-token rotation, so a leaked token stays valid for a week and a compromised account cannot be cut off. On its own this is a common SPA trade-off; combined with problem 1, any XSS anywhere in a 98,900-line frontend converts directly into seven days of account access. Cheapest meaningful mitigation, in order: ship the CSP from problem 1, then shorten the access-token lifetime to hours and add a refresh endpoint, then add a `token_version` integer on `users` that the JWT carries and the strategy checks, giving you a one-UPDATE global revocation. *(effort: ≈1-2 days for the full refresh + revocation path; maps to §5 F-02)*

3. **GDPR erasure exists only as an email address.** `Privacy.tsx:60-67` promises deletion on request to a support mailbox, and there is no `DELETE /users/me` anywhere — grep for `delete_account|deleteAccount` returns zero across both stacks. This is legally permissible but operationally fragile for a single maintainer, and the work is already 90% done: 18 tables carry `ondelete="CASCADE"` on `users.id`, and `app/routers/imports.py:506-510` already demonstrates the multi-table purge for the two tables that aren't cascade-covered. What's missing is one authenticated endpoint, a typed-confirmation dialog, and a test asserting every user-owned table is empty afterwards. *(effort: ≈half a day; maps to §5 F-03)*

4. **No logical backup layer, and no tested restore.** The only backup is Hetzner's daily whole-server snapshot on a 7-day rolling window (`README.md:142-148`). That covers disk loss well and covers logical corruption not at all: a bug that quietly corrupts rows over three weeks is present in every retained snapshot by the time anyone notices. The README already identifies the fix ("a logical `pg_dump` retained separately would be a useful second layer"). Minimal version: a nightly `pg_dump -Fc | gzip` to a Hetzner Storage Box with 30-day retention, plus one drill that restores yesterday's dump into a scratch database and runs a row-count sanity check — write the drill down as `docs/db-restore-runbook.md` while doing it, since the project already keeps runbooks for narrower operations. *(effort: ≈half a day including the first drill; maps to §5 F-04, F-05, F-14)*

5. **A frontend test that flakes at the default timeout, in a suite CI runs at the default timeout.** `src/pages/__tests__/Train.guestGate.test.tsx` failed 2 of its 6 tests at Vitest's 5,000 ms default on this machine and passed all 6 at 20,000 ms. CI runs `npm test` on a shared GitHub runner where contention is at least as bad. This produces red builds that carry no information, which is the fastest way to erode trust in a gate that is otherwise excellent. Note there is currently no `vitest.config.*` and no `test` block in `../../frontend/vite.config.ts`, so there is nowhere central to raise the ceiling — add one. *(effort: ≈30 minutes; maps to §5 F-06)*

6. **Zero dependency caching in CI, at ~21 commits/day.** No `cache:` input on `actions/setup-python@v6` or `actions/setup-node@v6`, no uv cache step, no `~/.npm` cache — every run re-resolves and re-downloads both dependency trees. At an 8-minute median and the current commit pace this is the single cheapest wall-clock win available: `setup-python` with `cache: 'pip'`, a `cache` step keyed on `../../uv.lock`, and `setup-node` with `cache: 'npm'` are three lines each. *(effort: ≈30 minutes for a plausible 1-2 minutes off every run; maps to §5 F-07)*

7. **Two god-files carrying the project's own rule violations.** `../../frontend/src/pages/Analysis.tsx` is 4,049 lines with 93 hook calls and roughly 3,400 lines of logic before the JSX return at `:3928` — against a documented hard limit of 200 logic LOC. `../../app/routers/eval_remote.py` is a 1,484-line router with ~25 inline `session.execute` calls, against a documented "no SQL in routers" rule. Neither is causing incidents today, and the `eval_remote` case has a defensible rationale (transaction boundaries in the worker lease/submit protocol are clearer inline) — but it is an undocumented exception to a written rule, which is how rules stop being followed. Cheapest first steps: write the exception down in `eval_remote.py`'s module docstring, and peel the top 3-4 `useXyzData` hooks out of `Analysis.tsx` rather than attempting a full split. *(effort: ≈1 hour to document the exception; multi-day to actually decompose `Analysis.tsx`; maps to §5 F-08, F-09)*

8. **Bus factor of 1.** 1,923 of 1,926 commits in the last 90 days come from one person, on a project with a 121-migration schema, a volunteer worker fleet, and an untested restore path. The codebase is unusually well documented — `../../CLAUDE.md` is 34 KB, comments explain *why*, and runbooks exist for VAPID and email — which is exactly the mitigation that matters, so this is more "keep doing that" than a defect. The gap worth closing is the operational one: the restore runbook from problem 4, plus a short "what to check when prod is down" page, are the two documents a second person would need first. *(effort: ongoing; maps to §5 F-21)*

## 7. What's Notably Good

- **Zobrist-hash position matching as the architectural spine** — three precomputed 64-bit integers per half-move (`../../app/services/zobrist.py`, `app/models/game_position.py:129-160`) turn position queries into indexed integer equality and enable a genuinely differentiated product feature (system-opening filtering by one color's pieces). The schema follows through: natural composite PK, `SmallInteger` ply, partial indexes gated on ply bounds.
- **Per-run cloned test databases** — `tests/conftest.py:50-78` clones each pytest run (and each xdist worker) a fresh database from a migrated template via `CREATE DATABASE ... TEMPLATE`, under an advisory lock, with the template auto-refreshing whenever the Alembic head moves. Result: 4,275 integration tests against real PostgreSQL in 89 seconds with zero manual maintenance after a migration. This is worth copying to any other project.
- **Generated files gated against drift in CI** — four separate steps (`ci.yml:47-65`) regenerate a TypeScript constants file from its Python source and fail on any diff. An entire class of "the threshold in the chart doesn't match the threshold in the calculation" bugs is structurally impossible here.
- **One `apply_game_filters()` for 44 call sites** — `../../app/repositories/query_utils.py` is the single implementation of time-control, platform, rated, opponent-type, recency, and color filtering across 8 modules. No repository re-derives it.
- **Total `ondelete` discipline** — 26 of 26 foreign keys carry an explicit delete policy, including the table-level `ForeignKeyConstraint` on the composite-PK hot table (`app/models/game_position.py:60`) that a casual grep would miss.
- **A layered, self-justifying supply-chain gate** — Renovate (grouped, scheduled, vulnerability-labeled) + `pip-audit --strict` + `audit-ci` + Trivy on the built image + CodeQL, with every single exception explained in a comment naming the advisory, why it doesn't apply, and what would make it revisitable (`ci.yml:67-78`). Most projects with this many scanners have a silent allowlist; this one has an argument.
- **Sentry configured rather than merely installed** — `before_send` collapses transient asyncpg errors into one fingerprint, `traces_sampler` zeroes out high-frequency worker polls, and the frontend's noise suppression fails *open* to reporting, with each browser global read behind its own `typeof` guard (`app/main.py:57-88`, `frontend/src/instrument.ts:20-45`).
- **Comments that record decisions, not syntax** — `pyproject.toml:37-42` pins `onnxruntime==1.20.1` and names the segfault, the repro file, and the script a future bumper must run. `deploy/Caddyfile:49-59` explains why 30 days beat `immutable` for the ORT WASM. `app/repositories/library_repository.py:2403` warns off `asyncio.gather` at the exact line where it would be tempting. This is what makes a bus-factor-1 project survivable.
- **`asyncio.gather`-on-one-session treated as a first-class hazard** — documented at 10+ call sites as a *reason not to*, with the one legitimate use carrying an explicit "MUST be called with NO session open" precondition (`app/services/eval_apply.py:1422`).
- **Browser-automation and accessibility discipline** — 909 `data-testid`, 336 `aria-label`, and zero `<div onClick>` across ≈85,000 non-test frontend lines.

## 9. Bottom Line

FlawChess is a production-grade codebase that would pass a technical due-diligence review on everything except its external-facing security headers, its GDPR erasure path, and its disaster-recovery depth — three gaps that together represent about two days of work, not a quarter. The engineering discipline is genuinely unusual for a five-month-old single-maintainer project: 91% backend coverage over a real PostgreSQL that finishes in 89 seconds because someone built per-run template cloning, foreign keys with explicit delete policies on all 26 declarations, four CI gates that make generated TypeScript byte-identical to its Python source, and comments that record why a version is pinned rather than what a line does. Anyone reading this codebase top-to-bottom should start with `../../CLAUDE.md`, then `../../app/services/zobrist.py` and `../../app/models/game_position.py` to understand the architectural bet, then `../../tests/conftest.py` for the single best idea in the repository. Expect two god-files (`Analysis.tsx` at 4,049 lines, `eval_remote.py` at 1,484) and a bus factor of 1; expect no rewrite. **This is a codebase where the remaining work is closing three named external-facing gaps, not fixing anything structural — the hard parts are already right.**
